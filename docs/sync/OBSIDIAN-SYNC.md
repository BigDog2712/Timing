# Obsidian 作为两端同步通道（Obsidian Sync / Remotely Save）

> 结论先行：**能用，但同步的不是数据库，而是 vault 里的那几段 Markdown。**
> 两端各有一份自己的 SQLite（离线可用），共享层是 Obsidian 同步的那篇日记。
>
> **把 `.db` 放进 vault 让插件去同步是不行的**，见 §0.2。

## 0. 先说清楚能力边界

### 0.1 两种同步插件都能用，但冲突处理不同

| | Obsidian Sync（官方） | Remotely Save（第三方） |
|---|---|---|
| 同步对象 | vault 里的文件 | vault 里的文件 |
| 冲突处理 | 生成 `xxx (Conflicted copy).md`，让人选 | **按修改时间择一覆盖，往往不留副本** |
| 触发方式 | 自动，近实时 | 定时 / 手动，**手机端需要 Obsidian 在运行** |
| 对 Timing 的影响 | 冲突副本需人工删 | 覆盖更「狠」，但本机 SQLite 兜得住（见 §5.2） |

本应用的设计对两者都成立：**Markdown 是同步协议，SQLite 是本地副本。** 之所以能在
Remotely Save 这种「会整体覆盖」的同步下不丢数据，靠的是三方合并 + 本地库兜底。

### 0.2 为什么不能把电脑端的 `.db` 迁进 vault

这是最容易被想到的方案，也是最危险的一个。四个独立的理由：

| 问题 | 具体后果 |
|---|---|
| **二进制不可合并** | git / 同步插件都只认「整个文件」。两端各记一条，文件就有两个版本，只能二选一，另一边当天的记录**整体消失** |
| **三件套必须原子替换** | SQLite 运行时会产生 `-wal`、`-shm` 两个附属文件。同步插件是一个文件一个文件传的，必然出现「`.db` 已换、`-wal` 还是旧的」的中间态 → **数据库损坏**，不是丢几条记录的问题 |
| **写时占用** | 手机上调库的同时插件在下载替换，SQLite 会拿到损坏的页，直接 `SQLITE_CORRUPT` |
| **失去救援能力** | 这是最关键的：SQLite 留着独立，才能在文件被覆盖后靠三方合并把记录救回来（§5.2）。把它也交给同步通道，等于把救生圈一起扔了 |

顺带一句：一个几 MB 的 `.db` 每次改动都整文件重传，Remotely Save 会很慢，Obsidian
还会把它当附件索引。所以**数据落点必须是 vault 里的 Markdown，不是 `.db`。**

### 0.3 所以设计上只有一条路

**让「共享的数据」以 Markdown 的形式落在 vault 里**，SQLite 退化成「本地索引 / 离线缓存」。
这也正是桌面端 V0.4.0 的 `md-sync` 插件已经在做的事。

## 1. 两层结构

```
┌─────────────────────────── 共享层（Obsidian 同步） ───────────────────────────┐
│  <vault>/<任意目录>/2026-11-03.md                                             │
│    #### 事项计时            ← 两端都读、都写                                  │
│    - [ ] 写作                                                                 │
│      ```yaml                                                                  │
│      planner:                                                                 │
│        log:                                                                   │
│          - start: 2026-11-03 09:00:00                                          │
│            end:   2026-11-03 09:30:00                                          │
│            duration: 30m00s        ← 只给人看，不参与落库                      │
│      ```                                                                      │
│    #### 便利贴              ← 目前只有桌面端写（手机没有便利贴功能）             │
└───────────────────────────────────────────────────────────────────────────────┘
        ↑ 读/写                                          ↑ 读/写
┌───────────────────┐                          ┌───────────────────┐
│ 桌面 Timing      │                          │ 安卓 Timing      │
│ %APPDATA%/...db   │  ← 私有层，不同步 →      │ 私有 timing.db   │
└───────────────────┘                          └───────────────────┘
```

两层的职责：

- **共享层**决定「这一天有什么」；
- **私有层**负责「界面快、离线也能用」，随时可以由共享层重建。

## 2. 「存储结构一致」具体一致在哪

| 维度 | 桌面端 | 安卓端 | 是否一致 |
|---|---|---|---|
| 表名 | `items` / `time_records` / `todos` | 同名 | ✅ |
| 关键列 | `started_at` / `ended_at` / `accumulated_sec` / `deleted_at` | 同名同义 | ✅ |
| 同步预留列 | `uid` / `device_id` / `rev` | 同名 | ✅ |
| 共享文件 | `{date}.md` | `{date}.md` | ✅ |
| 区块标题 | `#### 事项计时` | `#### 事项计时` | ✅ |
| 时间格式 | `yyyy-MM-dd HH:mm:ss`（本地时区） | 同 | ✅ |
| 归日依据 | `started_at` 落在当天 | 同 | ✅ |
| 进度中段落 | `ongoing: true` 标记 | 原样搬运，不参与合并 | ✅ |
| 便利贴（notes） | 支持 | 未实现 | ⚠️ 单端 |
| 待办（todos）同步 | 支持 | 未实现（只有本地待办） | ⚠️ 单端 |

> 差异项都不影响计时同步：手机不改 `#### 便利贴`，桌面端也不会碰手机的计时区块。

## 3. 落点可配置（能不能放在程序外部）

**两端都可以，但实现方式不同。**

### 桌面端：直接填绝对路径

设置 → 同步 → 填「根目录」。校验规则只有两条（`models/md_sync.rs::validate`）：

- 长度 ≤ 512 字符；
- 不能含换行。

不限制必须在程序目录内，所以 `D:\Obsidian\MyVault\Diary`、`\\NAS\share\Diary`
都能用；还支持 `%USERPROFILE%` 和开头的 `~` 展开。文件模板必须是**相对路径**
（不能带盘符、不能有 `..`）。

### 安卓端：用系统目录选择器（SAF）

**不能填路径**，这是 Android 的硬限制：Android 11 起分区存储禁止应用按
`/storage/emulated/0/...` 写共享存储，直接写会 `EACCES`。

替代路径是 SAF：

1. 设置 → 同步 → 点「日记目录」；
2. 系统弹出目录选择器，进到 Obsidian vault 里，选中放日记的那个目录；
3. 点「使用此文件夹」→ 允许。

拿到 `content://.../tree/...` 之后调 `takePersistableUriPermission` 把授权长期化，
**重启 App 后依然有效**。效果与填路径等价，只是目录由用户点选而不是手打。

技术上：`core/md/SafVault.kt` 用 `DocumentsContract` 直接读写（没有引 AndroidX 的
`DocumentFile`，以维持「零运行时依赖」）。

> ⚠️ 选 `Android/data/...` 或 `Android/obb/...` 下的目录会失败 —— 这两个目录在
> Android 11+ 对 SAF 关闭。Obsidian vault 一般不在那里。

## 4. 两端怎么配成一对

必须三项完全一致，否则会各写一块、互不相认：

| 配置 | 桌面端 | 安卓端 |
|---|---|---|
| 目录 | `...\MyVault\Diary` | 在系统选择器里选 `MyVault/Diary` |
| 文件模板 | `{date}.md` | `{date}.md` |
| 标题行 | `#### 事项计时` | `#### 事项计时` |

桌面端另有「立即同步」；安卓端每 20 秒自动跑一轮（仅前台），设置页也能手动触发。

### 手机端建库与 Remotely Save 的落地步骤

1. 手机装 Obsidian → 新建一个 vault。位置随意，**只要不在 `Android/data` / `Android/obb` 下**
   （那两个目录对系统选择器关闭，Timing 选不进去）；
2. 装 Remotely Save → 配同一个远端（WebDAV / 坚果云 / OneDrive / S3 都行，和电脑端同一套凭据）
   → 先同步一轮，把 `Diary/` 目录和已有日记拉下来；
3. 手机装 Timing → 设置 → 同步 → 打开开关 → 点「日记目录」→ 在选择器里选到
   `<vault>/Diary` → 允许；
4. 把「文件模板」和「标题行」调成与桌面端**完全一样**；
5. 点「立即同步」，状态应显示「收下 N 段」或「无变化」。

顺序建议是**先让 Obsidian 把目录拉下来，再选目录**。反过来也能用（Timing 会自己建目录
和文件），只是 Obsidian 那边要再同步一次才看得到新文件。

之后每次要用的时候：Timing 记录 → 打开一下 Obsidian（或在后台让它活着）→ 等它自动同步。
Timing 不负责上传，它只负责把那篇 `.md` 改对。

## 5. 冲突怎么处理（这是双端同步的核心）

桌面端原本是单机逻辑：以「上次写出的内容」为基线，二选一（SQL 变了就导出、
文件变了就导入）。**双端下二选一必然丢数据**——手机刚记的会被桌面刚写的覆盖。

所以安卓端升级成**三方合并**（`core/md/MdMerge.kt`）：

| 记号 | 含义 |
|---|---|
| `base` | 上次本机写出的区块（两端都见过的那一版） |
| `local` | 本机数据库现在的内容 |
| `remote` | 日记文件现在的内容 |

按 `(事项, 开始时刻)` 逐条判定：

| 情形 | 取值 | 说明 |
|---|---|---|
| `local == remote` | 任意 | 两边一致，含「都删了」 |
| `local == base` | `remote` | 只有对面动过 → 新增/修改/删除都传导过来 |
| `remote == base` | `local` | 只有本机动过 |
| 其余 | `remote` | 真冲突，文件优先 |

以 `(事项, 开始时刻)` 为键意味着「同一条被两端同时改」几乎不会发生：时段记录一旦
落盘就不可变，用户也不会去手改秒数。

`ongoing: true` 的实时段**不参与合并**（桌面端每两秒刷一次，参与比较会让基线永久抖动），
只做原样搬运——本机既不吞掉它，也不假装是已完成的记录。

### 为什么在 Remotely Save 下不会被「写死」

Remotely Save 会**整体覆盖**文件。假如本机每轮都判「文件变了」→ 写回 → 上传 → 另一端
也判变了 → 再写回，两端就会无限互相覆盖，既费流量，也可能把刚记的数据冲掉。

应用里有三道闸门，都锁在单测里（`MdRoundTripTest`，7 条）：

| 闸门 | 做法 | 防的是什么 |
|---|---|---|
| 归一化比较 | 比 `render(parse(body))` 而不是原文 | Linter / YAML 格式化插件改缩进、给 `duration` 加引号，不该算内容变化 |
| 无变化不写 | 归一化后相同就完全不碰文件 | 不碰文件 → mtime 不跳 → Remotely Save 不会认为需要上传 |
| 截断检测 | 围栏不成对 / 出现非法 UTF-8 / 整篇突然变空 | 读到写了一半的文件时整轮跳过，**绝不把「读到的缺失」当成「用户删除」** |

对应的不变量是「**合并结果渲染后必须与文件里的区块逐字节相同**」。测试里用真实形状的
日记跑「桌面写 → 手机收 → 手机写 → 桌面写 → 手机收 → 再跑一轮」，最后一步必须完全不动。

### 唯一会真丢数据的地方：半截文件

SAF 的 `openOutputStream(uri, "wt")` 是**就地截断写**，不是原子替换。同步插件在下载、
Obsidian 在重写、本应用在写入，三方随时可能撞上，于是「读到半个文件」是真实存在的窗口。

后果比看起来严重：半截文件里少掉的条目，在三方合并里会被判定成「用户删了」，本机
跟着删库。所以 `MdTimers.looksTruncated()` 一旦命中就**整轮跳过**——宁可晚一轮，不能删错。

判据都是精确的，不会误伤正常编辑：代码围栏 ` ``` ` 必须成对；解码后不能出现替换字符
`\uFFFD`；整篇突然变空而基线非空（用户删区块会留下标题和正文，不可能清成空文件）。

## 6. 已知限制

1. **只同步「当天」。** 基线按天存，打开 App 时同步今天的日记。历史日期由桌面端照常维护；
   手机上改历史日期不会回写。
2. **两端同时写会有秒级窗口。** 手机每 20 秒一轮、桌面每 2 秒一轮，理论上存在「桌面读到旧
   文件后又基于旧基线写回」的竞态。窗口很窄，且桌面写入前会先读一次并留备份
   （`md_backup`）。真正长时间离线再合并的情况不会丢数据，只会多一个冲突副本。
3. **冲突副本的差异。** Obsidian Sync 在两端并发写时会生成
   `2026-11-03 (Conflicted copy ...).md`；**Remotely Save 通常不生成，直接按修改时间择一覆盖**。
   两种情况本应用的合并逻辑都管不到那个副本本身，需要人工看一眼（一般删掉较旧的一份）。
   被覆盖掉的记录不用担心——本机 SQLite 还留着，下一轮同步会靠三方合并写回去。
4. **手机端 Obsidian 必须真的在跑。** Remotely Save 的定时同步挂在 Obsidian 进程上，
   Obsidian 被杀掉就不会上传。所以完整链路是「Timing 写文件 → Obsidian 同步 → 云端」，
   中间那步需要一个活着的 Obsidian。本应用能做的只是把文件写好。
5. **不要在手机端「清除数据 / 重装」而没先同步。** SQLite 是本地副本，也是被覆盖时的
   救援来源。它没了，未上传的那几条就真没了。
6. **待办 / 便利贴还没进手机。** 手机改了这两块不会被同步。
7. **手机删除当天最后一条**时，区块会变成空标题，桌面端读到空区块会清空当天记录
   —— 与桌面端既有的「文件是完整真相」语义一致。
8. **两端系统时钟差太多会影响 Remotely Save 的判定。** 它多半按 mtime 择新，手机时间
   明显落后时可能不覆盖云端。两端都开自动对时即可。
9. **未在真机验证。** SAF 实际读写行为、以及不同 ROM 的文件选择器表现需要装机确认。

## 7. 装机自检清单

1. 桌面端建好目录，设置 → 同步 填好路径、模板、标题，点「立即同步」；
2. 确认 `2026-11-03.md` 里出现了 `#### 事项计时` 区块；
3. 手机装 0.3.1 → 设置 → 同步 → 点「日记目录」→ 选中**同一个目录**；
4. 手机记一段 1 分钟以上的计时 → 回设置页，状态应显示「写入日记 · HH:mm」；
5. 打开手机 Obsidian，让 Remotely Save 跑一轮（或手动点同步）；
6. 桌面端 2 秒内应看到新时段出现在日记里（`#### 事项计时` 下）；
7. 反过来在 Obsidian 里手改某个 `end:`，手机同步后「记录」页应对应更新；
8. 关键一步：**两端各记一条，再各同步一次，确认两条都在**。这一步过了才算真通。

任何一步失败，先看设置页那行状态文案（`MdCfg.lastStatus`），它会写明是「授权失效」
「无法创建文件」还是「写日记失败」。
