# 事项为中心的计时模型（设计 + 施工书 · v2）

> 目标形态：**事项是主数据，应用活动是它的子记录**。
>
> ```
> 记录：事项「学习SQL」 分类「学习」 09:30–11:30
>   子  chrome    分类「学习」 09:30–11:00
>   子  pycharm   分类「学习」 11:10–11:30
>   子  Bilibili  分类「摸鱼」 11:00–11:20   （手机）
> ```
>
> v2 相比 v1 的两处实质改动：**分类规则从 5 条压到 3 条**（不再需要 `pinned` 与上下文覆盖行）、
> **同步从「状态快照」改为「事件流」**（§7，这是 v1 最脆弱的一环）。
>
> **v2.1 落地修正**（写代码时发现的，均已在本文档正文改正）：
> 1. `app_category` 从业务库**移到活动库** —— 分类的读写入口（`classification_settings` /
>    `resolve_session_category`）本来就全在活动库这套 pool 里，子记录切片也在活动库侧做。
>    放业务库等于每次解析都跨库取配置，而两个 pool 不能 JOIN。事项的 `category_key` 随块
>    投影过来（`focus_blocks.category_key` 是快照），活动库侧解析**不需要**读业务库。
> 2. `block_segment_override` 同理放活动库（切片时应用，与块同库）。
> 3. 所有新表的 `uid` 统一成 `前缀:设备:id`（与 `sessions`/`time_records` 同型），
>    靠自增 `id` 而不是复合键 —— 这样 `adopt_rows` 那套「认领 `device_id` + 补 uid + 查重」
>    可以原样复用，不必为每张表各写一套。

## 1. 现状：四处对不上

| # | 现状 | 后果 |
|---|---|---|
| P1 | `items` 在 `timing.db`，`sessions` 在 `patina.db` | 两库不能 JOIN，事项**根本进不了时间轴** |
| P2 | 分类是单值 KV：`__app_override::<exe>` → 一个分类 | chrome 无法同时是「学习」与「游戏」 |
| P3 | 事项↔应用只有单值 KV：`__app_item_binding::<exe>` → 一个 `itemId` | 一个应用只能挂一个事项，一个事项挂了几个应用无处存 |
| P4 | 计时状态是**行状态**（`status='active'`） | 无法表达「PC 发起、手机结束」——这需要跨设备写同一行 |

**已就绪、不需要重做**：`time_records` 的 `device_id` / `uid`（业务库 0009 guard）。数据结构在位，语义要改（§7.8）。

## 2. 概念模型：意图 / 事实 / 归属

```
意图（intent）      items             「我打算做学习 SQL」
事实（fact）        sessions          「17:03 我在 chrome 上」
归属（attribution） blocks            「09:30–11:30 这段归给学习 SQL」
操作（op）          timer_ops         「9:40 发起 / 9:50 结束」← 新增，§7
```

**子记录 = 事实 ∩ 归属块**，是**派生视图**，不建表。

### 为什么子记录绝不落表

反方案（子记录建表 + `parent_block_id` 外键）在四处立刻坏：

1. **块可变**。块从 09:30–11:30 改成 09:00–12:00，已落库的子记录要么全重写（双写），要么与块不一致。
2. **事实跨边界**。chrome 09:00 用到 10:00、块是 09:30–11:30，子记录只能是 `[09:30,10:00]` 这个**切片**；落表就得把一条事实拆两行，`sessions` 就不再是原始事实。
3. **块可以没有事实**（划了块去开会，电脑没记录）。派生给「空档」，落表只能造假 0。
4. **双端并行产生两条重叠块**。落表的子记录在重叠区双份，sum 直接翻倍。

所以：**事实表只存事实，块只存归属，子记录在读取时算。**

-- ⑤ 计时操作日志（事件真源，§7）------------------------------------------
CREATE TABLE IF NOT EXISTS timer_ops (

  device_id   TEXT    NOT NULL,
  seq         INTEGER NOT NULL,   -- 本机单调递增
  session_uid TEXT    NOT NULL,   -- 被操作的会话（start 造出来的那个 uid）
  item_uid    TEXT    NOT NULL,   -- 冗余，便于按事项取事件

  day_key     TEXT    NOT NULL,   -- = start op 的本地日，分片按它落天（§7.5）
  payload     TEXT,               -- start 的 mode/target_sec、adjust 的新起点
  created_at  INTEGER NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_timer_ops_device_seq ON timer_ops(device_id, seq);
CREATE INDEX IF NOT EXISTS idx_timer_ops_session ON timer_ops(session_uid, at_ms);
CREATE INDEX IF NOT EXISTS idx_timer_ops_day ON timer_ops(day_key);
```

### 3.2 为什么深度硬限 2 层

用户给的例子是「事项 → 子事项」一层。允许无限深会立刻产生三个无解歧义：

- 块挂哪一层？（挂子事项上，父事项时长要不要含它？）
- 父事项能否独立计时？（能，就和所有子事项并行重复计时）
- 聚合 rollup 到哪一层出报表？

**限 2 层 + 块只挂叶子**（有子事项的事项不可计时），三个歧义全部消失。要更细的维度用标签，不要用树。

### 3.3 活动库 `patina.db` · 迁移 0030

```sql
-- 块的投影（真源是业务库 fold(timer_ops) → time_records，§5）
CREATE TABLE IF NOT EXISTS focus_blocks (
  uid           TEXT PRIMARY KEY,   -- 同 time_records.uid
  device_id     TEXT NOT NULL,      -- 发起设备
  item_uid      TEXT NOT NULL,      -- 指向 items.uid（跨库，不建 FK）
  item_name     TEXT NOT NULL,      -- 投影时快照
  category_key  TEXT,               -- 投影时的事项分类快照
  start_time    INTEGER NOT NULL,
  end_time      INTEGER,            -- NULL = 进行中
  updated_at_ms INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_focus_blocks_range ON focus_blocks(start_time, end_time);
CREATE INDEX IF NOT EXISTS idx_focus_blocks_item ON focus_blocks(item_uid, start_time);
```

**存快照的理由**：时间轴要秒开，且事项改名后历史块应显示**当时的名字**。与 `app_usage`「不存显示名」的取舍相反，因为块是可读记录，改名会让历史整体漂移。

## 4. 分类解析：3 条规则

### 4.1 规则

```
resolve_child_category(app_categories /* 按 priority 升序 */, item_category) :
  1. item_category 非空 且 ∈ app_categories  → item_category      // 有对应分类 → 按事项分类
  2. app_categories 非空                       → app_categories[0] // 无对应 → 按分类首位
  3.                                           → 'other'
```

### 4.2 真值表（用户的例子就是验收用例）

| 事项分类 | 应用 | 应用的分类（按首位排序） | 结果 | 命中 |
|---|---|---|---|---|
| 学习 | chrome | 学习, 工作, 娱乐, 游戏 | 学习 | 1 |
| 学习 | pycharm | 学习 | 学习 | 1 |
| 学习 | bilibili | 摸鱼, 娱乐 | **摸鱼** | 2 |
| 游戏 | chrome | 学习, 工作, 娱乐, 游戏 | **游戏** | 1 |
| 游戏 | wechat | 社交 | **社交** | 2 |
| 游戏 | bilibili | 游戏, 摸鱼, 娱乐 | 游戏 | 1 |
| 游戏 | 未分类应用 | （空） | other | 3 |

七行与你给的例子逐条一致，最后一行是唯一兜底。

**「分类首位」是用户可调的**：`app_category.priority` 最小者即首位。bilibili 把「摸鱼」排在「娱乐」前，就是它在学习记录里显示摸鱼、而在有「游戏」分类时按 §4 规则 1 显示游戏的全部原因。

### 4.3 uid 前缀登记

| 前缀 | 表 | 形态 |
|---|---|---|
| `s` | sessions | `s:<device>:<id>`（已有） |
| `t` | time_records | `t:<device>:<id>`（已有） |
| `i` | items | `i:<device>:<id>`（本轮启用） |
| `b` | item_app | `b:<device>:<item_id>:<app_key>` |
| `c` | app_category | `c:<device>:<app_key>:<category_key>` |
| `o` | block_segment_override | `o:<device>:<hash>` |
| `p` | timer_ops | `p:<device>:<seq>` |

`n` / `d` 已被占用（notes / dashboard 视图），**不能再分配**。前缀常量集中在 `data/schema_registry.rs`，新增一项必须同步加唯一索引，否则 uid 静默重复、LWW 判错。

## 5. 块怎么进活动库

时间轴、聚合、读模型、历史页**全在 `patina.db`**；块的折叠结果在 `timing.db`。两个独立 pool，**不能 JOIN**。

### 方案 A：单向投影（推荐先做）

`time_records`（= `fold(timer_ops)` 的物化）是真源；`focus_blocks` 是**可重建投影**。

- 投影时机：fold 提交后立即补投影（同一命令内；失败不回滚业务库，只记待补）；启动时全量对账。
- 幂等：`INSERT ... ON CONFLICT(uid) DO UPDATE`。
- 对账判据：`count + max(updated_at_ms)` 两边比，不一致按 uid 重推。
- **判据**：清空 `focus_blocks` 能完整重造 ⇒ 是投影；不能 ⇒ 是双写。

### 方案 B：`time_records` 整体搬到 `patina.db`

更干净，但 **48 个文件**引用（面板计时、待办、倒计时、md 导入、appdata 迁移、手机端），且是 `md_sync` 的同步对象。P1 级搬迁，不与本轮混做。

**裁决点 D1**：先投影（A），还是排期搬迁（B）。

## 6. 读取路径：子记录怎么算

`cmd_get_item_timeline(from_ms, to_ms, device_scope)`：

```
1. blocks   = focus_blocks ∩ [from, to]        → 按 item_uid 聚合
2. logical  = union_of(blocks per item_uid)     ← 双端并行块先求并集
3. sessions = sessions ∩ [from, to]             ← 走 idx_sessions_device_date
4. for b in logical:
     for s in sessions where overlap(s, b):
        seg = [max(s.start,b.start), min(s.end,b.end)]
        if seg.empty: continue
        cat = resolve_child_category(app_categories(s.app_key), b.category_key)
        push({ block:b.uid, app:s.app_key, cat, seg })
5. 套 block_segment_override：命中则改判 / 剔除
6. 块内没有任何 session 的区间 → 产出 "unmeasured" 空档（不是 0）
```

三条必须钉住的口径：

- **步骤 2 必须先求并集**。同一事项两端各一条块，直接相加会把 9:30–11:30 算成 4 小时。复用 P2 的 `running max`，禁 `LAG`。
- **空档显式产出**。块 09:30–11:30、事实只有 09:30–11:00，那 11:00–11:30 是「未采集」不是「0 秒」——显示 0 会让用户以为计时坏了。
- **跨块事实只取交集**。剩余部分仍是「无主应用时间」，浅色独立显示——这是用户能看出「这条事项其实只占了一半」的唯一途径。

## 7. 同步：传操作，不传状态

### 7.1 为什么必须是事件流

要求的动作是「**PC 9:40 发起 → 手机同步后进入计时中 → 手机 9:50 结束 → PC 同步后结束并把时间写进数据**」。

如果同步传的是**行状态**，这个动作要求手机去改 PC 那一行 ⇒ 直接推翻 P4 的唯一支点「**一行永远只有它的属主写**」。一旦允许非属主写，就需要冲突解决、需要服务端 seq，整个「服务端可以砍掉」的结论随之崩塌。

传**操作**则完全不需要：手机产生的是一次 `stop` 事件，**这条事件属于手机**，PC 那条 `start` 事件一个字节都没被改。

```
sync 传 timer_ops（append-only）  →  两端各自 fold  →  两端的 time_records 一致
```

这就是「云端存的是数据执行的操作」这句话的严格形式。

### 7.2 事件语义

| kind | 语义 | 折叠作用 |
|---|---|---|
| `start` | 发起计时，`payload` 带 `mode`/`target_sec` | 开一个新会话 |
| `pause` | 暂停 | `accumulated += at - running_since` |
| `resume` | 继续 | `running_since = at` |
| `stop` | 结束 | `ended_at = at`，收口 |
| `adjust` | 改起点（手工修正） | `started_at = payload.started_at` |
| `drop` | 作废整个会话 | 折叠后不产出块 |

**关键**：`stop` 的 `at_ms` 是**语义时刻**（手机 9:50 按下那一刻），不是 PC 同步到的时刻。所以 PC 在 9:55 收到，也把会话收到 9:50 —— 这正是「将对应时间写入数据」。

### 7.3 折叠（纯函数）

```rust
fn fold_session(ops: &[TimerOp]) -> Option<Block>
```

- 排序键：`(at_ms, device_id, seq)` —— **不能只按本地时钟排**（时钟回拨会乱序）；`device_id + seq` 是打破同毫秒并列的确定性 tiebreak。
- 同会话出现**两条 stop**（两端同时结束）⇒ 取排序键最小的那条，另一条不改变结果（幂等，天然收敛）。
- `stop` 之后又收到 `resume`（对端不知道已结束）⇒ 忽略并告警，**不要**复活会话。
- 无 `stop` 的会话 ⇒ `end_time = NULL`（进行中）。

### 7.4 「共享一个会话」与「各起一个会话」是两件事

必须分开，否则实现会乱：

| 场景 | 表现 |
|---|---|
| **共享**（这一轮要的） | 一个 `start`，事件流里只有一条会话。两端 fold 出**同一条块**，双方 UI 都显示「计时中」。任意一端 `stop`，两端都结束。 |
| **并行**（上一轮要的「双端可同时对同一事项计时」） | 两个 `start`（各端各点一次），两条会话、两条块。UI 显示两个进行中，聚合按 **union** 不按 sum。 |

共享是默认行为（同步后自动唤起）；并行需要用户在另一端**主动再点一次开始**才产生。

### 7.5 分片：按「会话归属天」，不按事件时刻

一个 9:40 开始、次日 1:00 结束的会话，`start` 与 `stop` 落在不同自然日。若按事件时刻分片，fold 要跨两个 `day-*.jsonl` 拼事件，且拉取范围得覆盖所有相关天。

**规则：`timer_ops.day_key` 一律等于该会话 `start` 的本地日**（不是 `at_ms` 的日）。这样同一会话的全部事件永远在同一个分片里，fold 不需要跨文件。`sessions` 表本来就按 `start_time` 落天，口径一致。

### 7.6 兼容既有 P4

- `timer_ops` 是普通行，同样走 T12 的合并内核与行级 LWW。事件不可变，同 uid 重传内容相同，LWW 无害。
- `timer_ops` 也可被墓碑删除（彻底清数据），墓碑类别常量新增 `p`。
- **`time_records` 从「同步对象」降级为「本地物化视图」**：不再跨端传，因为它能从事件流重算。`INCLUDE_TIME_RECORDS` 随之作废（由 `INCLUDE_TIMER_OPS` 取代）。

### 7.7 前置：主数据过桥

现在 `INCLUDE_TIME_RECORDS = false`，注释写明「`items` 不过桥 ⇒ `item_id` 跨设备悬空」。要落地本设计必须先过桥：

- `items` / `item_app` / `app_category` 加入分片。
- 历史 `time_records` 的 `item_id` 在另一端会悬空 ⇒ 导出时把不存在的 `item_id` 折成 `1`（未归类）并告警，**不要**导出悬空外键。

### 7.8 索引语义的变化（本轮最危险的一处）

`uq_records_open_per_device`（`ON time_records(device_id) WHERE status='active'`）原本表达「**本机**最多一条进行中」。共享会话后，`device_id` 变成「**发起设备**」，这条索引表达的是「一个发起端不会重复发起」，**不再限制本机同时跑几个**。

所以「本机同时只允许一个进行中」必须由**应用层**保证（本机 running 状态本来就是 fold 出来的）。这条不能只写在注释里——漏了会出现「药丸显示 A、实际在跑 B」。

## 8. 手机端精确子记录（一条硬依赖）

`app_usage` 只有**按天聚合**（包名 + 当天累计秒），拿不出「11:00–11:20」。用户例子里的手机子记录**当前无法实现**。

二选一：

- **B1（准）**：Kotlin 侧 `UsageStatsManager.queryEvents` 取 `ACTIVITY_RESUMED/PAUSED`，生成手机 `sessions` 行（`device_id` = 手机，与桌面同表）。系统只留约 7 天明细，需当天落库。
- **B2（粗）**：按 15 分钟桶上报「某包在某桶内前台多少秒」，时间轴显示为粗粒度段。

B1 才能对上分钟级例子。`app_usage` 继续保留（跨天趋势、系统给不了的历史），两者不互相替代。

### 施工必踩的坑

- **`uq_records_open` 每次启动由 `0002_v020.sql` 重建**。0009 guard 的 `DROP` 是唯一抵消点，新迁移不能替代它；动这块先读那一整个文件的头注释。
- **`schema_revision_limit()` 绝不加新版本探测项**。加了 = 账本被整表改写成「已应用」而迁移从不执行，开机即 `schema validation failed`。
- **`item_app.app_key` 必须与 `sessions.app_key` 同一归一函数**。仓里踩过：建键 / 读表 / 行渲染三处用了不同归一 → 绑定了却匹配不上。
- **跨库不建 FK**。`focus_blocks.item_uid`、`block_segment_override.block_uid` 都是逻辑引用，删事项要显式级联清理。
- **事件排序绝不用「本地时钟单独排」**。排序键必须带 `device_id + seq`，否则同毫秒并列时两端 fold 出不同结果——而这类不一致只在两端都同步过完整历史后才显形。

## 11. 这个设计不做的事

- 不做「事项占满时间轴」：一天里可能只记了 3 个块，剩下是无主的。
- 不做子记录持久化（§2），手工修正走覆盖表。
- 不做实时推送：P4 是按天分片离线传输，「手机结束 1 秒后 PC 变」做不到，只能做到「同步完成那一刻」。
- 不把应用分类塞进 `sessions`：`app_usage` 迁移头注释已写明「不存显示名与分类，那两样会变，存进来就是过期副本」。

### 实现期才发现的事实

1. **`timer_ops` 的 `device_id` 必须由调用方显式写入**。`uid` 由 `AFTER INSERT` 触发器按它拼，
   漏了就是「uid 恒为 NULL ⇒ 这条事件永远不被导出 ⇒ 零报错」。同一件事在
   `start_session` 的 `time_records` 插入上一样成立（既有的 `insert_active` 就没写，
   所以老计时行的 `device_id` 一直是哨兵 `''`）。
2. **`DROP TABLE sync_tombstone` 在触发器引用它时会直接报错**
   （`error in trigger ...: no such table`，实测）。重建表前必须先 `DROP TRIGGER`，
   再由 0011 guard 把触发器建回来。文档里原本只写了「重建表」，漏了这一步。
3. **`append` 不能从「首条事件」抄 `item_uid`**。原型里这么写，结果 `start` 自己写不进去
   （它要抄的那条事件就是它自己）—— 报 `timer session 't:...:1' has no start event`，
   而空事件列表与「还没开始」长得一模一样。改成从
   `time_records JOIN items` 取。
4. **事件时刻与落库时刻必须是同一个数**。事件按**单调时刻** `at_ms`（不早于上一条），
   落库原本用裸墙钟 `now`，两者差几毫秒 ⇒ `folded_block_agrees_with_time_records`
   报「终点必须一致」。修法不是在断言里放宽容差，而是 `timer_stop::stop` 把
   `at_ms` 同时传给 `discard(...)` 与 `timer_split::finalize(...)` ——
   **让「用户按下的那一刻」只有一个数**。
5. **`device_id` 的跨平台取值只有一条路**：`services::identity` 的 `OnceLock` 缓存。
   不能每条命令现读文件（每次计时都碰一次磁盘），也不能只放在桌面侧的 `insight` 层
   （`timer.rs` 跨平台，安卓拿不到）。缓存挂在 `services` 顶层，
   由两条 `startup_*` 预热。

## 13. 与既有 KV 配置的共存（造不成「两套真源」，但**必须先解**）

### 现状

界面上的「应用 → 分类」「应用 → 事项」今天仍然写在设置表 KV 里：

| 键 | 语义 | 落点 |
|---|---|---|
| `__app_override::<exe>` | 这个应用归哪个分类（**单值**） | 业务库设置表 |
| `__app_item_binding::<exe>` | 这个应用平时做哪个事项（`{"itemId":123}`） | 业务库设置表 |

而本轮新增的 `app_category`（活动库，**多值 + priority**）与 `item_app`（业务库，**多对多**）
是目标模型。两边同时存在 ⇒ 改一处不改另一处 ⇒ 界面显示一套、子记录切出来另一套。

### 为什么**这一轮故意不建镜像**

`app_category` 目前只有一个消费者：`focus_blocks::block_detail` 的切片。而 `block_detail`
的调用方是**还没写的时间轴双层渲染**（§12 还没做）。也就是说：

- 现在建「KV → 新表」的启动镜像，会得到一条**没有任何消费者**的写路径；
- 而按本仓自己的判断标准——「留一个没人调的接口只会让人以为 UI 已经接了」——
  镜像比不建更糟：它会让下一个接手的人以为迁移已经完成。

`item_app` 同理：4 条命令有了，界面上还是双击应用行写 KV。

### 落地时必须一起做的三件事

1. **方向的唯一性**：新界面（T14/T15 的 CRUD 面板）上线的那一刻，KV 写入点必须**同时删掉**
   （`appItemBinding.ts` 的 `commitClassificationSettingMutations` 调用与
   `classificationStore.ts` 的 `APP_OVERRIDE_KEY_PREFIX` 写侧）。
   迁移期间可以**读旧写新**，但不能「两边都写」——那正是 §7.1 反对的状态/事件双轨。
2. **一次性回填**：启动时把 `__app_override::` / `__app_item_binding::` 读出来灌进新表，
   用 `__migration_item_centric::v1` 标记只跑一次。回填是**幂等 upsert**，
   且 `priority` 统一给 100（单值旧数据没有「首位」概念，全部同权时按 `category_key` 字典序，
   与 `resolve_child_category` 的规则 2 一致）。
3. **回填失败的可见性**：回填不阻断启动（与 `identity` 的 WARN 同策略），但必须在设置页
   留一处「分类配置尚未迁移」的提示——静默失败会让规则 1 永远不命中，而规则 2 会给出
   一个**看起来正确**的答案（§4.1），没人会发现。

### 判据

> 把 `__app_override::*` 与 `__app_item_binding::*` 全部删掉之后，子记录切片结果**必须不变**。

这条成立才算迁移完成。在那之前，旧 KV 仍是真源，新表只是空壳。
