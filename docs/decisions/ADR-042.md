# ADR-042：两边都改过时，以 Markdown 为准

## Status

Accepted（2026-11-05，V0.11.3）

## Background

Markdown 同步从 V0.4.0 起就是三方合并：拿上一次写出内容当基线，判断「谁变了」。
三种情况里两种是无歧义的——只有文件变了就导入，只有数据库变了就导出。

歧义只在第三种：**两边都变了**。原实现的判据是

```rust
let should_import = mtime > expected.latest_update;
```

即「最后写入者胜」。当时觉得公平：谁后写就听谁的。

## Problem

`mtime` 与 `latest_update` 根本不是同一个东西，拿它们比大小没有意义：

| 来源 | 含义 | 何时被推进 |
|---|---|---|
| `latest_update` | 应用写库那一刻的墙钟毫秒 | 用户真的在 Timing 里改了记录 |
| `mtime` | 文件系统记录的「最后一次写入」 | Obsidian 关闭时补写一次元数据、同步盘回写、编辑器「无改动保存」、备份工具 touch |

于是出现一类**偶发但不可接受**的故障：用户上午在 Obsidian 里手改了一行时长，
下午在 Timing 里点了别的事项（触发一次导出），文件 mtime 恰好比数据库新一点点 ——
那一行手改就被数据库的值覆盖回去了。用户看到的是「我明明改过，怎么又变回去了」。

对一份被明确定义为「第一优先级资料」的日记来说，这种反向覆盖比「晚几分钟同步」严重得多。

## Decision

**只要文件相对基线发生了变化，就以文件为准。** 数据库只在「文件没动」时才向外写。

```rust
// sync_binding：current 与 expected 已经不相等，剩下的判断只有一句
if file_changed { 导入 } else { 导出 }
```

`Exported::latest_update` 因此失去读者，一并删除（每个落点每轮省一次 `MAX(updated_at)`）。

## Consequences

- 用户手改日记永远不会被应用悄悄覆盖。想改回数据库的值，改文件或让应用重新导出即可。
- 代价：如果用户在应用里改了记录、同时文件也被外部工具 touch 过（内容没变），
  这一轮会先导入一次「内容其实没变」的文件，然后由导入后的重新渲染把数据库的值写回文件
  —— 净效果仍是数据库的值赢，只是多绕一圈。这是可接受的：`file_changed` 比的是**内容**，
  不是 mtime，单纯 touch 不会让 `file_changed` 变真。
- 真正的冲突（两边都真的改了内容）永远是文件赢。这条要写进产品说明，
  否则用户会以为是 bug。
