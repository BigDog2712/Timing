# ADR-033：插件 API v2 — 声明式 `mdSync` 与新增 `MD_SYNC_CONFIG_INVALID`

## Status

Accepted（2026-10-20，V0.4.0）

## Background

用户要求「为该软件制作第一个插件，同时完善插件系统」，插件名 `md-sync`，四条硬需求：

1. 用 SQL 里的数据生成 Markdown；
2. 落点可配置，例如计时写到 Obsidian 日记的 `#### 事项计时` 标题下，格式与往日笔记一致；
3. 双向同步：改 Markdown → 回写 SQL 并刷新界面；改 SQL → Markdown 跟着变；
4. 设置页能快捷配置落点，并能配置计时 / 便利贴等内容。

v1 插件系统只有 `quickTimers` 一个贡献点，且 V0.3.9 起它已不驱动菜单。如果直接把
「读写文件」做成插件可调用的命令，会破坏两条既有边界：

- **声明式插件**：宿主只读 `plugin.json`，从不执行插件代码；
- **数据访问单通道**：`commands → services → repositories`，前端 / 插件不直连 SQL（ADR-015）。

同时，前端已经能通过 `note_update` / `update_record` 改数据，但没有「文件」这一侧；
若在组件里直接调文件 API，又会把平台能力散到 UI 层。

## Decision

### 1. 升 `apiVersion` 到 2，新增 `contributes.mdSync`

```json
{
  "apiVersion": 2,
  "contributes": {
    "mdSync": {
      "bindings": [
        {
          "kind": "timers",
          "enabled": true,
          "root": "%USERPROFILE%\\...\\Diary",
          "file": "{date}.md",
          "heading": "#### 事项计时"
        }
      ]
    }
  }
}
```

- 插件只**声明落点**（kind / enabled / root / file / heading），不提供回调、不执行代码。
- 文件读写、格式解析、冲突判定全部在宿主 Rust 侧；插件拿不到数据库或任意文件句柄。
- 只声明 `quickTimers` 的 v1 插件继续有效；声明 `mdSync` 但 `apiVersion: 1` 会被拒载。
- 一个 `kind` 只允许一个落点（设置页按 kind 找状态）；`bindings` 上限 8。

### 2. 分层落点

| 层 | 文件 | 职责 |
|---|---|---|
| `models` | `models/md_sync.rs` | DTO、校验、状态 / 报告 |
| `infra` | `infra/md_file.rs` | 路径展开、标题区块读写、原子替换、CRLF 保持 |
| `repositories` | `repositories/md_sync.rs` | 同步专用的记录 / 便利贴 SQL |
| `services` | `services/md_sync/*` | 配置、导出、导入、轮询运行时、冲突判定 |
| `jobs` | `jobs/md_sync.rs` | 2 秒 tick |
| `commands` | `commands/md_sync_cmd.rs` | `md_sync_get` / `save` / `run` / `open` |
| 前端 | `stores/mdSyncStore.ts` + `settings/MdSyncTab` | 落点配置与状态展示 |

新增 `tauri-plugin-dialog` 仅用于原生目录选择，capability 只放 `dialog:allow-open`；
**没有**引入通用 `fs` 读写权限，文件仍只由 Rust 服务按声明路径访问。

### 3. 双向同步算法

每轮对每个启用的落点：

1. 计算 `expected`（当前 SQL 应渲染出的区块）；
2. 读文件得到 `current`（标题下正文）与 `mtime`；
3. 与内存 baseline 比较：
   - 只有文件变 → 解析并导入 SQL；
   - 只有 SQL 变 → 写文件；
   - 两边都变 → 比较文件 mtime 与相关记录最大 `updated_at`，最后写入者胜；
4. 导入后重新渲染 expected 并写回，保证文件里的「用户手写但语义等价」格式被规范化。

安全阀：文件 / 标题不存在时**只导出不导入**；空区块不被当成「用户删光了数据」。
计时按「事项名 + 第 N 段」对位；便利贴按行尾 `<!-- tb-note:ID -->` 对位。

轮询而非 `notify`：Obsidian / OneDrive 的写入模式（临时文件、同步延迟、原子替换）
在 Windows 上事件噪声大，2 秒轮询实现简单且可预测；代价是最大 2 秒延迟。

### 4. 新增错误码 `MD_SYNC_CONFIG_INVALID`

`MdSyncConfig::validate` 的失败原因（绝对路径、`..`、标题缺 `#`、重复 kind、超长等）
需要与 `DB_ERROR` / `IO_ERROR` 区分：它是**用户配置错误**，应在设置页原样展示并允许改，
而不是提示「数据库错误」。因此新增第 16 个错误码，前端 `ErrorCode` 与 `errorText()` 同步。

### 5. 前端刷新

新增事件 `md-sync:changed`，payload 为 `MdSyncReport`（`imported` / `kinds`）。
只在**真的导入了数据**时 emit；`useAppBootstrap`、`useTodayRecords`、`useRecordsData`、
`TodosWindow`、`NoteWindow` 按 `kinds` 刷新对应数据，空轮询不打扰界面。

## Consequences

- 插件系统从「只能改摸鱼预设」变成「能声明一类宿主服务」，但边界仍是声明式。
- 写文件路径由用户配置，插件作者可预设默认值（`md-sync` 用 `%USERPROFILE%\OneDrive\...`），
  用户可在设置页改；不会因为换机器就写到错误位置。
- 冲突策略是最后写入者胜，**不是合并**。同一段落两边同时改会丢一侧，这是刻意取舍：
  日记场景里「合并两段计时」比「丢一侧」更难解释。
- 新增 4 命令 / 1 事件 / 1 错误码：65 命令、11 事件、16 错误码。

## Alternatives considered

| 方案 | 否决原因 |
|---|---|
| 插件自带 JS 读写文件 | 需要沙箱、权限与生命周期，v2 不做半成品 |
| 前端直接调 `fs` 插件 | 绕过服务层与声明式边界，且前端会拿到任意路径读写能力 |
| `notify` 文件监听 | Windows 上事件重复 / 临时文件 / 云同步延迟导致误判，轮询更可预测 |
| 双向合并（diff3） | 日记是自由文本，没有可靠的结构化合并语义；先做可解释的 LWW |
| 复用 `IO_ERROR` 表达配置错误 | 设置页无法区分「路径写错」与「磁盘故障」，文案会误导 |
