# ADR-020：删除主窗 384×360 固定画布，浮层改为「显示器工作区」坐标系

## Status

Accepted（2026-10-18；关闭主窗「画布」这一层隐形地板）

## Background

主窗从第一天起就是一张**写死 384×360 的透明画布**：`html/body/#root` 按
`--window-w` / `--window-h` 排版，`.layer` 是 `position: fixed` 的 384×360 置层，
所有浮层（菜单、提醒浮层、待办面板、今日摘要、设置面板）都在画布里绝对定位。

画布承担三件事：

| 职责 | 具体表现 |
| --- | --- |
| 给浮层留地盘 | Windows 只在窗口矩形内绘制；浮层要「长」出去，就得先有一块窗口 |
| 坐标基准 | 贴边钳制读 `canvasViewport()` 的 384×360，而不是 `window.innerWidth` |
| 原点可移 | `useWindowAutoFit` 量完包围盒后 `setSize` / `setPosition`，再用 `.layer` 的 `translate` 把内容拽回原位 |

真正被用户看到的问题有三个：

1. **画布是虚构的坐标系，不是真实边界**。窗口的真实尺寸是「内容包围盒」（ADR-014），
   坐标却是 384×360；两者不一致，于是要 `.layer { position: fixed }` + `translate(-l,-t)`
   把内容拽回视觉原位，还要 `canvasViewport()` 在所有贴边钳制里代替 `window.innerWidth`。
   这套补偿全是为了让「假坐标」和「真窗口」对得上——去掉画布，两者合一，补偿自然消失。
2. **写死尺寸跟屏幕无关**。4K 屏上 384×360 只是屏幕一角，菜单比它长就被 `max-height`
   压扁并内部滚动；而在 1366×768 的笔记本上，384 宽的菜单又几乎顶满屏。
   所有面板的 `max-height` 都以「画布高」为口径，而不是「屏幕高」。
3. **首帧仍是一整块 384×360 透明窗**。启动时窗口按配置先开成 384×360（`tauri.conf.json`），
   要等 `useWindowAutoFit` 跑完才缩到胶囊大小；这段时间里透明区照样吞桌面点击
   —— 正是 ADR-014 要解决的问题，只是被延后了一帧。

用户的原话是「画布存在的意义是什么 感觉很影响美观 去掉行不行」。

结论：画布是一层**为了给浮层让位而虚构出来的空间**，它不等于任何真实边界，
却同时污染了坐标语义和窗口尺寸语义。

## Decision

**删掉固定画布，坐标系换成「主条所在显示器的工作区」。**

1. **根元素 = 视口**：`html/body/#root` 用 `width/height: 100%`，不再有 384×360；
   `.layer` 仍是 `position: fixed` + 视口铺满 + `pointer-events: none`。
2. **浮层可以长到视口外**：`.layer` 不给宽高，浮层用绝对定位落到负值/超出视口的坐标上。
   `fixed` 置层不会被裁剪，`getBoundingClientRect()` 照样量得到真实矩形——
   这是「先量、再撑窗口」能成立的前提。
3. **上界来自真实屏幕**：新增命令 `main_work_area`（第 63 个），返回主条**当前所在显示器**
   的工作区（DIP，已扣任务栏）。选取规则：主条窗口矩形与各显示器工作区求重叠面积，取最大；
   完全不在任何屏内时回落主显示器（与启动钳制 `reclamp_main` 同一套几何函数 `overlap_area`）。
4. **CSS 令牌换轨**：`--window-w/--window-h` → `--fit-w/--fit-h`。默认值 `100vw/100vh`
   （非主窗天然正确），主窗由 `src/lib/fitBounds.ts` 在启动与 `onMoved` 时覆盖成工作区像素。
   所有 `max-height` 从「画布高」改为「工作区高」：长菜单在屏幕内滚动，不再被窗口切掉。
5. **贴边钳制改读 `fitBounds()`**：菜单 / 倒计时自定义 / 提醒浮层三处统一走 `lib/fitBounds.ts`，
   取代已删除的 `lib/canvas.ts::canvasViewport()`。
6. **窗口仍是同一个**：不引入 overlay 独立窗口。`useWindowAutoFit` 的
   「量包围盒 → setSize → setPosition → translate 抵消」流程原样保留，只是包围盒的上界
   从常量 384×360 变成工作区。
7. **`.layer` 必须有实体尺寸**（`width: var(--fit-w); height: var(--fit-h)`）。
   实测坑：若 `.layer` 只写 `100%` / auto，它就跟窗口同宽，浮层被挤窄 → 包围盒更小 →
   窗口再缩 → 浮层更窄，形成自我坍缩的反馈环（胶囊被压到 129px、「新建事」折成两行）。
   尺寸挂在**工作区**而不是窗口上，才能打断这个环。
8. **贴边钳制用层坐标**：`fitBounds()` 返回的是「工作区换算到层坐标」后的矩形
   （`x/y` 通常为负，等于工作区左上角减窗口左上角），三个浮层的右/下边界写成 `x + w` / `y + h`。
   竖直方向的地板是 `0`（不是 `EDGE`）——auto-fit 只往右下扩张，层坐标 < 0 的内容会被窗口上沿裁掉；
   下沿放不下时不再硬顶出屏，而是把 `maxHeight` 收到「下沿 − y」，菜单内部滚动。

## Alternatives considered

- **每个浮层一个独立 OS 窗口**（像 `note-{id}` 那样）。彻底的模型统一，但代价是把
  「浮层跟随主条几何 / 置顶 / 随主条隐藏」这套逻辑复制到 5～6 个窗口，并与 ADR-014 的
  多窗几何模型重新对齐；本次诉求只是「去掉一块看不见的地板」，不值得为此重做窗口模型。
- **保留画布、只改样式（透明 / 与胶囊同高）**：视觉零收益——画布本来就不可见，
  用户抱怨的是它撑出的窗口区域与死尺寸，不是颜色。
- **隐藏的测量层**（先渲染到 `visibility: hidden` 的容器量完再显示）：本质还是留一块
  虚构空间，只是把它藏起来，坐标语义照旧混乱。
- **前端直接读 `screen.availWidth/availHeight`**：WebView2 里这是 CSS 像素且不扣任务栏、
  不区分显示器，与后端 `Monitor::work_area()` 的口径不一致，会出现「贴着任务栏」的位置差。

## Consequences

- **`--window-w/--window-h` 不再存在**：任何新增浮层必须用 `--fit-h`（限高）或
  `fitBounds()`（钳制），否则在窄窗口里会被裁掉。
- **指针锚点必须换算**：`.layer` 被 `translate(-l,-t)` 平移，指针事件的 `clientX/clientY` 是视口坐标，
  直接当 `anchor` 会让菜单稳定偏左上 `(l,t)`。所有「在光标处弹出」的入口改走
  `fitBounds.clientToLayer()`（非主窗没有平移，换算即恒等）。
- **瞬时裁切**：浮层出现的同一帧里视口可能还只有胶囊大小，最多约 250ms（auto-fit 轮询）
  后窗口才撑开。`MutationObserver` 已覆盖 `class/style/hidden`，纯插入节点依赖轮询兜底。
- **跨屏跟随**：窗口 `onMoved` 后重取工作区；拖动主条到另一块屏，钳制上界随之改变。
- **IPC 契约 +1**：63 命令。`check:contract` 四处一致仍是硬门禁，文档 §3.7 / §4.7 与本
  ADR 同步更新。错误码不变（复用 `IO_ERROR`，不新增码）。
- **测试口径**：`src/hooks/autoFit.test.ts` 的边界用例从「画布 384×360」改为「工作区 1440×900」，
  断言结构不变（21 条）；后端 195 条不受影响。
- **已知限制：混合 DPI 为近似**。工作区由「物理像素 ÷ 该显示器 `scale_factor`」换算，层坐标里
  `bounds.x/y` 相对窗口原点取值；当两块屏缩放比不同（如 150% + 100%）时，Windows 的虚拟桌面
  仍以物理像素表达，该换算与 `LogicalPosition` 在**跨屏**场景下的取整口径只差亚像素级。
  本机两块屏均为 150%，实测 `main_work_area` 返回 `x=2560, y=209.33, w=1706.67, h=1066.67`，
  层内右/下边界 866.67 / 775 与物理位置一致。若将来出现混合 DPI 的错位，优先改后端
  直接返回「相对主窗的工作区」而不是在前端补偏移。
