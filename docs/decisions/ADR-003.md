# ADR-003: 使用 SQLite（tauri-plugin-sql）作为本地数据存储

## Status

Accepted (2026-10-16)

## Background

Timing 免登录、纯本地，需存储三类数据：事项（items）、时间记录（time_records，持续增长且需按时间范围/事项聚合查询）、设置（settings）。要求：可靠性（防损坏）、支持结构化查询与索引、支持迁移、低运行时开销。候选：SQLite（`tauri-plugin-sql` + sqlx）、`tauri-plugin-store`（JSON KV）、自管理 JSON 文件。

## Decision

**业务数据用 SQLite（`tauri-plugin-sql` 2.5.0 + sqlite feature），轻量设置用 `tauri-plugin-store`**（双轨）。

理由：
1. 时间记录是持续增长的关系型数据，需按 `item_id` / `started_at` 过滤与聚合。SQLite + 索引高效且可验证；JSON KV 不适合这类查询。
2. `tauri-plugin-sql` 基于 sqlx，官方支持 `Migration`/`MigrationKind::Up`，schema 演进有正规路径。
3. 事务与 WAL 保证写入可靠性；自管理 JSON 文件需自行处理并发、损坏、迁移，成本更高。
4. 设置在 Rust/JS 两侧均可读，用 `tauri-plugin-store` 更顺手（KV 语义），且与业务库解耦。

存储位置：`%APPDATA%\com.timing.app\timing.db`；PRAGMA `journal_mode=WAL`、`foreign_keys=ON`。

## Consequences

正面：
- 结构化查询/索引/事务/迁移齐备，可支撑统计与明细分页。
- 单文件便于备份与迁移；官方插件省去连接管理。

负面：
- 迁移必须幂等（`IF NOT EXISTS`），否则重复执行报错（K-7）。
- 需在 `capabilities` 放行 `sql:allow-*`，否则运行时被拒（K-4）。
- 引入双轨存储，需明确「配置进 store、业务进 sqlite」的边界，避免同一数据两处写。
