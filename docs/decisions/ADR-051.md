# ADR-051：双形态打包——NSIS 用户级安装包 + 绿色便携版（`build-release.cmd` 升为统一入口）

## Status

Accepted（2026-11-06，V0.11.6；用户口径「现在对桌面端进行打包，做一个绿色便携版，还有打包版」，
即**两种形态都要**；配套落点口径见 ADR-050）

## Background

现状只有一条「半成品」产线和一个失控的产物目录：

| 现状 | 证据 |
|---|---|
| 打包配置声明了两种安装器，但没人用 | `src-tauri/tauri.conf.json`：`bundle.targets = ["nsis","msi"]`、`windows.webviewInstallMode.type = "embedBootstrapper"` |
| 脚本只出一个裸 exe | `scripts/build-release.cmd`：`npm run build` → `cargo clean --release -p timing` → `cargo build --release --features custom-protocol` → 拷 `release\Timing.exe` |
| 产物目录没有规范 | `release\` 里只有 4 个互不相关的历史文件（`RELEASE-NOTES.md` / `SHA256SUMS.txt` / `TickBar-v0.4.1-android-arm64.apk.idsig`），没有任何「这一次发布了什么」的表达 |
| 版本号六处必须一致 | `npm run check:version`（`package.json`、`package-lock.json` 两处、`Cargo.toml`、`Cargo.lock`、`tauri.conf.json`） |

ADR-050 把数据落点改成「应用同级优先」之后，安装位置从「无关紧要」变成**体验的决定因素**：
装在只读目录 → 每次首启都会命中提权对话框。所以打包策略必须与落点策略一起定，不能分开。

## Decision

### 1. 两种形态各出什么、放哪儿

```
release/
├─ Timing-0.11.6-portable\          绿色便携版（目录形态）
│  ├─ Timing.exe
│  ├─ data\README.txt              （空数据目录 + 说明；同时起「占位」作用）
│  └─ plugins\README.txt           （空插件目录 + 说明）
├─ Timing-0.11.6-portable.zip       同上，压缩分发
└─ Timing-0.11.6-setup.exe          NSIS 安装包（currentUser）
```

`release/` 下本轮**开始有目录规范**：一个版本 = 一个便携目录 + 一个 zip + 一个 setup.exe（产物名
**不带** `windows-x64` 后缀、也不产出 `SHA256SUMS-<ver>.txt`——构建脚本以「文件数 / 解压后体积」报告
产物，校验和留给发布流程按需生成）。历史散放文件原样保留（`RELEASE-NOTES.md` 是 v0.4.1 时代的，
已过期，不再作为产物说明；删除与否是另一个决定，本文不动）。

**绿色版是否包含 WebView2 运行时：不包含。** 结论与对策：

| 项 | 结论 |
|---|---|
| Win11 / 打过 Edge 的 Win10 | 系统已有 Evergreen 运行时，绿色版开箱即用 |
| 缺 WebView2 的机器 | 现在会**白窗或直接退出**（`CreateCoreWebView2EnvironmentWithOptions` 失败，日志一行，用户看到的是「双击没反应」） |
| 对策 | 启动前探针 + 原生提示，**不打包运行时** |
| 探针判据 | `%ProgramFiles(x86)%\Microsoft\EdgeWebView\Application\*\msedgewebview2.exe` 或 `%ProgramFiles%\...` 任一存在即视为已安装（纯 fs 探测，零新依赖；比读注册表更稳——不受 WOW6432Node 视图影响） |
| 探针位置 | `app::portable_prompt::webview2_ok()`，由 `portable_boot::prepare()` **在所有桌面启动的最前面**调用。**不是**「只在便携分支跑」：运行时缺失时连安装版也起不来，而「是否便携」恰恰要等这一步之后才决定（顺序上做不到），且安装版恒为 true、无副作用 |
| 缺时行为 | rfd `MessageLevel::Error`：「缺少 Microsoft Edge WebView2 运行时，Timing 无法显示界面。」+ 下载地址 `https://go.microsoft.com/fwlink/p/?LinkId=2124703` + 按钮「打开下载页 / 退出」（打开网页用新增的 `infra::shell_open::open_url`），随后 `exit(EXIT_NO_WEBVIEW2 = 4)` |
| 为什么不打 fixed-version 运行时 | +130MB，且与系统 Edge 版本脱钩、升级只能换包；便携版体积（zip 约 3MB）本身就是卖点 |
| 安装版 | 保持 `embedBootstrapper`：安装时缺运行时由内置 bootstrapper 自动补齐，不需要用户动手 |

### 2. `bundle.targets` 只留 `nsis`，并显式 `installMode: "currentUser"`

| 项 | 结论 |
|---|---|
| `bundle.targets` | `["nsis"]`（删 `msi`） |
| NSIS `installMode` | `"currentUser"` → 装到 `%LOCALAPPDATA%\Timing`（**用户可写**） |
| 关系 | 装在那儿的数据根 = `%LOCALAPPDATA%\Timing\data`，首启**不触发**提权对话框，行为与绿色版一致 |

删 MSI 的判据（单边结论，不留「两边都说」）：

1. Tauri 的 WiX 模板只有 perMachine 一种形态，装到 `C:\Program Files` → 目录只读 → ADR-050 的提权
   对话框成为**每一个** MSI 用户的首次启动体验。等于把本轮需求做成了「先看一个错误提示」。
2. MSI 首次构建要联网拉 WiX 工具链，让打包从「一条命令」变成「依赖网络」；NSIS 同理但只拉一次且产物更小。
3. 企业集中部署（MSI 唯一硬需求）至今零需求。真出现时应做的是另一套设计（perMachine + 数据落
   `%PROGRAMDATA%`），而不是现在硬扛两个互相矛盾的落点。

同时**不提供 NSIS 自定义安装目录**：Tauri 的 NSIS 模板默认不出现目录选择页，这是好事——让用户自己
挑一个只读目录（`Program Files`）正是我们要避免的。想放到别处的用户应该用绿色版。

### 3. 绿色版怎么产：`.cmd` 只负责 MSVC 环境，真正的流程在 `build-desktop.mjs`

| 文件 | 角色 | 为什么是这个而不是另一个 |
|---|---|---|
| `scripts/build-release.cmd` **保留**，只做「载入 `vcvars64.bat` + 转发参数」 | 参数 `portable\|installer\|all`（默认 `all`）→ `--portable` / `--installer` | 必须 `call vcvars64.bat` 才能让 `cargo` / `tauri build` 找到 `link.exe` 与 Windows SDK；Node 里继承 MSVC 环境不可靠。**这个文件保持 ASCII + CRLF**（cmd.exe 用 OEM 代码页读批处理） |
| `scripts/build-desktop.mjs`（新增，Node，无新依赖） | 全部实际步骤：前端构建 → 指纹判定要不要重编 Rust → 一次 `tauri build` → 组装便携目录 → 打包 zip → 收集安装包 → 打印产物报告 | 纯文件操作要读 `package.json` 版本、做内容指纹、按模板写文本；`.cmd` 做这些等于和引号/括号搏斗 |
| zip | **`C:\Windows\System32\tar.exe`（libarchive bsdtar）**，命令 `tar -a -cf <zip> -C <stage> .` | 见下方「为什么必须钉绝对路径」 |

**为什么必须钉 zip 工具的绝对路径**（踩过，别再踩）：PATH 上第一个 `tar` 通常是 Git 自带的
**GNU tar 1.35**，它有两个致命差异——① `-a` 只用来**选压缩算法**，不会按扩展名写 zip（GNU tar 根本
不能写 zip）；② 它会把 `D:\...` 当成**远程主机**，实测报 `tar: Cannot connect to D: resolve failed`。
所以脚本里先探 `C:\Windows\System32\tar.exe`，存在就用绝对路径，否则（非 Windows）才退回裸 `tar`。
同理，传给 bsdtar 的路径一律先转成**仓库相对路径**（`relPath()`），避开两个工具对盘符冒号的各自解读。

`build-desktop.mjs` 的步骤（顺序固定）：

1. `npm run build`（前端）；对 `dist/` 做**内容指纹**（相对路径 + 内容 sha256 前 16 位）与上次落盘的
   `src-tauri/target/.timing-dist-stamp` 比对，**不一致才** `touch src-tauri/build.rs` 逼 cargo 重编。
   用内容指纹而不是 mtime：vite 每次构建都重写文件，按 mtime 判等于每次都判变，退化成全量重编；
2. 写一份覆盖配置 `src-tauri/target/.timing-no-hook.json`（`{"build":{"beforeBuildCommand":""}}`），
   用 `--config` 传给 `tauri build`，避免同一份 dist 被 `beforeBuildCommand` 再编一遍；
3. **一次** `tauri build`：要安装包就 `--bundles nsis`（同时产出 `target/release/timing.exe`），
   只出便携版才 `--no-bundle`；
4. 组装 `release/Timing-<ver>-portable/`：拷 `timing.exe` → `Timing.exe`；建 `data\` 与 `plugins\`，
   各写一份 `README.txt`（空目录不进 zip，靠说明文件把目录钉住，顺带解释用途）；扫一遍产物，出现
   `.db` / `-wal` / `-shm` / `.md` 就告警（防「把本机用户数据打进发布包」）；
5. zip：`tar -a -cf release/Timing-<ver>-portable.zip -C <stage> .`，产物为空即失败退出；
6. 收集安装包：`target/release/bundle/nsis/` 下必须**恰好 1 个** `*-setup.exe`，拷成
   `release/Timing-<ver>-setup.exe`；最后打印「kind / 路径 / 体积 / 文件数」报告。

**为什么不能「先 `--no-bundle` 再 `--bundles nsis`」两次构建**：`--no-bundle` 会改变**内嵌的 config
指纹**（两次调用传给 `tauri-build` 的配置不同 → 生成的代码变化 → `generate_context!` 产物变化），
于是两次构建的编译产物**不可复用**，等于把整个 crate 重编两遍——实测**白花 2m06s**。所以：
「两者都要」时只跑一次 `--bundles nsis` 并让便携版复用它的 exe；只有明确只要便携版时才用
`--no-bundle`。

**为什么不再用 `cargo clean --release -p timing`**（旧脚本的招）：`dist/` 是 `include_dir` 嵌进二进制
的，cargo 不把它当输入，不处理就会让 exe 里留着上一版 UI。旧脚本用 `cargo clean` 绕过，代价是整 crate
重编；现在改成「指纹变了才 `touch build.rs`」，效果等同但重编量小得多。

**zip 里是否预置空 `data\` 与 `plugins\`：是。** 理由：用户解压后第一眼就能看到「数据放这儿」，而不是让
应用在旁边凭空建目录；同时让「整个文件夹拷到 U 盘」从第一步就成立。

### 4. 一次构建、两种形态：步骤与判据

| # | 步骤 | 命令 | 判据 |
|---|---|---|---|
| 0 | 载入 MSVC 环境 | `build-release.cmd` 里现有 vcvars 探测逻辑（`vswhere` → 两个固定候选） | 找不到 → `exit /b 1`；参数不认识 → `exit /b 2` |
| 1 | 前端 + 指纹 | `npm run build` → `stampDist()` | `dist/` 有产物；指纹变化时才 `touch src-tauri/build.rs` |
| 2 | 编译 | `node node_modules/@tauri-apps/cli/tauri.js build [--bundles nsis \| --no-bundle] --config <override>` | `src-tauri/target/release/timing.exe` 存在（不存在即退出） |
| 3 | 便携版（`all` / `portable`） | 组装 + `tar -a -cf` | `<stage>\Timing.exe` + `data\` + `plugins\` 都在；zip 非空 |
| 4 | 安装包（`all` / `installer`） | 拷 `bundle/nsis/*-setup.exe` | 该目录下**恰好 1 个** `*-setup.exe`，否则退出 |
| 5 | 报告 | stdout | 打印 kind / 路径 / 体积 / 解压后文件数 |

分支：`all`（默认）= 0-5，编译用 `--bundles nsis`（**一次**编译，便携版复用同一个 exe）；
`portable` = 0-3 + 5，编译用 `--no-bundle`（不出安装包时不拉 NSIS 工具链）；
`installer` = 0-2 + 4-5。`tauri build` 走 `node tauri.js` 直接执行，绕开 Windows 上 `.cmd` 与
shell 引号的问题。

### 5. `.gitignore` 与产物入库口径

`release/` 原本只忽略 `*.exe` / `*.msi` / `*.nsis.zip` / `*.apk`，本轮补两条（已落地）：

```
release/Timing-*/
release/*.zip
```

`.idsig` / `RELEASE-NOTES.md` / `SHA256SUMS.txt`（历史）已在库里，本轮不动它们。

| # | 命令 | 判据 |
|---|---|---|
| 1 | `npm run check` | 退出码 0（typecheck + contract + size + version + layers + brand + lint） |
| 2 | `npm run test` | 全绿 |
| 3 | `cd src-tauri && cargo test` | 全绿（含本轮新增的 portable 用例） |
| 4 | `cd src-tauri && cargo clippy --release -- -D warnings` | 0 warning |
| 5 | `npm run check:version` | 六处都是 0.11.6 |

| 7 | 便携目录删掉 `data\` 后启动 | 自动从 `%APPDATA%\com.timing.app` 复制；旧目录仍在；`data\migrated-to-portable.json` 出现 |
| 8 | 改名 `Microsoft\EdgeWebView` 目录后启动 | 出现「缺少 WebView2」对话框，而不是白窗 |

## Alternatives

| 方案 | 否决原因 |
|---|---|
| 保留 `nsis + msi` 双安装器 | MSI 只能 perMachine → 落点只读 → ADR-050 的提权框变成默认体验（见 §2 判据 1） |
| NSIS 用 `perMachine` | 同上，且安装需要 UAC 提权，与「绿色/便携」的产品调性相反 |
| 绿色版内置 fixed-version WebView2 | +130MB，升级只能换包；Green 版体积是卖点 |
| 新建 `scripts/build-all.mjs` 取代 .cmd | MSVC 环境的继承在 Node 里不可靠（`vcvars64.bat` 是 `cmd` 语义），现有 .cmd 已经解决过这个问题 |
| 不打 zip，只给目录 | 分发一个文件夹需要用户自己压缩；且 zip 是唯一能把「空 data/plugins」变成可分发形态的外壳 |
| zip 里不放空 `data\` / `plugins\` | 用户解压后看不到数据该放哪；且目录不会在解压时创建（应用首次启动才建），「删一个文件夹重置数据」的语义晚一步才成立 |
| 用 `tauri build` 顺便产便携包 | Tauri 没有 portable target；且它产出的裸 exe 没有 `data\` / `plugins\` 与说明文件 |
| 便携版换一个 identifier | identifier 决定 `.window-state.json` 与 WebView2 用户数据目录；换掉等于让便携版和安装版变成两个应用（自启、单实例、设置全分裂） |
| **两次构建**（先 `--no-bundle` 出裸 exe，再 `--bundles nsis` 出安装包） | `--no-bundle` 改变内嵌 config 指纹 → 两次产物不可复用 → 整个 crate 重编两遍，实测白花 2m06s（§3） |
| zip 用 `Compress-Archive` | 首版设计选它，实测被 `tar.exe` 取代：bsdtar 一条 `-a -cf` 就够、不用起 `powershell` 进程，且能保住 `data\` / `plugins\` 的子目录结构（`Compress-Archive -Path <stage>` 的目录语义要额外调参数） |
| zip 用裸 `tar`（PATH 上的那个） | PATH 第一个通常是 Git 的 GNU tar 1.35：`-a` 不能写 zip，还会把 `D:\...` 当远程主机报 `Cannot connect to D:`（§3） |
| 继续用 `cargo clean --release -p timing` 强制重嵌前端 | 等效但代价是整 crate 重编；改用 dist 内容指纹 + `touch build.rs`（§3） |

## Consequences

- **一条命令出两个形态**：`scripts\build-release.cmd`（默认 `all`）→ 一次 Rust 编译 → `release\` 下齐活。
  CI 只需调用它。
- **产物目录第一次有规范**：`release\Timing-<ver>-portable\` + `Timing-<ver>-portable.zip` +
  `Timing-<ver>-setup.exe`（本版本实测：zip 2.9MB / setup 4.1MB）。
- **构建时间对半砍**：「两者都要」只编译一次（旧设计要两次），且前端未变时不再重编 Rust crate。
- **默认安装位置变了**：NSIS 从「perMachine（`Program Files`）」变成「currentUser
  （`%LOCALAPPDATA%\Timing`）」。老用户升级会在新位置重装一次，旧位置（若曾手装）需自行卸载——本版本
  还没有老安装包用户（此前只发裸 exe），所以无迁移负担。
- **MSI 下架**：`bundle.targets` 减少一项，`tauri build` 不再拉 WiX；文档、脚本、发布说明里不再提 `.msi`。
- **首启提权对话框只出现在两种场景**：绿色版被放到只读位置、用户手动把安装目录搬进 `Program Files`。
  这两种都是用户自选，且对话框给出了三条出路。
- **WebView2 探针在所有桌面启动都跑**（不只是便携版）：安装版恒为 true，代价是每次启动两次
  `fs::metadata`；换来的是「便携版放到没运行时的机器上不会是白窗」。
- **`release\RELEASE-NOTES.md` / `SHA256SUMS.txt` 已过期**（v0.4.1 时代），本轮不作为产物说明；本版本的
  发布说明写在 `CHANGELOG.md` 的 `0.11.6` 段与 ADR-050 / ADR-051。
- **已知限制**：便携版整体移动目录后，Windows 自启项（记录的是旧 exe 绝对路径）失效，需要用户重新
  开关一次自启（`docs` 无入口，属 P2）。

### 已知限制：安装版的卸载残留与「删除应用数据」空转（本轮不修）

三件事都是 `tauri build` 生成的 NSIS 模板行为，不是我们的代码，**本轮不改模板**：

| # | 现象 | 证据（`src-tauri/target/release/nsis/x64/installer.nsi`） |
|---|---|---|
| 1 | 卸载后**整个安装目录残留**（`%LOCALAPPDATA%\Timing\` 还在，里面是 `data\` 那棵树） | `:786` 是 `RMDir "$INSTDIR"`，**没有 `/r`**。`$INSTDIR\data` 非空 → 这一步必然失败，`$INSTDIR` 保留 |
| 2 | 卸载页「删除应用数据」勾选**对真实数据空转** | `:836` `${If} $DeleteAppDataCheckboxState = 1` 里面是 `:848-849` 的 `RmDir /r "$APPDATA\${BUNDLEID}"` 与 `RmDir /r "$LOCALAPPDATA\${BUNDLEID}"`（`BUNDLEID = com.timing.app`）。而 V0.11.6 起真实数据在 `$INSTDIR\data`（= `%LOCALAPPDATA%\Timing\data`，`installMode: currentUser`）——勾了也删不到。它删掉的只是 `%APPDATA%\com.timing.app`（现有内容：`.window-state.json` + 迁移保留的那份旧数据）与 `%LOCALAPPDATA%\com.timing.app`（V0.5.0 起就没用过） |
| 3 | 卸载**不删** `data\` 这件事本身是对的 | 「卸载不删用户数据」是安全默认：用户卸了再装回来，数据还在。副作用只是「卸载后磁盘上留一堆东西」，比「误删三年计时记录」轻得多 |

**为什么本轮不修**：要改就得自定义 `bundle.windows.nsis.template`——整份 NSIS 模板（上千行）从此由我们
维护，Tauri 每次升级都要 diff 一遍；而收益只是「卸载更干净 + 勾选不那么误导」。相较之下，同样的工时
放在 ADR-050 的数据落点上收益高一个量级。**记录现状 + 在发布说明里告知**是这一轮该做的事。

**后续要修时的方向**（留给下一个人，别再重新推导）：

1. `bundle.windows.nsis.template = "windows/installer.nsi"`（复制 Tauri 2.12 的模板，只改卸载段）；
2. 卸载段把 `RMDir "$INSTDIR"` 改成先判 `data\`：勾了「删除应用数据」→ `RmDir /r "$INSTDIR\data"`；
   没勾 → 只 `RMDir /r` 其余子目录，保留 `data\`；
3. 「删除应用数据」的两条 `RmDir /r` 增加 `"$INSTDIR\data"` 目标（保留 `%APPDATA%\com.timing.app` 的
   `.window-state.json` 清理，那是真该删的）；
4. 改完必须实测三遍：全新安装→卸载（不勾）→ 数据仍在；卸载（勾）→ `data\` 消失；升级安装 → 数据不动。

另外：**升级安装（`$UpdateMode = 1`）不走删数据这段**（`:836-837` 是
`${If} $DeleteAppDataCheckboxState = 1` + `${AndIf} $UpdateMode <> 1`），所以残留只在「卸载」时发生，
升级不会丢数据。注意 `:786` 的 `RMDir "$INSTDIR"` **不在** `$UpdateMode` 判断里——升级时它也会跑一次，
但因为 `data\` 非空所以同样静默失败，恰好等于「什么都不做」。
