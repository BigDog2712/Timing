# ADR-039：手机端便利贴复用桌面 note 命令与 `notes` 表，不另建移动侧模型

## Status

Accepted（2026-11-05，V0.11.0）

## Background

V1.0-Android 交出的手机端有四页签（计时 / 事项 / 记录 / 设置）。走查结论里写得很清楚：
移动端可及 36 条命令，**真缺的 10 条是便利贴 5 + 提醒 3 + 简报 2**。也就是说便利贴在手机上
完全不可用，而它恰恰是「随手记下正在干什么」最需要手机的场景。

V0.11.0 的口径：「补齐手机端便利贴功能，数据落点与桌面端一致，通过 Obsidian 的 md 文档
双向同步（与计时功能一致）」。

有三条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| A | 复用桌面 5 条 note 命令 + 同一张 `notes` 表，新写一层轻量 action | 无新契约、无新表 |
| B | 复用 `stores/noteStore` | 那个 store 的语义是「**当前窗口**那一张」：`note-{id}` 单例、几何去抖、关窗前 flush。手机没有多窗也没有几何，硬套会带进一堆死字段，且为了手机改桌面语义 |
| C | 为移动端新建表和命令 | 两套数据必然漂移；md 同步要写两份 |

## Decision

**选 A。**

1. **数据面零新增**：`note_create / note_get / note_list / note_update / note_delete` 本来就
   在移动端注册（`lib.rs` 的 `generate_handler!` 里没有 `#[cfg(desktop)]`），不需要动 Rust。
   命令 67 / 事件 11 / 错误码 16 / schema v4 **全部不变**。
2. **新增 `services/mobileNoteActions.ts`**：`listNotes / getNote / createNote / saveNoteContent /
   bindNote / removeNote`。不碰 `noteStore`，也不给 `noteStore` 加移动分支。
3. **几何字段照传桌面默认值（320×232，落点 0,0）**：手机不消费，桌面首次打开时会按显示器
   工作区重新钳制。不传会违反 `note_create` 的参数契约。
4. **归属默认取当前事项**（会话事项 → 最近事项 → null），与桌面 V0.3.9 的
   「便利贴应默认绑定事项」同一口径；编辑页可改归属或解绑成随记。
5. **空正文即删除**：与桌面 `noteActions.closeNote` 一致。留一张看不见的空白贴比删掉更糟。
6. **md 同步不写移动代码**：`plugins/md-sync` 的 `notes` 绑定由**桌面宿主**每 2 秒轮询执行。
   手机端 `md_sync_*` 四条命令仍是桩（返回 `IO_ERROR`，见 `commands/md_sync_cmd_mobile.rs`），
   原因是没有 SAF 目录授权模型——**这一点与计时完全同构**：手机上写的东西进本地 SQLite，
   由桌面那一侧负责落到 md。所以「与计时功能一致」不是敷衍，是唯一成立的解释。

## Consequences

**好处**

- 一份数据、一套命令、一处同步逻辑。手机上写的内容回到电脑打开就是同一张便利贴。
- 契约零变化：不需要碰 `check:contract` 的任何一处镜像。

**代价 / 已知边界**

- **手机端仍然不能直接把 md 同步到 Obsidian**（SAF 授权未做）。用户如果只用手机、不装桌面端，
  便利贴只存在手机本地库。这是既有约束，不是本轮引入。
- 手机上没有「一张便利贴一个窗」的桌面感：列表 + 全屏编辑页。桌面可以同时摊开多张，
  手机上不能——这是形态差异，不做对齐。
- 手机上创建的便利贴 `posX/posY = 0,0`：桌面首次打开会被钳制到工作区，可能与用户预期位置
  不同（落点是「屏幕左上角」而非「上次编辑处」）。
- **未做**：安卓真机跑通关（本机无 Android SDK / NDK / JDK）。验收来自 typecheck / lint /
  vitest 42 文件 322 条 + 两端 vite build 通过。

## Verification

- `npm run check` 全绿；`npx vitest run` 42 文件 322 条通过。
- `TAURI_ENV_FAMILY=mobile npx vite build` 通过（107.38 kB CSS / 103.63 kB 业务 chunk）。
