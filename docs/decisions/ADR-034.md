# ADR-034：待办区显示全部未完成，时间列区分逾期 / 未来日期

## Status

Accepted（2026-10-20，V0.4.x / Unreleased）

取代：ADR-032 §1「只显示今天」的**显示范围**。ADR-032 §2 的逾期视觉（降透明度 + 一道横线）
与 V0.3.15「过期待办跨天自动删除」继续有效。

## Background

用户口径（原话）：

> 在事项组件右键唤起的事项菜单，待办事项区应保存为规定时间及规定在以后完成的待办事项

追问后确认三条：

1. 位置 = 事项窗口（右键事项组件唤出的那个窗）里的「待办事项 · N」区（`TodosTodoSection`）；
2. 该区显示哪些 = **未完成的全部**（今天 + 以后 + 已逾期 + 未排期）；
3. 右侧时间列 = 「在右侧显示逾期；对于未来的任务，显示日期」。

问题出在 ADR-032：它把待办区限制成「只显示今天 + 未排期」（`lib/todoToday.ts` 的
`filterToday`），于是**明天 / 下周的待办在面板里完全不可见** —— 用户明明设了未来计划，
窗口里却一条也看不到，等于把「计划」这个功能做成了数据黑洞。当时 ADR-032 的
Consequences 自己也写了这个代价（「未来的待办在它们的日子里之前不可见」），现在用户
明确不接受这个代价。

同时，一旦显示全部未完成，时间列沿用旧的「只写 `HH:MM`」就不成立了：
「明天 09:00」和「今天 09:00」会显示成同一个 `09:00`。

## Decision

### 1. 显示范围：全部未完成 + 今天完成的已完成（`lib/todoPanelLists.ts`）

```ts
pending: doneAt == null                      // 全部未完成：今天 / 未来 / 已逾期 / 未排期
done:    doneAt != null && doneAt >= 今天 00:00  // 只留今天完成的
```

- **未完成不加任何时间过滤**：这是用户这次要的东西。ADR-032 的 `filterToday` /
  `isTodoToday` / `lib/todoToday.ts` 已删除（全仓无其它引用，`startOfTomorrow` 一并消失）。
- **已完成只留「今天完成的」**：用户只要求放开*未完成*的范围。已完成是逐日累积的历史，
  几个月下来可能上百条，252px 宽的面板会被它占满，真正要做的待办反而被挤到屏幕外；
  面板本身是「今日」面板（表头就是「今日计时」），今天的完成记录才有当天的反馈价值。
  昨天的完成记录仍在库里（`todo_list { includeDone: true }` 一直拿全量），要改只需改本文件一处。
- 边界按自然日 `[今天 00:00, 明天 00:00)`，与 `useTodayRecords` 的今日区间同口径。
- 切分在**纯函数**里，因为面板文件已贴着 300 行上限（AGENTS.md 硬约束），且面板级测试
  需要一个可直接断言的入口。`lib/` 不反向依赖 `stores/`（zustand + React 运行时不该进纯函数层），
  所以没有复用旧的口径入口，而是就地写两条判据 —— 旧的 `todoStore.splitTodos` 因此成为死代码，
  已在本轮删除（留着会给后来者第二套切分口径）。
- 计数不另写过滤：「待办事项 · N」= `pending.length`、「已完成 · N」= `done.length`，
  随范围自动跟随；空态判定改成「今日记录为空 且 两节都为空」。

### 2. 时间列：按「与今天的关系」分级（`lib/todoTimeLabel.ts`）

| 情形 | 右侧文案 | `title`（hover） |
|---|---|---|
| 两项时间都没设 | 空（留白，ADR-028 §7） | 无 |
| 未完成 + `planned_at < now`（逾期） | `逾期` | 逾期基准确认到分钟 `YYYY-MM-DD HH:MM` |
| 未完成 + 目标时刻不在今天 | `MM-DD`（如 `10-22`） | 目标时刻的完整时间 |
| 未完成 + 目标时刻在今天 | `HH:MM` | 同上 |
| 已完成 | 完成日 = 今天 → `HH:MM`；否则日期 | 同上 |

- **目标时刻**沿用 ADR-028 §7 的口径：`remind_at ?? planned_at`（有开始时间按开始），
  不改成只看 `planned_at`。
- **逾期只判 `planned_at < now`**：`remind_at` 是开始 / 提醒时刻，过了不代表没兑现截止承诺
  （与 `pendingTone` 同一条判据）。两处现在**共用** `isTodoOverdue`，避免
  「格子写着逾期、行却不着色」这类漂移。
- **逾期时 `title` 给的是 `planned_at`**（逾期基准）而不是目标时刻：只设了开始时间、
  开始时间还没到、截止却已过的行，hover 到开始时间会答非所问。
- **跨年写 `YY-MM-DD`**（如 `27-01-05`）：面板里只写 `01-05` 的话，读者分不清是哪一年。
- 逾期行的颜色仍由既有 `data-tone="overdue"` 的 CSS 负责，**没有新增色值**；
  `.todo-pend__time` 的 `min-width` 从 34 → 40px（`MM-DD` / 「逾期」在 34px 里会被挤成两行），
  跨年的 8 位日期让它按内容自然撑开。

## Consequences

- **面板会变长**：用户未来所有未完成待办都在这里。缓冲手段是既有的两条 —— 未完成 > 8 条
  折叠成「还有 N 条」，以及窗口高度上限内的滚动。真到几百条仍会难用；那时该做的是
  「按日期分组 / 全部待办窗口」，而不是把范围收回去。
- **`title` 兜住被缩写的信息**：格子里最多 5–8 个字符，完整时间只在 hover 出现；
  触屏 / 无 hover 场景读不到，但那一格本来就只是索引，改时间走「编辑事项」。
- **md-sync 后端口径不变**：插件 `#### 待办事项` 区块仍是「未完成 + 计划时间不在今天」
  （上一轮已定的口径，见 CHANGELOG `[Unreleased]` 第一种同步落点）。前端面板与日记区块
  是两套过滤器，**不要**指望它们一一对应：面板是给人当下看的工作面，日记是给未来的自动归档。
- **过期待办仍会在跨天被清掉**（V0.3.15）：所以「逾期」这个文案只在当天可见，符合预期。
- 未排期待办（两项时间都空）仍留在列表里，时间列留白 —— 它没有任何别处可显示，
  隐藏等于让它彻底消失（ADR-032 的这条理由继续成立）。
