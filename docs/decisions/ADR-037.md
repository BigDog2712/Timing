# ADR-037：迁移可见性为什么必须新增 2 条 IPC 命令（破「命令 65 零变化」）

## Status

Accepted（2026-11-04，V0.5.0）

## Background

0.5.0 把 identifier 从 `com.tickbar.app` 换成 `com.timing.app`（品牌从重写期工程代号
`TickBar` 回归 `Timing`，见 ADR-036）。老用户的数据躺在旧目录里，新版本首次启动时由
`lib.rs::run()` 最开头的迁移模块**只复制不移动**地搬过来，旧目录永久保留。

两件事撞在一起：

1. **迁移发生在窗口出现之前**。它跑在 `Builder::run()` 之前（`ARCHITECTURE §1.3.1`：`setup`
   钩子晚于 config 建窗，写在那里会让 window-state 先回填默认位置，首启必失败）。那一刻
   没有 `AppHandle`、没有日志（`log::init` 还没跑）、更不能弹 Tauri 的对话框。
2. **用户对结果的唯一感知是「打开后东西还在不在」**。迁移成功与「数据丢了」在用户眼里
   长得一模一样——都能打开，都不知道原来那 8 个事项、512 条记录去哪了。失败路径还会问用户
   「重试 / 以空白数据启动 / 退出」，选过「空白启动」的人下次再打开，看到的是一个
   **能正常使用、但空的新库**，而旧数据还在磁盘上。

所以 PRD 有一条硬需求 D4：设置页要能显示「数据来源」并给出「打开旧数据目录」的入口。

## Decision

**新增 2 条命令，且只加 2 条**：

| 命令 | 语义 | 入参 | 返回 |
|---|---|---|---|
| `get_migration_info` | 纯查询，幂等、无副作用 | 无 | `MigrationInfo` |
| `open_legacy_dir` | 动作：资源管理器打开旧数据目录；目录不存在返回 `IO_ERROR`，**不创建** | 无 | `()` |

命令数 65 → **67**；错误码 **16 不变**；事件 **11 不变**；DB schema **v4 不变**。

### 1. 为什么不用「复用现有命令」

逐条查过当时的 65 条：

- `plugin_list` / `plugin_open_dir` 绑死 `<app_data>/plugins`，`md_sync_*` 绑死用户配置的
  外部落点；**没有任何一条能读 `app_data_dir` 下的任意文件或打开任意目录**；
- 诊断快照 `diagnostics.txt` 只有写没有读，而且它根本不是 IPC 命令。

「打开目录」这一半其实**不需要新能力**：`services/plugin.rs:124 open_user_dir` →
`infra/plugin_fs.rs:191 open_dir` 早就有现成的 `explorer <dir>` 实现，本方案只是把
「spawn explorer 且不建目录」抽成 `infra::shell_open::open_dir` 复用，`open_legacy_dir`
的命令体约 15 行。

但**已有的 `plugin_fs::open_dir` 不能直接复用成一个通用命令**：它接受调用方给的任意路径，
只是被 `plugin_open_dir` 硬编成了 plugins 子目录。把它暴露成「打开任意目录」的命令，等于
给前端开一条越过最小权限面的通路，与 ADR-015（前端不直连文件系统）冲突。路径必须由
后端用「权威 `app_data_dir` 的父目录 + 固定旧 identifier」现算，前端连传参的机会都不给。

### 2. 为什么不用「写 settings 表 + `get_settings` 读」

`settings` 确实是 kv 表（`migrations/0001_init.sql:73`：`key TEXT PRIMARY KEY / value TEXT NOT NULL /
updated_at INTEGER`），看起来「把迁移摘要写进一个 kv 行、前端读设置就有了」是零成本方案。

**但前端读设置不是读 kv。** `commands/settings_cmd.rs:54-58 get_settings(app, state) -> AppResult<Settings>`
返回的是**强类型 `Settings` 结构体**（`models/settings.rs`，`#[serde(rename_all = "camelCase")]`），
由 `services::settings::get()` 把 kv 行映射成字段。要展示迁移信息就得扩 `Settings` 类型 +
`services::settings::get()` 的映射 + 前端 `src/types/domain` 的 `Settings` 接口 + `settingsStore`
的消费方——**那是一次完整的响应体契约变更**，只是不新增命令名。而「打开旧目录」这一半仍需
1 条新命令，最终得到的是「1 条新命令 + 1 次隐式响应体变更」。

### 3. 结论的准确表述

> **(c) 省掉的只是「命令条数」这一项数字，省不掉契约变更本身；而且它是最坏的一类——`check:contract` 只比对命令名 / 错误码 / 事件，对响应体字段零校验，于是变更发生了而门禁全程绿。** (a) 把变更**显式化**：代价是多 2 个命令名、2 份 mock 实现与 1 节契约文档，换来**可枚举、可被 `check:contract` 机械校验**。故选 (a)。

这段是整份决策的核心理由，不要压缩成「为了迁移可见性新增了 2 条命令」——那句话丢掉了
**为什么另一个方案更差**，而「更差」正是选 (a) 的原因。

一句话概括这个不对称：**门禁看得见的变更，代价是 2 个命令名；门禁看不见的变更，代价是
一次没人评审过的兼容破坏。**

## Consequences

1. **四处落点必须同时改**：`lib.rs::generate_handler!`、`src/types/domain/ipc.ts::IpcApi`、
   `src/services/ipc.ts`、`src/mocks/browserMock*.ts`。缺一处 `npm run check:contract` 直接红，
   这正是选 (a) 换来的东西。
2. **不新增错误码**（约束一）：两条命令的失败一律 `IO_ERROR`。理由：错误码只在
   `error.rs` 定义且数量不变是 PRD 铁律；「旧目录不存在」「explorer 起不来」都不是用户
   可操作的新错误类别，给它们各开一个码只会让 16 码的封闭清单开始渗水。
3. **`open_legacy_dir` 路径由后端重算**（约束二）：完全忽略 `MigrationInfo.legacyDir` 的回传值。
   迁移标记是用户目录下的明文 JSON，改一行就能让应用 `explorer` 打开任意目录（路径注入）；
   `legacyDir` 字段只用于展示。
4. **`MigrationSource` 由后端判定**（5 值：`legacy` / `pending` / `skipped` / `fresh` / `unattached`）。
   判定需要「目标有无库 / 旧目录有无数据 / 两个标记文件是否存在 / 本次进程是否跳过」四项事实，
   前端只能看到其中一项的投影；把判定搬到前端等于让「文案」和「事实」各算一遍。
5. **响应体字段仍不受门禁保护**：`MigrationInfo` 增删字段时 `check:contract` 依旧全绿。
   这是 (a) 也没解决的问题，只是 (a) 把**命令面**的变化变得可见，已经比「什么都没变」好；
   字段级保护需要在契约文档里人工评审（`IPC-CONTRACT-v2.md` §12.9.2）。
6. **移动端同样注册两条命令**：`get_migration_info` 正常返回（无旧目录 → `fresh`），
   `open_legacy_dir` 返回 `IO_ERROR`；设置页的迁移卡在移动端整体不挂载。

## Alternatives considered

| 备选 | 可行性核实 | 结论 |
|---|---|---|
| **(a) 新增 2 条显式命令** | 4 处落点可枚举，`check:contract` 机械校验；「打开目录」复用既有 `plugin_fs::open_dir` 链路 | **采纳** |
| (b) 复用现有命令（`plugin_open_dir` 加 path 参数等） | 65 条里没有任何一条能读 `app_data_dir` 下任意文件或打开任意目录；`plugin_fs::open_dir` 虽已存在，但只接受调用方路径、由 `plugin_open_dir` 硬编成 plugins 子目录，暴露成通用命令 = 给前端一条「打开任意目录」的通路，与 ADR-015 最小权限面冲突 | **否决**（语义污染 + 越权面扩大） |
| (c) 写 `settings` 表 + `get_settings` 读 | `settings` 是 kv 表没错，但 `get_settings` 返回强类型 `Settings`，改它就是改响应体契约；且「打开旧目录」仍需 1 条新命令 → 最终是「1 条新命令 + 1 次隐式响应体变更」，而 `check:contract` 对响应体零校验 | **否决**（不是零成本，且是最坏的静默契约变更） |
