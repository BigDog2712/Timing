# ADR-029：事项窗口两节列对齐、编辑事项覆盖计时、进行中排最后、提醒圆圈

## Status

Accepted（2026-10-19，V0.3.11）

## Background

V0.3.10 把待办行改成「时间可见 + 点哪改哪」之后，用户对着真机给了五条调整（原话）：

1. 「事项菜单中，待办事项时间应显示在对应的开始时间列」；
2. 「事项菜单中，编辑事项功能应也能修改计时的事项」；
3. 「现在计时的事项应按时间显示在计时最后」；
4. 「今日计时后与待办事项后统一，将今日计时后的统计格式改为待办事项的格式」；
5. 「单击待办事项为是否提醒，提醒放在显示总时间的部分，黄色圆圈代表有时间提醒，无色为无提醒」。

其中 5 的点击目标经追问确认为：**点整行 = 开关提醒，完成改由圆圈承担**。

## Decision

### 1. 两节共用一套三列网格，时间列落在行的水平中线上

`minmax(0, 1fr) auto minmax(0, 1fr)` + 中列 `text-align: center`，两节同模板同 gap。

关键推论：因为左右各 1fr 等分，中列中心恒等于 `padding-left + 内容宽 / 2`，**与中列内容宽度无关** ——
所以「记录行 `09:00–10:30`」与「待办行 `09:00`」即使宽度不同，中线也完全重合。
headless Chrome 实测两节时间列中心同为 `x = 388`。

### 2. 「编辑事项」覆盖两节

计时行在编辑模式下：名字变改名按钮（就地 `InlineEditBar`）、行尾出现删除（→ 既有内联确认条）。
记录挂的是**事项**，删的是事项本身，所以保留二次确认 —— 不像待办行那样即时删除 + 撤销条。

**编辑态隐藏「时长」列**：四列（名字 / 时间 / 时长 / 删除）时名字只剩 **25px**（实测），改名时看不到字；
改成三列（名字 / 时间 / 删除）后名字回到 **108px**。编辑是瞬时态，时长的优先级低于名字。

### 3. 进行中排在计时最后

`TodosRecords` 先渲染已保存分组（开始时间升序），进行中的会话放最末。它是最后开始的那条，
时间序上本来就在末尾；以前钉在第一行，看起来像「不在时间线里」。

### 4. 表头统计格式统一

`今日计时 · N 条` → **`今日计时 · N`**，与 `待办事项 · N` 同格式；右侧总时长（`X 小时 Y 分`）保留。

### 5. 提醒圆圈：行尾、贴右沿、只表达提醒

- 位置：第三列、`justify-self: end` —— 右沿与表头总时长**同一列**（用户口径「提醒放在显示总时间的部分」），
  实测两处右沿同为 `497`。
- 颜色：`remind_at` 非空 → `--color-warn` 实心（黄）；为空 → `--line-3` 空心（无色）。
- 点击：**圆圈 = 完成 / 未完成**（`role="checkbox"`，`stopPropagation`）；**行内其余区域 = 开关提醒**。
- 打开提醒时的时刻来源：已有 `remind_at` → 清空；否则借用 `planned_at`；两个时间都没有 →
  当场弹 `DateTimePicker`（否则「打开提醒」没有时刻可依据）。已完成的待办点整行不动作。

## Consequences

- 两节在视觉上成为同一张表的上下两半：名字左、时间居中、右侧一列（时长 / 圆圈）。
  代价是待办行的名字列宽随中列内容变化（`1fr` 等分），不再是「名字尽量长」。
- **圆圈一词双职**（指示提醒 + 触发完成）是用户明确选择，但确实不是一个自解释的控件：
  完成态仍靠名字删除线，圆圈颜色永远只讲提醒。若真机上觉得别扭，最小改动是「圆圈只做完成开关、
  提醒色改为名字左侧细条」，无需动数据层。
- 编辑态与只读态的列数不同（记录行 3→3、待办行 3→4），编辑态是瞬时状态，不追求与只读态逐列对齐。
- 零 IPC / 零迁移 / 零错误码：提醒开关完全复用 `todo_update` 的 `remind_at` 三态；记录改名 / 删除复用既有命令。
