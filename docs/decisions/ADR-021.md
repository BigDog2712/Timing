# ADR-021：事项允许同名，下架 `ITEM_NAME_DUPLICATE`（17 → 16）

## Status

Accepted（2026-10-18；用户口径「新建事项应允许同名」，同时确认重命名 / 归档恢复一并放开）

## Background

`services/item.rs` 从 v0.1.0 起对事项名做唯一性校验：`create` / `update` / `unarchive` 三处
都先查 `repositories::item::name_exists`（`lower(trim(name))` 比较 active 事项），撞名就返回
`ITEM_NAME_DUPLICATE`。前端配合做了两件事：`ItemPicker` 捕获该码后渲染「已存在同名事项 +
直接使用该事项」的兜底按钮，`errorText()` 提供「已存在同名事项」文案。

这套设计把「名字」当成了业务主键，但事项真正的主键一直是 `id`。实际使用中它拦掉了三类
正当需求：

1. 归档后重建同名——因为 `unarchive` 也查重，归档项恢复时会被同名 active 项挡住；
2. 两条同名但不同色 / 不同提醒的事项（例如两个项目的「周会」）；
3. 改名撞上已有名字（用户只是想统一叫法）。

「同名记录要合并」这个真实需求不属于事项域，而属于**今日计时列表的展示口径**：原实现
`src/lib/todayGroups.ts` 按事项名分组。它与唯一性校验是绑在一起的一对——名字唯一时才成立。
一旦允许同名，按名字分组会把两条独立事项的记录挤成一行，右键菜单（改名 / 删除 / 便利贴）
只作用于其中一条。所以放开同名必须同时改分组口径。

## Decision

1. **事项允许同名**。`create` / `update` / `unarchive` 三处唯一性校验整体移除，
   `repositories::item::name_exists` 一并删除（没有第二个调用方）。
   名字仍做「trim + 非空 + ≤60 字」校验，口径不变。
2. **下架 `ITEM_NAME_DUPLICATE`**。它不再有触发点；闭集里留一个永远返回不了的码，等于给
   调用方一份假的失败契约。`error.rs` 的枚举、`as_str()`、构造器，前端 union
   `ErrorCode`、`errorText()` 的 case，`browserMockItems` 的同名校验同步删除。
   **基数是 16，不是 17**——下架与新增一样需要一次契约评审（与 ADR-018 同一条规矩）。
3. **今日计时改按 `itemId` 分组**。`groupTodayRecords` 的分组键由「事项名」改为「事项 id」；
   显示名仍取自 `nameOf(itemId)`（事项的**当前**名字），所以「改名前的历史记录与主记录并成
   一行」这个原始需求依旧成立——它们本来就是同一条事项。同名不同事项则各占一行。
4. `ItemPicker` 去掉 duplicate 态与「直接使用该事项」按钮（含 `app.css` 里随之失效的
   `.inline-error__action` 样式）。

## Alternatives

- **只放开新建**：改动最小，但口径不一致——新建能同名，把其中一条改成同名字却报错。
- **放开同名但今日计时仍按名字合并**：代码零改动，但同名两条事项的计时记录会并成一行，
  合并行的右键只作用于第一条，属于静默数据错配。
- **保留错误码但让它永不触发**：契约文档会继续宣称「同名会被拒」，而实际不会；
  `check:contract` 只比对三处清单是否一致，抓不到「码与行为脱节」。

## Consequences

- **契约变更**：命令数不变（63），错误码 17 → 16。`check:contract` 三处清单必须同步，
  否则门禁直接红——这条是机械保证，不靠记性。
- **老的 `ITEM_NAME_DUPLICATE` 不会再出现**：前端若仍有 `err.code === 'ITEM_NAME_DUPLICATE'`
  分支，TS 会报 `TS2367`（类型无重叠），编译期就能发现。
- **同名事项在 UI 上靠颜色 / 排序区分**，名字不再是身份：`items` 列表按
  `is_pinned DESC, sort_order ASC, id ASC` 排序，同名项稳定有序。
- **今日计时面板可能出现两行同名**：这是有意的——它们是两条独立事项，各自可改名 / 删除。
- **数据库无迁移**：`items` 表从 v0.1.0 起就没有 `UNIQUE(name)` 或同名唯一索引（`0001_init.sql`
  只给 `time_records` 建了 `uq_records_open`），唯一性从来只在 `services/item.rs` 里用一次
  `COUNT(*)` 现算。因此这不是 schema 变更，去掉校验即可生效，历史数据无需清洗。
