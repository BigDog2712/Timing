# ADR-035：事项菜单点行开始计时 / 强制退出可选补时 / 记录按连续性分行

## Status

Accepted（2026-10-21，V0.4.x / Unreleased）

## Background

用户口径（原话，一次给三条）：

> 在事项菜单点击事项 可以直接开始计时
> 对于被强制退出的事项，可选择退出期间是否并入计时
> 同一事项若时间不连续，则分行记录，若时间连续则合并记录

三句话分别打在三个不同的地方，但都指向同一件事：**「这一条事项现在该不该在计时」这个
问题，用户希望从记录本身就能回答，而不是靠记性去找菜单。**

### 1）点事项没有反应

事项窗口（= 用户口中的「事项菜单」）里，今日计时的记录行只支持右键：左键点了什么都不会发生。
右键菜单更奇怪——首项恒为「停止计时 · {事项}」，只有当前正在计的那条可用，其它行上它就是
一条**永远禁用**的项，等于「这个窗口里没有任何办法开始计时」。

顺带查出一个更底层的毛病：`switch_item(end_and_start)` 在 Rust 侧有一条守卫
（`services/timer.rs`：会话 `running_since` 非空直接返回 `TIMER_ALREADY_RUNNING`），
而三个前端入口（`ItemMenu` / `CommonItems` / `usePillInlineEdit`）都在「计时中」直接调它——
浏览器里点「开始计时 · 另一个事项」，收到的是错误提示而不是切换。契约 §5.2 的状态图
（`running/paused ──switch_item(end_and_start)──▶ running`）与这条守卫是矛盾的。

### 2）强制退出期间算不算工作

`resolve_open` 原来只有 R-2 一种口径：应用关着就停表。崩溃 / 被杀之后重启，继续计时从
`now` 重新累加，结束并保存只认最后一次落盘的 `accumulated_sec`。但真实情况常常是
「我一直在这件事上，只是 Timing 被关掉了」——比如系统更新强制重启、任务管理器误杀。
这段时间该不该算，只有用户知道，所以做成一个**默认关闭**的开关，而不是改默认口径。

### 3）一天里同一件事的两段被拉成一行

`groupTodayRecords` 按事项 id 合并，把「09:00–09:30」和「14:00–14:15」并成
`09:00–14:15 · 45 分钟`。起点与止点被拉满整个白天，读起来像「一天都在干这件事」，
时长却只有 45 分钟——两个数字互相打脸。

## Decision

### A. 记录行整行可点 = 开始这一条事项（`onActivate`）

- 只读态整行可点（`data-clickable="true"`，`cursor: pointer`），`Enter` 等价点击；
  行内命中按钮 / 输入框不算点行；**编辑模式整行不可点**（那里的点击是改名 / 输时间）。
- 口径收敛到 `useTimerActions.startOrSwitch(itemId)` 一个函数：
  - 空闲 → `start(itemId)`；
  - 正在计**别的**事项 → 先 `pause_timer`（冻结累计）再 `switch_item(end_and_start)`；
  - 就是**当前这一条** → 跑着不动，暂停着继续。
- 为什么不是先改后端守卫：`switch` 的守卫是既有行为（有专门用例钉着），而「暂停 → 分段」
  两步在语义上与它等价（`live_duration` 在暂停后就是 `accumulated_sec`），且不动状态机。
  代价是多一次 IPC（~30ms，肉眼不可见）。
- `ItemMenu` / `CommonItems` 一并改走 `startOrSwitch`——它们原本就是「运行中点不动」的受害者。
- 事项窗右键菜单首项改为随状态切换：当前会话 → 「停止计时」，其它 → 「开始计时 · {事项}」。

### B. `resolve_open_record` 增加 `includeGap`（可选，默认 `false`）

- `gap = floor((目标时刻 − running_since) / 1000)`；`resume` 的目标时刻是 `now`，
  `close` 的是 `endedAt`。
- 三个前提缺一不可：`includeGap` 为真、会话**当时正在跑**（`running_since` 非空）、
  `目标时刻 > running_since`。暂停中崩溃不补（没有流逝，补了等于把暂停算成工作）；
  墙钟回拨不补（不倒扣累计）。
- `discard` 一律忽略——记录本身都不要了。
- 前端只在空档 ≥ 1 分钟时显示勾选项（`lib/recoverGap.ts` 的 `shouldAskGap`）；
  「继续计时」「结束并保存」都吃这个开关，「丢弃」不吃。
- 默认值保持 R-2：不勾 = 原行为，老前端不带该字段也不会报错（Rust 侧 `Option<bool>`）。

### C. 记录行按「事项 + 连续性」切分

- `lib/todayGroups.ts`：先按事项 id 分桶，桶内按开始时间升序扫描；相邻两条
  `next.startedAt ≤ prev.endedAt + CONTIGUOUS_GAP_MS`（60s）才留在同一行，否则另起一行。
- 60s 是「停止 → 又点开始」的手速上限；再严会把正常的分段拆碎，再松会把两段不相干的工作并回去。
- 上行没有结束时间（脏数据）时无从判断连续，直接另起一行。
- 行 key 改 `grp-{itemId}-{firstId}`：旧的 `grp-{name}` 在拆分后必然撞 key，
  右键 / 删除确认会作用到错误的那一行。
- 时间口径不变：合并行 = **时长求和 + 最晚结束**，不做区间反推（应用关着不计时，
  这是 R-2 与 B 的共同前提）。
- 日记（`#### 事项计时`）**不动**：那里一个事项就是一个 Planner 任务、多段 `log` 条目
  本来就是分开写的；把连续段合并会破坏渲染 ↔ 解析的往返（导入按 `started_at` 精确配对记录），
  收益远小于风险。

## Alternatives

- **放开后端 `switch` 的守卫**：一处改动就能让所有入口正常，但它会同时打开「双击分段」
  这类竞态（第二次点击会把刚开的新会话再切一次，产生零长度段），而现守卫有专门用例与
  注释支撑。前端两跳的代价只有一次 IPC。
- **`just_switch` 改归属**：不行。它保持同一条会话不换，等于把上一段的工作时间全记到
  新事项上——那是「纠正错误归属」的语义，不是「换一件事做」。
- **强制退出一律补时**：会把「昨晚忘关应用」的 12 小时记成工作，且无法撤回。做成默认关闭的
  勾选项，让用户在弹窗那一刻自己判断。
- **强制退出一律不补**（现状）：正是这次要改的，用户在「我知道自己一直在干活」的场景没有出路。
- **分行阈值改成 5 分钟 / 15 分钟**：5 分钟会把「去倒杯水回来接着干」拆成两行；15 分钟会把
  两段独立的工作并回去。60s 只覆盖手速与误触。
- **把连续性规则也套到日记上**：见 §C 最后一条，往返会坏。

## Consequences

- **契约**：`resolve_open_record` 入参多一个可选 `includeGap`，命令数不变（65）。
  `docs/phase2/IPC-CONTRACT-v2.md` §3.4 / §4.4 已同步；`check:contract` 只核对命令名与错误码，
  参数变化靠文档 + 本 ADR 约束。
- **无迁移**：`includeGap` 是入参不是字段；记录表的 `accumulated_sec` 仍是唯一时长事实。
- **`resolve_open` 签名变化**：所有调用点（commands / tray / 3 个测试文件）都补了第 4 个参数，
  新增用例 `tests/timer_recover_gap.rs` 6 条把四种组合钉死。
- **行为变化（不再是 bug 静默）**：计时中点另一条事项现在会真的切过去。旧行为是弹
  `TIMER_ALREADY_RUNNING` 提示。
- **今日计时行数会变多**：一天里断成几段就有几行，表头「今日计时 · N」的计数跟着变准。
- **合并行的编辑边界**：拆行后 `firstId` / `lastId` 属于**该段**，改时刻只影响这一段——
  这正是用户要的「分行记录」。
- **已知未做**：日记区块仍按事项合一个块（见 §C），如果以后要「日记也按段分行」，
  必须同时改导入的配对策略。
