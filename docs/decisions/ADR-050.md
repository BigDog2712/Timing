# ADR-050：数据与插件落点移到应用同级（便携优先，不可写时显式回退 AppData）

## Status

Accepted（2026-11-06，V0.11.6；用户口径「调整数据及插件默认落点，落点应在应用所在位置，若无应新建
对应文件夹如 plugins 以及对应数据落点」；追问后确认：「我就要放置在同目录，不能获取权限就提醒用户
获取权限，未获取权限无法写入再考虑 AppData」、「老数据首次启动自动搬过来（复制，不删旧数据）」、
「Markdown 同步一起挪到应用旁边」）

## Background

`com.timing.app` 这个 identifier 从 V0.5.0 起把三样东西钉在 `%APPDATA%`：

| 现状 | 证据 |
|---|---|
| 数据根 = `%APPDATA%\com.timing.app` | `app/bootstrap.rs:32`、`commands/plugin_cmd.rs:22,32`、`commands/migration_cmd.rs:25,66`，共 5 处调用 `app.path().app_data_dir()` |
| 用户插件目录 = `<数据根>\plugins` | `infra/plugin_fs.rs:44-46` `user_plugin_dir()` |
| md 同步出厂落点 = `%USERPROFILE%\Documents\Timing` | `models/md_sync_config.rs:21` |

这带来三个与产品形态冲突的后果：

1. **便携不成立。** 把 exe 拷到 U 盘带回家，数据仍在这台机器的 `%APPDATA%`——绿色版只是「不用安装
   的安装版」。
2. **用户找不到自己的数据。** 用户报障时要发的是 `<exe 同级>\data\timing.db`，而实际在
   `C:\Users\<用户>\AppData\Roaming\com.timing.app\`——一个默认隐藏、名字像哈希的目录。
3. **插件有两个语义相同的位置。** `plugin_fs.rs:47-70` 已经在扫 `<exe 目录>\plugins`（`PluginSource::Exe`）
   和 `<数据根>\plugins`（`PluginSource::User`），用户完全分不清该往哪放。

约束（不能碰的口径）：单文件 ≤300 行；Rust 六层单向依赖 `platform → infra → services → app/jobs →
commands`；契约 67 命令 / 11 事件 / 16 错误码不变；`infra/appdata_migrate`（V0.5.0 品牌改名迁移）必须
继续可用。

## Decision

### 1. 落点形状：`<exe 目录>` 是唯一入口，数据与插件**同级不同父**

```
<exe 目录>\
├─ Timing.exe                     主程序
├─ data\                          数据根 platform::app_dir::data_root()
│  ├─ timing.db (+ -wal / -shm)   infra::db::init_pool
│  ├─ logs\                       platform::log::init（timing-YYYY-MM-DD.log / panic.log / diagnostics.txt）
│  ├─ backups\md\                 infra::md_backup::set_root
│  ├─ md\                         md 同步出厂落点（%APP_DIR%\md，见 §5）
│  ├─ migrated-to-portable.json   本文 §4 的幂等标记
│  └─ migrated-from-tickbar-app.json / pending-migrate.json / migration-failed.txt
│                                 品牌改名迁移痕迹（随整树复制过来，不重算）
└─ plugins\                       插件根 platform::app_dir::plugins_root()
   └─ <id>\plugin.json
```

`%APPDATA%\com.timing.app` 不会被删，也不会被清空；它只保留一样东西——`.window-state.json`（见 §6）。

**为什么 `plugins\` 放根、不放 `data\` 下**（四条判据，任一独立成立）：

| # | 判据 |
|---|---|
| 1 | 事实层面：`infra/plugin_fs.rs:47-56` 的 `exe_plugin_dir()` **已经**是 `<exe>\plugins`，而且 `docs/plugin-spec.md` 把「随包插件放 exe 同级」写成过口径。改成 `data\plugins` 等于给同一语义增加第二个位置，用户已经在用的旧位置失效 |
| 2 | 可删性级别不同：删 `data\` = 重置我的计时数据，删 `plugins\` = 卸载我装的插件。同一个父目录下，用户无法执行其中一个而不心惊 |
| 3 | 可见性要求相反：`plugins\` 是唯一一个用户**要主动打开、往里放文件**的目录（`plugin_open_dir` 按钮就是为了它）；`data\` 是程序自管、用户手改会坏。把手放目录藏进自管目录，等于把「插件放哪」变成需要解释的问题 |
| 4 | 升级覆盖安全：便携升级只解压 `Timing.exe` 一层，永不覆盖 `data\` / `plugins\`。两者同级时这条规则只要在一处成立，嵌套后会多出「解压顺序 vs 目标已存在」的分支 |

**旧位置逐项对应**：

| 旧（`%APPDATA%\com.timing.app\`） | 新（便携模式） | 谁在用 | 可删 |
|---|---|---|---|
| `timing.db` / `-wal` / `-shm` | `<exe>\data\timing.db` | `infra::db::init_pool` | 否（删 = 丢数据） |
| `logs\*.log` / `panic.log` / `diagnostics.txt` | `<exe>\data\logs\` | `platform::log` / `app::diagnostics` | 是 |
| `backups\md\*.bak` | `<exe>\data\backups\md\` | `infra::md_backup` | 是（只是覆写留底） |
| `plugins\<id>\` | `<exe>\plugins\<id>\` | `infra::plugin_fs` | 是（删 = 卸载插件） |
| `migrated-from-tickbar-app.json` / `pending-migrate.json` / `migration-failed.txt` | `<exe>\data\` 同名 | `infra::appdata_migrate` | 否（QA 核对依据） |
| `.window-state.json` | **不搬**（见 §6） | `tauri-plugin-window-state` | 是（窗口位置） |
| （无） | `<exe>\data\migrated-to-portable.json` | `infra::portable_migrate` | 否（删 = 允许重搬一次） |
| `%USERPROFILE%\Documents\Timing\*.md` | `<exe>\data\md\*.md`（只影响未保存过落点的用户） | `services::md_sync` | 用户自己的日记，不归应用管 |

**插件扫描拓扑（三种组合，`infra::plugin_fs::scan_roots`）**——这是「插件放哪」的实际生效规则，三种
组合必须分开说，混着讲就会在开发档上自我打脸：

| 组合 | 扫描根（按优先级） | 设置页的「来源」标签 | 说明 |
|---|---|---|---|
| **便携 + release** | `User` 一条 = `<exe>\plugins` | 只会出现「用户」 | **不产 `Exe`**：`<exe>\plugins` 在便携模式下**就是**用户目录（`plugin_open_dir` 给用户的正是它），再标成「随包」是文案在骗人；而 V0.11.5 删掉 `md-sync` 贡献点之后，仓库里本来也不存在「随包插件」这个实体 |
| **回退 AppData** | `Exe` = `<exe>\plugins` → `User` = `%APPDATA%\<identifier>\plugins` | 「随包」与「用户」都可能出现 | 两条路径不同，是真正的两个位置：装在 `Program Files` 的用户可以靠 `<exe>\plugins` 做「随程序分发的插件」 |
| **debug 构建（任意落点）** | 最前面恒多一条 `Dev` = `<仓库根>/plugins` | 「开发」 | `dev_plugin_dir()` 只看 `cfg!(debug_assertions)`，与落点无关。所以「便携模式下恒为 user」这句话的准确表述是**「便携 + release」** |

`scan_roots` 末尾仍有一次**按小写路径去重**：它是**防御，不是主路径**——上面三种组合在正常配置下
都不会出现重复路径，只有「用户把整个便携目录拷进 `%APPDATA%`」「手动建同名目录」这类异常才会命中。
**它命中时本身就是一条值得看一眼的信号**（说明扫描根配置异常），所以保留它、但在文档里明确它
**不承担便携模式的正确性**：便携模式不重复是靠「不 push `Exe`」，不是靠去重。

**文案分支一个都没删**：`PluginsTab.tsx:26` 的 `exe: '随包'`、`services/plugin_merge.rs:50` 的
`"exe" => "随包"`、`services/plugin.rs:50` 的「同一 id 已由『…』来源加载，本份被跳过」全部原样保留——
回退 AppData 与 debug 组合下这三处**仍会命中**。所以准确口径是：**「随包」与「同 id 被跳过」这两种提示
只在回退 AppData / debug 下可能出现；便携 + release 下插件来源恒为「用户」**。判据是「哪种组合会命中」，
不是「把这个标签删掉」——删了回退模式的用户会看到一个空标签和一条没有下文的日志。

### 2. 单一解析点：`platform/app_dir.rs` + `OnceLock`，五处调用收敛为两处

新增叶子模块 `src-tauri/src/platform/app_dir.rs`（只依赖 `std` / `dirs`，不依赖 tauri）：

| 项 | 形状 |
|---|---|
| `pub struct Roots { data: PathBuf, plugins: PathBuf, portable: bool }` | 一次决策的完整结果；`Roots::sandbox(app_data_dir)` 给移动端用（插件根 = `<沙箱>/plugins`） |
| `static ROOTS: OnceLock<Roots>` | 进程内唯一、写入后不可变 |
| `pub fn set(roots: Roots) -> bool` | 只由 `app::portable_boot` 调一次；返回「本次是否写入成功」（`false` = 已被写过，忽略并记 WARN，不 panic） |
| `pub fn get() -> Option<&'static Roots>` | 显式询问「解析过没有」 |
| `pub fn data_root() -> PathBuf` | 已解析返回 `roots.data`，否则返回 `fallback_appdata()` |
| `pub fn plugins_root() -> PathBuf` | 同上口径的插件根（**插件目录本身**，便携 = `<exe>\plugins`） |
| `pub fn plugin_base() -> PathBuf` | `plugins_root()` 的**父目录**。存在的唯一理由：`infra::plugin_fs::user_plugin_dir(root)` 内部还会 `join("plugins")`，命令层直接喂 `plugins_root()` 会得到 `<exe>\plugins\plugins`。**不改 `user_plugin_dir` 的签名**——那会连带改 8 个测试夹具；两个口径分开命名，「插件放哪」就不会以「多一层 plugins」的形式悄悄坏掉 |
| `pub fn exe_dir() -> Option<PathBuf>` | `std::env::current_exe()?.parent()` |
| `pub fn appdata_dir(identifier: &str) -> Option<PathBuf>` | `dirs::data_dir()?.join(identifier)`（与 Tauri 同源，ARCHITECTURE §1.3.4） |

> **`plugin_base()` 的不变式不是恒等式**：它**无条件丢掉末段**（`path.parent()`），所以
> `plugins_root()` 的末段**必须**是字面量 `plugins`。哪天有人把插件根改成 `extensions`（或任何别的名字）
> 而只改了 `Roots` 的构造处，`plugin_base()` 会静默返回上一层目录 → 扫描/建目录落到错误的文件夹，
> 而且没有任何报错。QA 判为「latent 耦合，不是 bug」，但这条不变式必须写在文档里：
> **改插件目录名 = 同时改 `Roots.plugins` 与「末段必须叫 plugins」这个前提**。真要支持任意目录名，
> 正确做法是让 `plugin_fs::user_plugin_dir()` 接受「插件目录本身」而不是「父目录 + join」。
| `pub fn fallback_appdata() -> PathBuf` | `appdata_dir("com.timing.app")`；**只**在 `get()` 为 None 时兜底（单测 / 移动端早期） |
| `pub const TOKEN: &str = "%APP_DIR%"` | md 落点占位符（§5） |

**为什么是 `OnceLock` 而不是存进 `AppState`**：

1. 解析必须发生在 `AppState::manage` **之前**——日志根、md 备份根、`db::init_pool` 全部以数据根为入参
   （`bootstrap.rs:32-60` 的顺序注释写明了这条依赖）。放进 `AppState` 就是「建库之后才能知道库在哪」。
2. `migration_cmd` / `plugin_cmd` 是异步命令，拿 `OnceLock` 是无锁读取；`AppState` 里塞 `PathBuf` 还要
   每条命令解 `State`。
3. `OnceLock` 不可清除 = 「一个进程只做一次落点决策」这个语义的机械保证。**不能**改成每次调用
   `current_exe()` 现算：探测/迁移是有副作用的一次性动作，现算会让用户在对话框里选过的结论在后续
   调用里被推翻。

**三处 `app.path().app_data_dir()` 怎么改**（`bootstrap.rs:32`、`plugin_cmd.rs:22,32`、
`migration_cmd.rs:25,66`）：

| 文件:行 | 改法 |
|---|---|
| `app/bootstrap.rs:32` | `let data_root = platform::app_dir::data_root();`；`#[cfg(mobile)]` 分支先 `app_dir::set(Roots::sandbox(app.path().app_data_dir()?))`（移动端沙箱不变）。之后的 `log::init` / `boot_timing::set_dir` / `md_backup::set_root` / `init_pool` / `write_snapshot` 全部换成 `&data_root` |
| `commands/plugin_cmd.rs:22,32` | `let root = platform::app_dir::plugin_base();`（**插件根的父目录**，不是 `plugins_root()`，也不是数据根）→ 继续调 `services::plugin::ensure_user_dir(&root)` / `open_user_dir(&root)`。**`plugin_fs::user_plugin_dir(root)` 的签名保持 `root.join("plugins")` 不变**，测试夹具零改动 |
| `commands/migration_cmd.rs:25,66` | marker / pending / `db::resolve_db_path` 用 `app_dir::data_root()`；`legacy_dir_of(app_data_dir)` **换成新函数** `appdata_migrate::legacy_dir()`（= `dirs::data_dir()/com.tickbar.app`，见 §4 末尾的坑） |

不新增 IPC 命令，契约面不动。

### 3. 可写性：每次启动探测（成本微秒），不可写时用 rfd 弹「为什么 + 怎么办」

落点是**三个文件**，边界按「顺序 / 文案 / 磁盘」切开（`portable_boot` 一度冲到 310 行撞门禁，
且改文案不该碰决策流程）：

| 文件 | 职责 |
|---|---|
| `app/portable_boot.rs` | 顺序与判据：探测 → 迁移 → 注入 `app_dir`；用户点了哪一项就注入哪个根 |
| `app/portable_prompt.rs` | **纯 UI**：`rfd::MessageDialog` 的五段文案与按钮映射（`ask_permission` / `ask_migrate_failed` / `ask_appdata_notice` / `ask_no_data_dir` / `ask_webview2` + `webview2_ok`）。**不复用** `app::preboot::ask`：那是 private，且文案与品牌改名迁移绑死 |
| `infra/portable_probe.rs` | **碰磁盘**：`probe()` 可写性探测 + `OptOut` 读写（`OPTOUT_FILE` 常量） |

| 项 | 结论 |
|---|---|
| **何时探测** | 每次启动，位置在 `app::portable_boot::prepare()`（`Builder::run()` 之前，与 `app::preboot` 同级）。唯一例外：`portable-optout.json` 存在时整段跳过（用户已明确选择过） |
| **为什么每次** | 权限可能被回收、目录可能被整包搬到别处。探测 = `create_dir_all` + 写 16 字节 + 回读 + 删除，微秒级。「探测一次存起来」会让用户改完权限后仍走 AppData，那是最难排查的一类「我明明给了权限」 |
| **怎么探测** | `infra::portable_probe::probe(dir)`：建目录 → 写 `.timing-write-probe.tmp` → **回读比对** → 删除 |
| **判据** | `create_dir_all` 失败（只读介质 / 无 ACL 写入权 → `os error 5 Access is denied`）→ 不可写；写失败 → 不可写；回读内容不一致 → 不可写（被重定向） |
| **不用什么** | 不用 `metadata().permissions().readonly()`：它只反映文件的 `FILE_ATTRIBUTE_READONLY` 位，与 ACL 无关，在 `C:\Program Files` 上返回 `false` 却写不进去 |
| **探测的副作用** | `probe` 会**建出** `<exe>\data`。探测通过后必须 `fs::remove_dir`（只删得掉空目录）再进迁移，否则迁移的 `rename` 目标已存在、Windows 上必失败，还会白留一份空备份 |
| **对话框用什么** | **Rust 侧 `rfd::MessageDialog`**。不用 `tauri-plugin-dialog`：它的 `blocking_show` 源码注释明写「should NOT be used when running on the main thread」，而这一步就在主线程（理由是 `app/preboot.rs` 顶部那段注释，同一套场景）。rfd 已是依赖（`default-features=false, features=["common-controls-v6"]`），零新增编译单元；此刻事件循环未启动，同步阻塞安全。前端 dialog API 在这里用不上——还没有窗口 |

```rust
// src-tauri/src/infra/portable_probe.rs
/// 返回 Err 时，字符串是**直接给用户看**的中文原因（不做 code 映射，也不进 IPC）。
pub fn probe(dir: &Path) -> Result<(), String> {
    std::fs::create_dir_all(dir).map_err(|e| format!("无法创建目录 {}：{e}", dir.display()))?;
    let probe = dir.join(".timing-write-probe.tmp");
    std::fs::write(&probe, b"timing-probe")
        .map_err(|e| format!("无法写入 {}：{e}", probe.display()))?;
    let back = std::fs::read(&probe).map_err(|e| format!("回读校验失败：{e}"))?;
    let _ = std::fs::remove_file(&probe);
    if back != b"timing-probe" {
        return Err("写入后的内容回读不一致（可能被系统重定向到 VirtualStore）".into());
    }
    Ok(())
}
```

**提示文案**（逐字；标题「无法在应用目录写入数据」，`MessageLevel::Warning`，
按钮 `MessageButtons::YesNoCancelCustom("重试", "改用 AppData", "退出")`——Windows 在部分系统语言下
会走 `MessageDialogResult::Custom(文案)` 分支，两种都要认，照抄 `app/preboot.rs::ask`）：

```
Timing 的数据要放在应用旁边，但当前没有写入权限：
  <exe>\data

原因：<系统返回的错误原文>

请任选一种方式授予权限，然后点「重试」：
  · 右键 Timing.exe 所在文件夹 → 属性 → 安全 → 编辑 → 选中你的用户 → 勾选「完全控制」
  · 或右键 Timing.exe →「以管理员身份运行」（数据将由管理员账户写入）
  · 或把整个 Timing 文件夹移到你有写权限的位置（例如 D:\Tools\Timing）

确实无法授予权限时，可以点「改用 AppData」：数据会存到
  %APPDATA%\com.timing.app
此时数据不再位于应用旁边，Timing 会在该目录留下 portable-optout.json 记录这个选择。
```

用户点「改用 AppData」后，**再弹一句确认**（`MessageLevel::Info`，按钮 OK）——这是「不能静默」的
落点，不靠日志：

```
已改用 AppData
数据目录：%APPDATA%\com.timing.app

想让数据回到应用旁边：给目录权限后，删除上面目录里的 portable-optout.json，
下次启动会自动重新检测并搬过来（旧数据只复制、不删除）。
```

**状态落盘**：`%APPDATA%\<identifier>\portable-optout.json`。

```json
{ "schema": 1, "at": "2026-11-06T10:12:33+08:00", "appVersion": "0.11.6",
  "reason": "permission-denied", "exeDir": "C:\\Program Files\\Timing",
  "dataDir": "C:\\Users\\me\\AppData\\Roaming\\com.timing.app",
  "detail": "无法写入 C:\\Program Files\\Timing\\data\\.timing-write-probe.tmp：Access is denied. (os error 5)" }
```

`reason` 是**稳定机读串**（不是中文句子，`detail` 才是给人看的原文），三个值：

| 值 | 何时写 |
|---|---|
| `permission-denied` | `<exe>\data` 探测失败，用户点了「改用 AppData」 |
| `migrate-failed` | 老数据迁移失败（`stage: detail` 拼进 `detail`），用户点了「改用 AppData」 |
| `exe-dir-unavailable` | 拿不到 `current_exe().parent()`（极端环境），没有「应用旁边」可言 |

**为什么落在这儿**：它必须能在「数据根还没定」的瞬间被读到 → 不能进 db；落在兜底位置本身，则「写不
进去」这个事实就等价于「连 AppData 也不可用」，直接报错退出，语义闭合。它同时是「用户已被告知」的
书面证据。存在时启动**不再探测、不再询问**，只在日志写一行
`portable: data root = <path> (reason: portable-optout.json)`，并在 `logs/diagnostics.txt` 多两行
（`portable` / `plugins_dir`）。**恢复路径**：删掉该文件，下次启动重新探测（对话框里写明了）。

**回退顺序与尽头**：`<exe>\data`（探测通过 + 迁移可用）→ `%APPDATA%\<identifier>`（用户明确选择）→
两者都不可写时弹 `MessageLevel::Error` 并 `std::process::exit(3)`（新常量
`EXIT_NO_DATA_DIR`）。不能带病启动：没有可写目录 = 没有日志、没有库、没有可诊断的信息。
回退到 AppData 时插件根也回到 `%APPDATA%\<identifier>\plugins`（`plugin_list` 的
`ensure_user_dir` 照旧建空目录），**不在应用旁边另建一份空 `plugins\`**——两处都建等于让用户再一次
分不清该往哪放。

### 4. 老数据迁移：复用 `appdata_migrate` 的原语，不共用它的状态

新增 `src-tauri/src/infra/portable_migrate.rs`，编排顺序与 `appdata_migrate::run_at` 一致：
`cleanup_temp → 判据 → copy → verify → swap → write_marker`（as-built 没有独立的 `decide` 函数，
判据内联在 `execute()` 里；swap 的备份走 `stash_aside`，落点是 `source` 的兄弟目录，见下表）。

| 复用什么 | 怎么用 |
|---|---|
| `appdata_migrate::copy::copy_tree(source, temp)` | 整树复制（含 `-wal` / `-shm`，按名字前缀映射） |
| `appdata_migrate::verify::verify(temp, source)` | 四重校验，返回五表行数 |
| `appdata_migrate::copy::rename_aside(target, backup)` | 目标已存在时改名备份（**V0.11.6 落地时改到** `%APPDATA%\<identifier>.portable-premigrate-<ts>\`（`source` 的**兄弟**目录，不是它里面），保留不删；exe 旁边只许有 `Timing.exe` / `data` / `plugins`。**不能**放进 `source` 里：那会让迁移往「只读」的旧目录写东西，且下次迁移会把备份当用户数据一起复制（QA `a1d` / `a1e`）。跨盘时 rename 会 `EXDEV`，退成「复制 → 删原件」，见 `portable_migrate::stash_aside`） |
| `appdata_migrate::paths::DB_NAME` | 库名唯一口径 |

**不**复用什么（这是新建文件而不是加参数的唯一理由）：`appdata_migrate::Paths` 的形状是「同一个
`base` 下两个 identifier 目录 + `.migrating` 临时名」，而本次 target（`<exe>\data`）与 source
（`%APPDATA%\com.timing.app`）**不同父**；更关键的是 `mod.rs` 的 `OUTCOME` / `PATHS` 是全局单值缓存，
两个来源共用一个缓存会让 `app::diagnostics::migration_label` 与 `commands::migration_cmd::resolve_source`
张冠李戴（品牌改名 vs 搬运落点，是两件事）。

自己的状态：`static OUTCOME: Mutex<Option<Outcome>>`，`Outcome ∈ {NoLegacy, AlreadyPresent(PathBuf),
Migrated(Facts), Failed{stage, reason}}`（`stage ∈ cleanup / copy / verify / swap`；写标记失败**不**是一
种 `Failed`，见下）。供 `bootstrap` 在日志就绪后补记（`app::portable_boot::note()` + `portable_migrate::outcome()` 两处读）。
临时目录 `<exe>\data.migrating`（同盘 → 换名原子）。

**落地时砍掉了设计里的 `Occupied`**：判据表 ① ② 两行（目标已有库 / 已有标记）语义相同——「什么都不做」，
`AlreadyPresent(PathBuf)` 一个变体就够，多一个分支只会让调用方写两遍同样的 match 臂。

**触发判据**（表即实现，顺序即优先级）：

| # | 条件 | 结局 | 动作 |
|---|---|---|---|
| ① | `<data>\timing.db` 存在 | `AlreadyPresent` | 什么都不做。**绝不覆盖、绝不合并**用户的新数据 |
| ② | 无 data 库 + `migrated-to-portable.json` 存在 | `AlreadyPresent` | 同上（用户删了库但留着标记 = 有意重置） |
| ③ | 无 data 库 + 无标记 + `%APPDATA%\com.timing.app\timing.db` 存在 | `Migrated` | 复制 → 校验 → 换名 → 写标记 |
| ④ | 无 data 库 + 无标记 + 旧目录无 `timing.db` | `NoLegacy` | 不搬。判据只看 **db**：`appdata_migrate` 的 `has_legacy_data` 把 `logs` / `.window-state.json` 也算「有数据」，那是为「别把老目录改名丢下」，本次搬家的价值全在库，`logs` 重来即可 |
| ⑤ | 复制 / 校验 / 换名任一步失败 | `Failed` | 清临时目录 → 弹窗三选一 → **旧目录原样保留**（`copy_tree` 全程只读源；已被 `stash_aside` 挪走的目标目录在回滚时挪回） |

「新旧同时存在」= 命中 ① 或 ②，一律不动。若 data 目录非空但**没有**库（用户手动放了别的东西），
仍然走 ③：只往空位加文件、不删任何东西。换名前的目标目录由 `portable_migrate::stash_aside`
挪到 **`%APPDATA%\<identifier>.portable-premigrate-<ts>\`**（`source` 的**兄弟**目录，
不是它里面，也不在 exe 旁边）——**永不删除**，那是用户自己的文件。

**幂等与「只复制不删除」**：标记 `<data>\migrated-to-portable.json`
（`schema:1, at, appVersion, source, dbBytes, walCopied, verified:"size+integrity+rows"`）写在**数据目录
里**，随数据一起走——换机器 / 换 U 盘后标记跟着数据，不会重复搬；反过来，新机器上 `%APPDATA%` 即使
有数据也不会盖掉便携数据（① 优先）。
`plugins` 子目录的处置：迁移成功后若 `<exe>\plugins` **不存在**，把 `<data>\plugins` 整个
`fs::rename` 到 `<exe>\plugins`（同盘原子、零拷贝，appdata 里那份仍在）。

**若 `<exe>\plugins` 已存在**（便携包里带 `plugins\README.txt` 占位，所以这是绝大多数情况，
不是边缘情况）：**逐个子目录**搬到 `<exe>\plugins\<name>`，撞名的那个留原地 + 一条 WARN，
两边都不删不覆盖；顶层散文件（`README.txt`）不动。「不合并」的正确粒度是**单个插件**，
不是整个目录——整目录放弃会让升级用户的插件文件还在、功能全没（`data\plugins` 不在
`plugin_fs::scan_roots` 的扫描拓扑里）。

**失败不阻塞**，但「用户看到的」与「落盘的」是两回事，别混。三种情形要分开记：

| 情形 | 结局 | 用户看到的 | 落盘的 |
|---|---|---|---|
| `cleanup` / `copy` / `verify` / `swap` 失败 | `Failed { stage, reason }` | 弹框三选一（重试 / 改用 AppData / 退出） | **只进 `logs/`**：`bootstrap` 补记 `portable migrate failed: stage=… reason=…`（ERROR）。**不**写 `portable-migrate-failed.txt` |
| 数据已就位、**标记写不进去** | **仍是 `Migrated`**（不是 `Failed`！） | 什么都不弹——数据真的搬好了，弹失败框会让用户以为白搬一次，而重试立刻命中 `AlreadyPresent`，比不报更糟 | `%APPDATA%\<identifier>\portable-migrate-failed.txt` 追加一段明细 `stage=marker` + 日志 ERROR |
| 用户选「改用 AppData」 | `Proceed`（AppData 根） | 二次告知框（`ask_appdata_notice`） | `portable-optout.json(reason:"migrate-failed")` + 上表的日志 |

也就是说：**`portable-migrate-failed.txt` 只有一个写入点**——`append_failure(source, "marker", …)`
（`infra/portable_migrate.rs:163-165`），只记录「标记写失败」这一种。`copy` / `verify` / `swap` 这类
真失败**不写这个文件**，只进 `logs/`。选「重试」原地重跑（内部先清 `.migrating`）。
**「旧目录一个字节都不改」的准确口径**——旧目录里**已有内容**一个字节不动（不删、不改、不覆盖）；
只有两处**新增**，且都不覆盖任何东西：

1. 备份目录 `%APPDATA%\<identifier>.portable-premigrate-<ts>\`（`source` 的**兄弟**目录），
   只在 `<exe>\data` 已存在时产生。**永不删除**——里面是用户自己的文件，谁都不能删，包括我们自己。
2. `%APPDATA%\<identifier>\portable-migrate-failed.txt`（仅「标记写失败」时 `append` 追加一行，见上表）。

源侧读取本身也是只读：`copy_tree` 不写源；V4 行数比对的源库改成在**影子副本**上开，
见 `appdata_migrate/verify.rs::shadow_facts`——只读连接同样会让 SQLite 在源目录落地 `-shm`/`-wal`。

**坑（必须一起改）**：`app/bootstrap.rs:133` 的 `record_migration` 会拿
`mig::paths_used().target`（品牌改名迁移的目标 = `%APPDATA%\<identifier>`）和「权威数据根」比对，
不一致就打 ERROR。改造后权威数据根是 `<exe>\data`，这个比对会**每次启动都报一条假 ERROR**。
必须把比对对象换成「按 `dirs::data_dir() + identifier` 独立算出的品牌迁移目标」。

### 5. Markdown 同步出厂落点：`%APP_DIR%\md`

| 项 | 结论 |
|---|---|
| 字面量 | `MD_SYNC_DEFAULT_ROOT = r"%APP_DIR%\md"`（`MD_SYNC_DEFAULT_FILE` 不变） |
| 占位符语义 | `%APP_DIR%` = **数据根**（便携 = `<exe>\data`；AppData 兜底 = `%APPDATA%\com.timing.app`），不是 exe 目录 |
| 为什么不用绝对路径 | 便携版要带着走；绝对路径写进默认值后换盘符 / 换机器立刻失效。这与「原来用 `%USERPROFILE%` 而不是 `C:\Users\me\Documents`」是同一条理由 |
| 为什么不用 `%USERPROFILE%` | 用户口径明确「一起挪到应用旁边」 |
| 解析位置 | 新文件 `infra/md_env.rs`（把 `md_file.rs:55-95` 的 `expand_env` 整段搬过来，`md_file.rs` 留 `pub use crate::infra::md_env::expand_env;`）。**必须搬**：`infra/md_file.rs` 现在 298/300 行，塞不下新逻辑 |
| 解析顺序 | 先替换 `%APP_DIR%`（**保留名，永不查环境变量**，否则用户机器上恰好有 `APP_DIR` 变量就会被劫持），再走原有 `%VAR%` / `~` |
| 兜底 | `app_dir::get()` 为 `None` 时退回 `fallback_appdata()`（纯函数、无 IO）。**绝不返回未替换的占位符**——那会在 CWD 下造出一棵叫 `%APP_DIR%` 的目录树，比报错更难查 |
| 老用户 | **不受影响**：`services/md_sync/config.rs::load` → `merge_bindings(saved, defaults)` 只在「保存值里缺这个 kind」时追加默认值，保存过的 `root` 一个字节都不动 |
| `enabled` | 出厂仍 `false`（V0.11.5 定的），不动 |

### 6. 明确不搬的东西

`.window-state.json` 由 `tauri-plugin-window-state` 写在 `app_config_dir()`（Windows 上 =
`%APPDATA%\<identifier>`）。该插件 2.5.0 的 `Builder` 只提供 `with_filename(impl Into<String>)`
（`src/lib.rs:366`），目录由 `app.path().app_config_dir()` 决定（`:138`、`:541`），**没有改目录的
公开入口**。结论：不搬，记为已知限制——代价只是「窗口位置不跟着走」，不影响数据完整性与可写性
（`%APPDATA%` 恒可写）。要真正做到零残留得 fork 插件或自己写窗口状态持久化，收益不抵成本。

落地还有一个动作：迁移是**整树复制**，所以 `%APPDATA%` 里那份 `.window-state.json` 会被一起复制进
`<data>\`；`portable_migrate` 在换名成功后显式 `fs::remove_file(<data>\.window-state.json)` 删掉这份
**复制品**（源目录那份不动）。不删的话，便携目录里会长期躺着一个「看起来像配置、实际永不读取」的文件，
用户手改它也不会生效——比没有更糟。

### 7. 契约与门禁

| 项 | 结论 |
|---|---|
| 命令 67 | 不变。不新增 IPC（插件目录在 `plugin_list` 内部解析；数据根由启动阶段决定，不经命令暴露） |
| 事件 11 | 不变。启动期提示一律走 rfd 原生对话框，不 emit |
| 错误码 16 | 不变。不可写 / 数据根解析失败一律 `IO_ERROR`（与 `migration_cmd` 既有口径一致） |
| `check:contract` | 绿。本轮不动 `lib.rs::generate_handler!`、`error.rs`、`infra/events.rs`、`src/types/**`、`src/mocks/**` 的处理器键集合 |
| `get_migration_info` DTO | **不加** `source: "portable"` 变体。它表达的是「品牌改名迁移」，把「数据根在哪」塞进同一字段会让两件事共用一个词 |
| `check:size` | 绿的前提是先搬 `expand_env`（`md_file.rs` 298→约 250）与行数中性地改 `MdSyncTab.tsx:289`（该文件 295/300） |
| `check:layers` | 绿。`platform` 是叶子，只用 `std` / `dirs`；`infra → platform`、`app → platform`、`commands → platform` 都在允许方向 |

## Alternatives

| 方案 | 否决原因 |
|---|---|
| 数据根直接等于 `<exe 目录>`（不套 `data\`） | exe 同级会立刻混进 `timing.db`、`logs\`、`backups\`、`.window-state.json`，与用户自己放在那儿的 dll / 说明文件无法区分；`data\` 一层换来「删一个目录 = 重置数据」的干净语义 |
| `plugins\` 放 `data\plugins` | 见 §1 四条判据；额外一条**致命**理由：`data\plugins` **不在 `plugin_fs::scan_roots` 的扫描拓扑里**（拓扑只有 `Dev` / `Exe` / `User` 三个根，`data\` 一个都不占）。后果不是「扫两遍、同 id 互相判被跳过」这种可见的重复记录，而是**整个目录根本不会被读**——旧插件文件还在、功能静默全失效，用户只能看到「插件没了」而找不到原因 |
| 把 `Roots` 存进 `AppState` | 数据根要用于「建库之前」的日志与迁移，`AppState` 是建库之后才 `manage` 的（`bootstrap.rs:53`） |
| 每次调用现算 `current_exe()` / `app_data_dir()` | 落点是有副作用的一次性决策（探测 + 迁移 + 用户选择），现算会让用户在对话框里的选择被后续调用推翻 |
| `metadata().permissions().readonly()` 判可写 | 只看文件属性位不看 ACL，`C:\Program Files` 上返回 `false`，判据无效 |
| 不可写时静默回退 `%APPDATA%` | 用户明确否决（「不能获取权限就提醒用户」，回退必须是显式可见的） |
| 用 `tauri-plugin-dialog` 弹启动期提示 | `blocking_show` 不能跑在主线程，而这一步必须在 `Builder::run()` 之前 |
| 把落点选择写进 `settings` 表 | 决策时刻数据库还不存在（迁移跑在 `init_pool` 之前），读不到 |
| 迁移用 `fs::copy` 直接覆盖 | 覆盖即丢数据；沿用「复制到 `.migrating` → 校验 → 换名 → 写标记」 |
| 迁移成功后删掉 `%APPDATA%` 那份 | 用户明确否决（「复制，不删旧数据」）；删除也无法回滚 |
| md 默认落点写死绝对路径 | 换盘符 / 换机器立刻失效；便携版的核心诉求就是可搬 |
| 给 `get_migration_info` 加 `portable` 来源 | 语义污染，且要同步改 TS 类型 + mock + 组件测试，收益为零 |

## Consequences

- **便携版第一次真正成立**：整个文件夹（`Timing.exe` + `data\` + `plugins\`）复制到任何可写位置即可
  带走全部数据与插件；删除 `data\` 等于重置。
- **权限提示成为首要接触面**：装在 `C:\Program Files` 的旧用户升级后会看到一次提权对话框。这是本条
  需求的直接代价，必须在 ADR-051 里用安装位置策略（NSIS `currentUser`）把它变成少数场景而不是默认。
- **`%APPDATA%\com.timing.app` 长期保留**：它继续保存 `.window-state.json` 与那份迁移前的原样数据。
  设置页「迁移信息」卡片（`MigrationInfoCard.tsx`）已经能打开旧目录，用户可自行清理。
- **`infra/md_file.rs` 变小、新增 `infra/md_env.rs`**：`expand_env` 的外部调用点只有
  `md_file_test.rs:59`，靠 re-export 保持路径不变。
- **两条日志/诊断口径要同步**：`diagnostics.txt` 的 `legacy` 行改由 `appdata_migrate::legacy_dir()`
  算（不再由数据根反推），并新增 `portable` / `plugins_dir` 两行；否则便携模式下这一行会打印
  `<exe>\com.tickbar.app`（一个永不存在的路径）。
- **测试面几乎为零**：`grep -rn "app_data_dir" src-tauri/src/tests/` 命中 0，`support::unique_dir()`
  只造临时目录传给 `db::init_pool(&dir)`，所以**没有夹具需要跟着改**。唯一语义变化是
  `tests/md_sync_disabled_gate.rs:162` 那条「默认值指向哪儿」的守卫，断言是存在性不变、仍通过，
  但注释要改。新增用例见 ADR-051 §7 与交接清单。
- **已知限制（本文登记，不另开单）**：
  1. `.window-state.json` 仍在 `%APPDATA%`（插件无改目录 API）。
  2. 迁移后若 `<exe>\plugins` 已存在，旧插件留在 `data\plugins` 不自动合并。
  3. 便携目录被整体移动后，Windows 自启（`tauri-plugin-autostart` 记的是旧 exe 绝对路径）失效，
     需要用户重新开关一次。
  4. **便携包自带的 `<exe>\data\README.txt` 会让每次首启都产生一个备份**：`portable_boot.rs:118` 的
     `remove_dir(<exe>\data)` 在目录非空时失败（`scripts/build-desktop.mjs:211` 会往便携包写
     `data\README.txt` 占位），于是每个用户首次启动都会走一次 `stash_aside`，在 `%APPDATA%` 留下一个
     `<identifier>.portable-premigrate-<ts>\`（内容只有一个占位文件）。v0.11.6 收尾修正在迁移前先清掉
     「只含我们自己的占位文件」的目录，正常路径不再产生备份；用户真的往 `<exe>\data` 里放过东西时仍走
     stash。**修复只影响「是否产生这个空备份」，不删除任何已存在的 `portable-premigrate-*` 目录**——
     那份永远是用户原有文件（修复落地前的中机构建会出现该目录；出厂构建不应再有）。
     判据站得住的理由：那个占位文件是**我们自己写的**，内容里就写着「删掉本文件不影响使用」
     （`scripts/build-desktop.mjs:212-216`），清掉它不算动用户数据；一旦目录里出现别的文件就不清。
