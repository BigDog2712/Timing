# ADR-030：待办两级提醒、到点自动开始、待办→计时一次到位、记录时刻可改

## Status

Accepted（2026-10-19，V0.3.12）

## Background

V0.3.11 把黄圈做成「有没有提醒」的指示后，用户补充了它的**含义**，并追加三条联动要求（原话）：

1. 「黄色圆点的提醒指的是，在事项开始前 15 分钟，弹窗提醒，是否要修改时间。这个提醒是‘轻提醒’，
   目的是给那些不确定时间的事项用的」；
2. 「待办事项提前五分钟弹出提醒，询问是否在当前事项结束时自动开启待办事项计时，若无事项，
   在既定时间自动开始计时」；
3. 「待办事项开始计时后自动挪至计时区，不再在待办区」；
4. 「编辑事项功能开启后，可以修改所有事项的名称和时间，点击哪里就改哪里」。

经追问确认三处口径：弹窗**复用现有提醒浮出卡**；开始计时**立即软删除**待办；记录（计时行）的
**起止时刻也要能改**（也就意味着不能只靠前端，得让后端认这件事）。

## Decision

### 1. 两级提醒都挂在 `todos.remind_at`（= 开始时间）

| 级 | 时刻 | 载荷 | 浮出卡正文 | 动作 |
| --- | --- | --- | --- | --- |
| 1 轻提醒 | `remind_at - 15min` | `todo-nudge { stage: 1 }` | 「15 分钟后开始 · HH:MM，要不要改时间？」 | 推迟 15 分 / 1 小时 / 明天此刻（= 平移 `remind_at`）、不用改 |
| 2 自动开始询问 | `remind_at - 5min` | `todo-nudge { stage: 2 }` | 「HH:MM 开始 · 当前计时结束后自动开始？」 | 结束后自动开始（`auto_start=1`）、现在就开始（`todo_start`） |

- **为什么不再复用 `reminded_at`**：它是一次性标记，只够去重一次。两级提醒需要**单调递进的阶段**，
  于是新增 `todos.remind_stage`（0 → 1 → 2，`MAX()` 只升不降）。`reminded_at` 仍由
  `reminder_set/clear` 维护，供通用提醒列表使用。
- **改时间会重置链路**：`repositories::todo::update` 一旦写入新的 `remind_at`，同时把
  `remind_stage` 归零、`reminded_at` 清空 —— 否则「推迟 15 分钟」之后永远不会再提醒。
- **待办退出通用到点提醒**：`repositories::reminder::due` 只查 `items`。待办的 `remind_at`
  语义是「开始时间」，再走一遍 `reminder-fired` 会在 T 时刻多弹一条系统通知。
- **抗休眠靠宽限窗口**：`TODO_NUDGE_GRACE_MS = 10min`。`remind_at + 10min < now` 的待办由
  `todo_nudge::expire` 静默记成 `stage=2` 并撤回 `auto_start` —— 关机一夜后不该连着补弹两条、
  更不该在启动瞬间自己起一个计时。
- **事件**：新增第 10 个事件 `todo-nudge`（载荷 `TodoNudge`），前端在 `useAppBootstrap` 订阅，
  交给 `todoNudgeActions.onNudge` → 复用同一张 `ReminderPopover`（新增 `mode: 'nudge'`，
  正文抽到 `NudgeBody`）。这样「到点提醒 / 轻提醒 / 自动开始询问」永远只占一张卡。

### 2. 到点自动开始：空闲直接开始，忙碌等会话结束

- 空闲（`timer::state.session.is_none()`）且该待办两级提醒都已过、刚到点（宽限窗口内）→
  `jobs::nudge` 直接 `todo_start`（用户口径「若无事项，在既定时间自动开始计时」）。
- 忙碌时用户点「结束后自动开始」→ `auto_start = 1`；`services::timer_stop::stop` 保存成功后调用
  `todo_start::after_stop`，把最早一条应允过的待办顶上。**不受宽限窗口限制**（用户显式答应过，
  长会话跑完也该开始），失败只记日志 —— 自动开始失败不能把「结束计时」变成失败。
- 重启后的陈旧应允由 `expire` 撤回（`auto_start = 0`），避免开机瞬间自动起计时。

### 3. `todo_start`：开启即移出待办区

新增第 61 个命令 `todo_start(id)` → `services::todo_start::start`：

1. 待办必须存在且未完成（否则 `TODO_NOT_FOUND`）；已有会话 → `TIMER_ALREADY_RUNNING`；
2. 事项**按标题匹配**（`items.name COLLATE BINARY = todos.title`），没有就新建一条
   —— 与 `soft_delete_for_saved_record` 同一口径，避免同名两个事项；
3. `timer::start` 之后**立刻**软删除这条待办（用户口径「不再在待办区」）。

> `timer::stop` 里按同名清理待办的老逻辑保留：它服务的是「用户手动起了同名事项」这条历史路径
> （`timer_todo_link.rs` 的用例仍在断言它）。

### 4. 记录起止时刻可改：复用 `update_record`，不新增命令

`update_record` 本来就带 `startedAt` / `endedAt`（且有 `ended >= started` 校验），
所以命令层零改动，只补两件事：

- **时长跟着区间走**：`services::record::update` 在 `startedAt` 或 `endedAt` 真的被写时，
  重算 `accumulated_sec = (ended - started) / 1000`。只改备注 / 事项时**不动**累计秒数
  —— 那可能是含暂停的真实时长。
- **前端**：记录行在「编辑事项」模式下，两段时刻变成两枚 `RecordTimeChip`（点开 `DateTimePicker`，
  落库后重拉今日数据）；记录的时刻没有「置空」语义，浮层的「清除」按「不改」处理。
  分组行改的是**组内最早开始**与**最晚结束**那两条记录（`TodayGroup.firstId / lastId`）。

## Consequences

- 契约增量：命令 60 → **61**（`todo_start`）、事件 9 → **10**（`todo-nudge`）、错误码仍 15
  （`TODO_NOT_FOUND` / `TIMER_ALREADY_RUNNING` / `INVALID_DURATION` 都已存在）。
- 数据库增量：`0004_v0312.sql` + `MIGRATE_COLUMNS_V4`（`todos.remind_stage`、`todos.auto_start`），
  `schema.version = 4`；`tests/migration*.rs` 的版本断言同步。
- **轻提醒不是每条待办都能关**：它是「有开始时间」的必然结果（黄圈 = 有开始时间）。
  这符合用户口径（轻提醒给不确定时间的待办用 —— 给个大概时刻即可），但意味着
  「有开始时间但不想被提醒」目前做不到。真要分开，得给 `todos` 加一个独立的开关列。
- 两级提醒都只在应用运行时有效（查询式扫描，无系统级闹钟）：应用没开就不会提醒，
  这也正是宽限窗口存在的理由。
- 记录时长与区间从此强绑定：手动改正一段记错的时间，`accumulated_sec` 会被区间覆盖，
  原来的暂停时间不再保留（用户要的就是「这段时间」）。
