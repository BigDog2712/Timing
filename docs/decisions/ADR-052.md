# ADR-052：跨窗口数据刷新走「窗口焦点」，不为它新增 IPC 事件

## Status

Accepted（2026-11-06，V0.11.7；触发点是现场「事项窗三条记录全显示『未归类』、还被拆成三行」）

## Background

现场（v0.11.6 安装版真实数据库，用户当时正在用）：

| 表 | 数据 |
|---|---|
| `time_records` 今日 | id 60 → `item_id=19`；id 61 → `item_id=20`；id 62 → `item_id=19` |
| `items` | 19 = `Timing优化及十五五文件学习`；20 = `上厕所`；都 active、名字正常、没有 NULL |

界面上这三行**全部**显示「未归类」，而且被拆成三段。看起来像「事项名丢了」，实际数据完好。

根因（读代码确认，不是推测）：

1. 悬浮窗（label `main`）与事项窗（label `todos`）是**两个独立 webview**，各有自己的一份
   zustand store（`useItemStore`）。
2. `usePillInlineEdit`（悬浮窗新建 / 改名事项）只刷新**悬浮窗自己**那份 itemStore。
3. 事项窗是浮层：`useWindowLeaveHide` 只 `hide()` 不卸载，「再打开」不重新 mount，
   所以 `useEffect([])` 的首帧 `useItemStore.reload()` 不重跑。
4. `TodosWindow` 的 `window focus` 监听只 reload 了**待办**（`useTodoStore`），没有事项。
5. 于是事项窗的 items 里查不到 19 → `itemStore.itemName()` 回落「未归类」；而
   `lib/todayGroups.ts::identityOf()` 对「未归类」改用 `id:<itemId>` 当分组键 →
   19 / 20 / 19 被拆成三行。

即：**视图快照过期**，数据库与 Markdown 一直是对的（所以修在前端，不动存储层）。

## Decision

新增 `src/hooks/useItemsRefreshOnFocus.ts`，在**会显示事项名的窗口**里挂一次：
`window focus` 与 `document visibilitychange`（转 visible）时重拉 `list_items`。
目前挂在两处：

| 窗口 | 挂载点 | 覆盖的场景 |
|---|---|---|
| 事项窗 `todos` | `TodosWindow` | 悬浮窗新建 / 改名事项后，事项窗再打开显示真名 |
| 主窗 `main` | `App.tsx::MainWindow` | 事项窗「编辑事项」改名后，悬浮条的 `--pill__name`、事项菜单、便利贴列表跟上 |

设置窗 / 便利贴窗不挂：它们不显示事项名，挂上只是多打一次没有消费者的查询。

**不新增 IPC 事件**，理由见下。

## 为什么不新增一条 `items:changed` 事件

事件的成本不是「多一个字符串」：

1. **它是契约的一部分**。现在是 11 条事件，`npm run check:contract` 三方断言（后端常量 /
   `IPC_EVENTS` / emit 点）逐条比对。加一条要走契约评审、改三处、更新
   `docs/phase2/IPC-CONTRACT-v3.md`。
2. **它会把窗口生命周期泄漏进 IPC 契约**。要发得对，得在**每一个**改 items 的地方 emit：
   `usePillInlineEdit`（新建 / 改名）、`itemRowActions`（改名 / 删除）、`ItemMenu`、`ItemPicker`、
   `mobileTimerActions`、`moyuActions`、`items_*` 的 md 导入……漏一处就回到今天这个 bug，
   而且漏了没人报错——这类「靠记性维持」的契约正是本仓库最反对的东西（AGENTS.md 硬约束一段）。
3. **它不解决「什么时候该刷」**。事件只解决「有变化」，而窗口**重新可见**这个时刻本身
   （hide → show 不重挂）也只能靠焦点/可见性来感知，绕不开。

焦点是每个窗口天然拿得到的信号，不依赖「谁改的」、不依赖记得 emit，因此放在窗口侧收口。

## 取舍与代价（明确说清）

| 项 | 结论 |
|---|---|
| 多打的查询 | 主窗每次获得焦点会多一次 `list_items`。本地 SQLite 小表查询，毫秒级；换来「一整类跨窗陈旧」的消失 |
| 不可见时不拉 | `visibilitychange` 转 `hidden` 同样会触发，所以 handler 里先看 `document.visibilityState === 'hidden'` 直接返回 |
| 失败静默 | 焦点刷新是「顺手跟上」，失败不弹提示（`catch(() => undefined)`）——不该因为一次后台重拉失败打断正在打字的人 |
| 与 `mdSyncChanged` 的关系 | **不替代**。那条事件仍负责「md 导入改了数据 → 各窗刷新」，它是服务端明确知道「有了新数据」的场合；本 hook 只补「窗口刚被看见」这一维 |
| 两个信号并联 | `focus` 是主路径（后端 `show() + set_focus()`，见 `infra::window::open_panel_window`）；`visibilitychange` 兜最小化还原。任一条不灵时另一条兜底。**均未在真机上验证**（沙箱无 GUI），已列入 CHANGELOG 的待人工确认项 |

## 备选方案（都否掉了）

| 方案 | 否掉的理由 |
|---|---|
| 新增 `items:changed` 事件 | 见上一节：契约成本 + 漏 emit 无报错 + 仍解决不了「窗口重新可见」 |
| 事项窗每次 `show` 时后端主动 emit 一次 | 后端 `open_todos_window` 只管窗口，不该知道前端有哪些 store；而且「显示」与「刷新」又被绑成一条新契约 |
| 把事项窗改成「隐藏即卸载」 | 直接毁掉 `useWindowLeaveHide` 的现成体验（再开即原位、无白闪、无重挂开销），代价远大于收益 |
| `list_items` 结果做跨窗共享缓存（localStorage / BroadcastChannel） | 两个 webview 之间同步状态要自己实现一致性（谁赢、何时失效），比「重拉一次」复杂一个数量级，且仍然解决不了上面第 3 点 |
| 让 `itemName()` 回落时显示 `id:19` 之类的原始 id | 只是把「未归类」换成另一种错误显示，问题没解决（分组仍然拆开） |

## Consequences

- 跨窗陈旧这一类问题从「每个改动点都要记得 emit」变成「窗口获得焦点就自愈」，新增的
  改名入口不需要再想这件事。
- 现状的 `mdSyncChanged` 刷新逻辑保持不变；两者是互补维度（数据变化 vs 窗口可见）。
- 若将来出现**不通过焦点也能变**的 items 变更（例如后台定时任务批量改名），仍需那条 IPC 事件——
  届时再按契约流程加，理由与这次不同（这次是「窗口可见」，那次是「后台无窗口」）。
