`check:layers` 7 条规则双绿；`services/md_sync/mod.rs`（300 行）、`infra/md_file.rs`、`models/md_sync.rs` 三个文件的

## Background

v0.11.12 及以前的手机链路是四跳：

```
SQL(PC) → md(PC) → OneDrive → RemotelySave → Obsidian(手机) → SAF → SQL(手机)
```

四跳里有两个第三方（OneDrive、Obsidian）、两种授权（OneDrive 账号、SAF 目录授权），以及一个随时会坏的环节：
Obsidian 的自动格式化插件重排标题与表格，而 Timing 靠「区块标题 + Markdown 表格」定位解析，格式一变就解析不动。
链路上任何一跳失败，症状都是「手机上少了几条」，而且没有一处日志能说清是哪一跳。

主人 2026-11-06 两次拍板（后一次推翻当天早先的「7 天窗口」版本），把目标定成两端对称：

```
SQL(PC) ↔ WebDAV(坚果云) ↔ SQL(手机)
```

口径六条：路径可配 + 两种部署模式（本地目录 / WebDAV）；只同步当天、历史天不参与；待传队列补漏；
冲突用内容差分不用 mtime；TimingMD 独立存一份（默认 `%APP_DIR%\md-webdav`）；备份可查看可恢复覆写；不做端到端加密。

这一轮真正的难点不是「怎么发 HTTP」，而是四个边界条件：

1. 合并逻辑不能再写一份（`sync_all` 已经 300 行贴线）；
2. 历史欠账没有日期参数可用（`sync_all` 内部把日期写死成今天）；
3. WebDAV 上不存在可信的时间戳（客户端写不回 mtime）；
4. 备份文件名要能回溯落点，而写盘那条路径的签名不许动。

与既有决策的接口：ADR-042（两边都改过时以 Markdown 为准，内容差分）、ADR-047（同步内核化、出厂默认关）、
ADR-050（数据落点改到 exe 同级的 `<exe>\data`，`%APP_DIR%\md-webdav` 因此可用）、ADR-053（托盘入口与
`report.errors` 口径）、ADR-054 / 055 / 056（手机桥的「全有或全无」「`invoke.getArgs()`」「只许 `JSObject`」）。

## Decision

### 1. 云端第二落点复用 `sync_all`，不另写合并逻辑

现状事实：`src-tauri/src/services/md_sync/mod.rs` 正好 **300 行**，就是门禁上限（`scripts/check-size.mjs` 的
`LIMIT = 300`，`EXT` 覆盖 `.rs`）。`sync_all(pool, root_override: Option<&str>)` 是 `pub(super)`（`mod.rs:118`），
`super` = `crate::services`；`mirror::run_in(pool, root: &str)`（`mirror.rs:61`）是它的 `pub` 包装，手机端已经用它
跑过「换 root 的一轮」。

决策：`services/md_cloud` 做成 `md_sync` 的**兄弟模块**（`services::md_cloud`，`services/mod.rs` 加一行
`pub mod md_cloud;`），云端那一轮只调 `crate::services::md_sync::mirror::run_in(pool, cloud_root)`，一行合并逻辑都不写。
落地为 8 个小文件：`mod.rs` 146 / `round_webdav.rs` 188 / `round_push.rs` 198 / `round_folder.rs` 48 /
`pending.rs` 63 / `backoff.rs` 58 / `probe.rs` 89 / `state.rs` 52，最长的 198 行，离红线有 100 行以上余量。

为什么不能放子模块：加一行 `pub mod cloud;` 就是 301 行，撞门禁。而门禁不许为了让方案通过而降级——
这条纪律从 ADR-017 起就是硬约束，`scripts/size-allowlist.json` 的豁免要带 owner 与到期日，本轮**不开豁免**。

代价：`sync_all` 内部把日期写死成今天（`mod.rs:136` `let date = Local::now().date_naive();`，同款在 `mod.rs:96`），
所以云端那一轮**无法处理历史日期**，历史补传只能纯 PUT（第 2 条）。这个代价是自觉买下的：换来 `mod.rs` 的
`git diff` 为空，验收从「合并逻辑没改」升级成「整个文件零改动」，可机器断言。

顺序也是决策的一部分：Obsidian 那一轮在前、云端那一轮在后（`round_webdav::run` 的 ⑤ 先于 ⑥，`round_folder::run`
同构）。理由：Obsidian 侧的用户手改先入库，云端这份再从「已含手改的 SQL」渲染出去，于是 PUT 上去的内容
**一定包含本轮所有变更**；反过来（云端轮在前）会让 PUT 出去的那份缺一块，要等下一轮才补。而且 `root_override`
只替换 root、path 由 `root + file` 重算，两个落点的文件集合天然不相交（除非用户把 `local_root` 指到 Obsidian
目录，`MdSyncCloud::validate` 在保存时拒绝）。代价：手机在云端那份的改动，要等下一轮才出现在 Obsidian 那份里
（≤1 个轮询周期，默认 15 分钟）。两个方向必有一个滞后一轮，选「保证上传内容干净」这一侧。

一条实现期选择（与设计定稿不同，记在此处）：设计 §1.2 计划给 `models/md_sync.rs` 加 `MdSyncReport::absorb`
（254 → 264 行）。实现把 `absorb` 落在 `services/md_cloud/mod.rs:129`（`pub(crate) fn absorb`），于是
`models/md_sync.rs` 也保持零改动——「把两轮报告并成一份」是编排层的事，不该让数据模型知道「存在两轮」。

被否方案：`services/md_sync/cloud/` 子目录。技术上只差一行 `pub mod cloud;`，但那行就是 301。

### 2. 历史欠账只 PUT、不重新合并

现状事实：待传行的产生条件是「本地写 TimingMD 且内容变化」（`services/md_cloud/pending.rs::record_if_changed`），
触发点在 `round_webdav::run` 的第 ⑦ 步——**在两轮同步之后**读 `cloud_root/<today>.md` 算 FNV-1a 指纹。
也就是说，欠账那天的本地文件已经是「GET 到的远端内容 + SQL」的合并结果；补传只是把这份终态送上去。
而且历史那天的 SQL 不再增长（ADR-043 的跨零点拆分只发生在记录结束当时），本地文件对那天而言是终态。

决策：`round_push::push_history`（`round_push.rs:112`）只做「读本地 `<cloud_root>/<date>.md` → 带 `If-Match` PUT」，
不 GET、不合并、不重跑同步。模块注释（`round_push.rs:1-6`）把「不再合并」写死，理由指向设计 §2.3。

代价一：远端在欠账期间被第三方改过 → PUT 返回 412 → 记 `skip=conflict` + `report.errors`，**保留
`pending_since` 不覆盖**，下一轮再试。这比任务书 §6.1 的「同一天两端都改 → 后写覆盖先写」更保守，
用户口径是「宁可晚一天同步，也不要静默丢掉一端的手改」。

代价二（实现期补充，设计没写）：本地 `<cloud_root>/<date>.md` 不存在时**清账**（`repo::clear` +
日志 `skip=missing`）。不清就一直攒着，而它永远不会再产生内容——一条永远清不掉的欠账会让
`md cloud: pending=[…]` 那行永久非空，把真正待补的日期淹掉。

被否方案：给 `sync_all` 加 `date: Option<NaiveDate>` 参数（签名 1 行 + `mod.rs:136` 一行 + 5 个调用点
`run` / `tick` / `save_config_with_report` / `open` / `mirror::run_in` 传 `None`）。技术上完全可行，
但这是为一条当前走不到的路径（要真的出现「历史天两端都改」，前提是那天 PUT 失败且远端又被第三方改）
牺牲「整文件零改动」的证据强度，不划算。若以后真出现该场景，这 2 行 + 5 个调用点是最小改动，届时另开一份 ADR。

### 3. `rustls-no-provider` 下必须显式安装 crypto provider（不加就是崩溃）

现状事实：任务书 §4.5 写的 `rustls-tls-native-roots` 在 **`reqwest 0.13.5` 不存在**（`Cargo.lock:3089` 已锁 0.13.5；
本地 registry 的 `Cargo.toml` 的 `[features]` 里只有 `rustls` 与 `rustls-no-provider` 两个 TLS 入口）。
`rustls` 那条会连带 `__rustls-aws-lc-rs`：Windows 上要 cmake + NASM，Android 交叉编译更麻烦，本轮构建环境没有。

关键事实：`rustls-no-provider` 下 reqwest 的 `default_rustls_crypto_provider()` 是 **`panic!`** 实现。
而 `src-tauri/Cargo.toml:93` 的 release profile 写着 `panic = "abort"`——于是**第一次 HTTPS 请求就会把整个
进程带走**。这不是「同步失败」，是应用直接消失，而且发生在「用户填对了密码、第一次点同步」那一刻。

决策：`infra/md_webdav.rs::client()`（:175）在建 `Client` **之前**执行
`rustls::crypto::ring::default_provider().install_default()`（:181），用 `let _ =` 吞掉「已经装过」的返回值。
配套声明：`Cargo.toml:48` `reqwest = { version = "0.13", default-features = false, features = ["rustls-no-provider"] }`、
`Cargo.toml:51` `rustls = { version = "0.23", default-features = false, features = ["ring", "std", "tls12"] }`。
选 `ring` 是因为它只需要 cc，Windows 与 NDK 都能编。

代价：`Cargo.toml` 里那两段注释与 `client()` 里那一行 `install_default` 是**永久注释 / 永久行**，删掉即回归崩溃，
而崩溃现象（「输对密码的第一次同步 → 进程没了」）不会让人往 TLS provider 上想。第二道保险在同一函数里：
`Client::builder().build()` 失败**不 panic**，走 `unwrap_or_else(|_| Client::new())` 退回默认 Client
（`md_webdav.rs:186-191`），只丢超时设置、不丢进程。

为什么这条必须写进 ADR 而不是只留代码注释：`src-tauri/src/tests/md_webdav.rs` 里的假服务器全部是
`http://127.0.0.1:<port>` 明文（不碰 TLS），所以**测试全绿也证明不了 provider 装对了**。
崩溃路径只有真机 HTTPS 才走得到，而它的现象是进程消失、没有栈。同理，`probe.rs` 的「测试连接」走的是同一个
`client()`，provider 是全局一次安装，两条路径一起被保护，不存在「测试连接能通、正式同步崩」的错位。

被否方案：`features = ["rustls"]`，一行搞定，但拉 `aws-lc-rs`——构建环境里没有 cmake / NASM 就直接编不过，
这属于「用一个装不上的依赖换一行配置」。也不采用 `native-tls`：它在 Android 上落到 OpenSSL（要交叉编译好的
libssl），在 Windows 上落到 Schannel，两端行为不一致且各带一份系统依赖，与任务书「不引默认 TLS 栈」相冲。

### 4. 不做 PROPFIND、不做目录列举（有外部硬证据）

外部证据来源：只读参考实现 `remotely-save`。其中 `src/` 为 Apache-2.0，**仅阅读**；`pro/` 为 PolyForm Strict
（Source Available），**未打开、未引用、未派生**；Rust 侧**未复制任何代码**。下面每条都标明出处判据：

1. 坚果云**单次目录列举上限 750 条**：该实现 `src/fsWebdav.ts` 里 `r4.length >= 749` 即中止翻页，其注释引
   `help.jianguoyun.com/?p=2064`。超过 750 条的目录，一次列举拿不全。
2. 坚果云**不支持 infinity PROPFIND**，只能逐层 BFS。也就是「一次列完整个 vault」在这台服务器上根本做不到。
3. 它慢的根因正是这个模式：每次同步先 list 整个 vault，再逐个比时间戳。

决策：`infra/md_webdav.rs` 的公开面只有三个函数——`get`（:114）/ `put`（:130）/ `probe`（:153，200 与 404
都算通）。一次 PROPFIND 都不发，`Depth: infinity` 这个词在代码里不存在（该文件 `:4` 的模块注释把结论写死）。
同步只认「今天 + 已知欠账日期」的文件名：路径由 `md_file::expand_tokens` 直接算得出，不需要先知道远端有什么。

代价：远端新增的文件不会被发现。这与产品语义一致（本地写、云端读），不是漏洞：TimingMD 那份声明为只有
Timing 读写（任务书 §二），若有人在坚果云网页版手写一份 `2026-11-20.md`，我们永远看不见它。要支持
「云端新增也要拉」，必须回到列举，而列举在这台服务器上就是 750 条硬顶 + 逐层 BFS——退化成我们刻意
不移植的那套东西。

被否方案：先列目录再逐个比。除了慢，它还会引入「列表与读取之间的时间窗」这套原本不需要处理的竞态：
列完到读之间，远端可能又被改了一次，于是「有没有变」的判定依据变成一份过期的列表。

### 5. 冲突判定用区块内容基线，不用 mtime

现状事实：WebDAV **没有通用设置 mtime 的办法**。同一参考实现的注释原文是
`mtimeCli = mtimeSvr, // no universal way`——服务端 mtime 由服务端定，客户端写不回去。ADR-042 早就把
「最后写入者胜」从 `sync_binding` 里删了，理由是 `latest_update` 是应用写库的毫秒墙钟、`mtime` 取决于
「谁最后碰过文件」（Obsidian 关闭时补写、**同步盘回写**、一次无改动保存都会把它推后）。加了 WebDAV 之后这个
理由更硬：客户端连 mtime 都设不了，任何基于 mtime 的判定必然失真。这一条可以读成「ADR-042 在 WebDAV 场景下
被一个外部实现独立验证」。

决策：沿用既有 `Runtime.baselines`（`services/md_sync/runtime.rs:28`，key 由 `key(kind, path, heading)` 生成，
读写入口 `runtime.rs:46` / `:50`），比的是**区块内容**，不是时间戳。云端那轮天然按 path 分键：
`<数据根>\md\2026-11-06.md` 与 `<数据根>\md-webdav\2026-11-06.md` 是两条基线，两份落点不互相污染，
不需要为「两份会打架」额外做隔离——这也是「两份日记」这个设计代价最低的部分。

代价：基线只在进程内存里，重启后第一轮对两份落点都按「无可比基线」处理（既有行为，非本轮引入）。
另一个代价是基线必须由「程序刚写出去的内容」更新：漏一次 `set_baseline`，下一轮就会把程序自己写的内容
误判成外部改动。备份恢复那条链路因此把 `set_baseline` 写成第 ⑧ 步的硬要求（见第 9 条）。

被否方案：mtime + ETag 混合判定。ETag 只回答「PUT 时远端有没有变」这一个问题（`If-Match` 的用途），
它不回答「文件内容与我上次写出的那段区块是否一致」——两个问题混用会让 412 的退让逻辑失去依据。

### 6. 待传队列的唯一欠账判据是 `pending_since`，不是 `last_hash`

现状事实：设计初稿 §2.2 末尾写了「上传失败**不写** `last_hash`」，而同一节冻结的 UPSERT 每次冲突都更新
`last_hash`。两句自相矛盾。实现按 SQL 走，本条是对设计初稿的**明确口径修正**，不留给读者猜。

决策：`pending_since > 0` 是**唯一**欠账判据（`repositories/md_cloud_pending.rs:70`
`WHERE pending_since > 0 ORDER BY date ASC`）；`last_hash` 只回答「内容有没有变」
（`services/md_cloud/pending.rs::record_if_changed`）；`mark_pending` 的 `ON CONFLICT` 保证 `pending_since`
一旦非 0 就不被覆盖（`repositories/md_cloud_pending.rs:84-89`：`CASE WHEN pending_since = 0 THEN excluded
ELSE pending_since END`）。于是上传失败后 `pending_since` 留着，下一轮 `push_history` 照旧补传——
自愈是 SQL 的不变式，不靠调用方记性（调用方那层「先读再判再写」中间任何一条早退分支都会把欠账时间刷成当下）。

代价：`last_hash` 会记录「一份从未成功上传过的内容」，它不再承担「上次成功同步的内容」这个语义，名字略有
误导。换来的是 `pending_since` 单一职责。用时间戳而不是布尔列，是因为它同时承担「欠了多久」的诊断价值
（`md cloud: pending=[…]` 那行日志与设置页 `pendingDates` 都从它来）。

被否方案一：加 `dirty` 布尔列，与 `pending_since` 语义重复且要再改一次迁移。被否方案二：把队列塞进
`settings` 的 JSON——那是一整块读写，多端并发会丢更新（任务书 §4.2 明文禁止）。

验收口径落在这三态上（任务书 §七-5，`src-tauri/src/tests/md_cloud_pending.rs`）：`mark_pending` 后表里有行且
`pending_since > 0`；`mark_synced` 后 `pending_since = 0` 且 `etag` / `last_hash` 一起更新；**连续两次
`mark_pending` 后 `pending_since` 保持第一次的值**。第三态就是「不重置」的机器证据——它保证欠账时间戳记的是
「第一次发现没传成功」，而不是「最后一次尝试」。另外 `md_cloud_pending.date` 与文件模板的 `{date}` 同源，
一律本地时区 `%Y-%m-%d`（`services/md_cloud/mod.rs::today`，`chrono::Local`），不允许出现 UTC 日期：
否则晚上 8 点之后「今天」会变成明天，那一天的欠账会被永远跳过。

### 7. 备份归属用「落点根 → 标识」注册表，且 `restore` 绝不登记根

现状事实：`infra/md_backup::save(source, text)`（:115）只拿路径，不知道这份内容属于哪个落点；而
`md_file::write_section` 在改这条链路之前的唯一调用方是 `sync_binding`（`md_sync/mod.rs:259`），改签名就撞
300 行红线（`md_file.rs` 261 行、`md_sync/mod.rs` 300 行都动不得）；恢复链路要写文件，只能复用同一个
`write_section`（`services/md_backup.rs:113` / `:120`），于是它也不能有「落点」参数。两个落点下同名的
`2026-11-06.md` 落在同一个备份目录里，用户看不出哪一份能恢复哪个落点。

决策：`register_root(dir, tag)` 幂等注册表（`infra/md_backup.rs:57`），标识白名单
`TAGS = ["obsidian", "webdav", "folder"]` 在 `infra/md_backup_store.rs:27`；`tag_of(source)` 按**路径分量数**
做最长前缀匹配（`tag_in`，`Path::starts_with` 按分量比较，`...\md-webdav` 不会被当成 `...\md` 的子目录）。
`save` 签名与 `md_file` **零改动**，只在 `save_to` 里拼文件名
`<tag>__<sanitize(stem)>-<yyyyMMdd-HHmmss>.md`。注册点只有三处：`app/bootstrap.rs:77`
（`data_root.join("md")` → `obsidian`）、`services/md_cloud/round_webdav.rs:171`（→ `webdav`）、
`round_folder.rs:34`（→ `folder`），且必须在云端那轮**之前**登记——登记晚了，本轮的备份就会标成 `obsidian`。
老备份 `parse_name` 返回 `Some((None, stem))` → 列表标「归属未知」，**不删、不改名**；`prune` 只按 mtime
计 `KEEP = 30`（`infra/md_backup.rs:48`），完全不认名字。

**实现期关键发现（必须留在这里）**：`services/md_backup::restore` **绝不调用 `register_root`**。它有 fallback
路径——`root_of`（`services/md_backup.rs:152`）在云端未启用 / 解析失败时退回 binding 自己的根，而那条
fallback 指向的正是 Obsidian 目录。在那里登记会把 Obsidian 目录**错标成 `webdav`**：此后所有 Obsidian 备份
都带 `webdav__` 前缀，恢复时再按前缀反推目标 → 用户点「恢复 webdav 那份」，实际覆盖的是 Obsidian 目录。
登记是 `round` 的职责，恢复只**读**注册表。这条可机器断言：`grep -rn "register_root" src-tauri/src` 现在
命中 `app/bootstrap.rs`、`infra/md_backup.rs`（定义处）、`services/md_cloud/{round_webdav,round_folder}.rs`
与测试，`services/md_backup.rs` 里一处都没有。

代价：为了行数，读侧拆成 `infra/md_backup_store.rs`（152 行），`md_backup.rs` 248 行，由 `md_backup` 里
`pub use` 转发 `list` / `read` / `parse_name` / `BackupFile`，对外路径不变。设计定稿预估「`md_backup.rs`
169 → 295 行、只剩 5 行余量」，实现选择了拆文件而不是贴线。

被否方案：「进程内当前落点标记」（一个 `static` 变量，跑云端那轮前置位、跑完复位）。要配 RAII 守卫才能
勉强等价，且存在「panic 后没复位 → 之后所有备份全标错」的窗口（与 ADR-053 里 `Gate` 那类问题同源）。
注册表是幂等的，没有这个窗口。

### 8. 新增 1 个错误码 `MD_SYNC_REMOTE_ERROR`，云端不新增任何事件

现状事实：契约当前是 **71 命令 / 16 错误码 / 11 事件**（`node scripts/check-contract.mjs` 实测输出）。本轮加
3 条命令（`md_sync_test` / `md_backup_list` / `md_backup_restore`）→ **74**。远端错误若复用 `IO_ERROR`，
「网络不通，稍后自动重试」与「本地文件打不开」在界面上就是同一句话，而这两件事的处理方式完全相反
（等 vs 修文件）。

决策：错误码 16 → **17**。`error.rs` 加 `ErrorCode::MdSyncRemoteError` + `as_str()` = `"MD_SYNC_REMOTE_ERROR"`
+ `AppError::md_sync_remote_error(msg)`；前端 `types/domain/models.ts::ErrorCode` 与 `services/ipc.ts::errorText()`
同步，`errorText` 对这条**原样透出 `err.message`**（与 `MD_SYNC_CONFIG_INVALID` 同做法），因为后端已经把
401 / 403 / 429 / 超时翻译成人话（`round_push::fail_text`，`round_push.rs:46`）。
事件面 **11 → 11，一条不加**：云端一轮的结果复用既有 `md-sync:changed`（`MdSyncReport` 载荷不变），
因为「云端同步完」与「本地同步完」对前端是同一件事（刷新 store）。加事件就得让每个消费者为同一件事
写两遍处理函数，而两边载荷一模一样。

代价：`md-sync:changed` 的语义从「本地一轮完成」拓宽成「任一路径完成一轮」，文档口径要跟着改。
为了让「一整天 401 在界面上完全无声」不再发生，`md_cloud::tick`（`services/md_cloud/mod.rs:80`）把
「值得广播」的判据从 `report.touched()` 扩成三项：`touched() || !errors.is_empty() || pending 清单变了`。
这是**行为变化**，记在这里以免以后被当成噪音清理掉。

被否方案一：复用 `IO_ERROR`（任务书 §4.9 明文否掉）。被否方案二：为云端新增 `md-cloud:changed`
（前端会把同一次刷新写两遍）。被否方案三：不设错误码，只把远端错误塞进 `report.errors`——那样设置页拿不到
「这一轮失败是因为网络还是因为密码」，用户只能看到一句笼统的「同步失败」。

3 条新命令按既有「五处对齐」办：`lib.rs` 的 `generate_handler!`、`types/domain/ipc.ts` 的 `IpcApi`、
`services/ipc.ts` 的 `call()` + 方法、mock 的处理器、以及桌面与移动**两份同名实现**。移动端两条备份命令
不做功能、只回一句明确的 `IO_ERROR`（「手机端暂不支持，请在电脑上恢复」）——不许「只在桌面注册」，
那会让 `check:contract` 的四路计数立刻红（Rust / IpcApi / ipc.ts / mock 必须都是 74）。

### 9. 备份恢复是「强制导入」，与同步的冲突判定是两套语义

现状事实：恢复不是合并。用户在设置页点「恢复」，意思是「把这份覆盖回去」；三方判定（基线 / 文件 / SQL）
在这里没有意义——它会让「我就是要回到昨天那份」被基线拦住。而 `sync_all` 内部要拿
`md_sync::runtime::lock()`，`tokio::sync::Mutex` 不可重入。

决策：`services/md_backup::restore`（:57）全程持 `md_sync::runtime::lock()`（:95 取锁，:128 `drop(rt)`），
**锁内不许调 `sync_all`**（它自己也拿这把锁 → 死锁）。与 15 分钟轮询天然互斥：恢复期间轮询拿不到锁。
锁内八步：

① 解析备份名 → `(归属, 来源文件名)` → 日期；解析不出 → `MD_SYNC_CONFIG_INVALID`
② 读备份全文（拿锁**之前**读完，早失败早返回）
③ 按解析后的**绝对路径**分组：三个 kind 常落同一个 `{date}.md`，一个文件只算一次 `written`；
相对路径直接拒绝，否则 `create_dir_all` 会写到进程 CWD
④ `md_file::read_section` 读当前（坏）内容
⑤ `md_file::write_section` 写回备份区块——**写前留底在这一步自动发生**
⑥ `import::by_kind(pool, kind, date, body_old, body_backup)` 强制覆盖、无冲突判定
⑦ `export::by_kind` 重渲染后再 `write_section`：导入会规范化时间格式与分组顺序，文件必须与库一致，
否则下一轮同步立刻又判「文件变了」
⑧ `rt.set_baseline(...)`：基线跟上，下一轮不把程序自己写的内容当外部改动

调的是 `import::by_kind` / `export::by_kind`（都吃 `date` 参数），所以**历史日期也能恢复**，且整条链路不碰
`sync_all`。`effective == Some("webdav")` 时结尾 `mark_pending`（:130-137），下一轮把回滚结果也传上去。

代价 / 承诺：「恢复本身不会再丢一次」是真的，可以照任务书 §4.4-4 写进确认文案——第 ⑤ 步之前
`write_section` 已经把当前坏内容留了一份底。

**实现期补充（必须写）**：备份里没有某个标题时**跳过该 binding**（`services/md_backup.rs:100-105`，
`log_warn` + `continue`），不 append 空区块。append 会追加一个空标题，接着 `import` 按「old 有、new 没有」
把该种类行**全部软删**——那比跳过坏得多。这是「恢复反而破坏数据」的唯一入口。

被否方案：让 `restore` 走 `sync_all`（先写文件再跑一轮普通同步）。会被基线拦成「文件变了」→ 走导入 →
看起来能用，但语义变成「把备份当成外部改动」，而且必须在锁内调 `sync_all`（死锁）。

## Consequences

正面：

- **合并逻辑全库唯一一份**。`mirror::run_in` 的调用方从 1 处（`app/md_sync_mobile.rs:121`）变成 3 处
  （+ `round_webdav.rs:130`、`round_folder.rs:45`），合并代码一行没加；「两份落点」是同一段逻辑跑两遍，
  不是两套逻辑。
- **三个文件零改动可机器断言**：`services/md_sync/mod.rs`（300 行）、`infra/md_file.rs`、
  `models/md_sync.rs` 的 `git diff` 均为空（`git diff --stat` 里不出现它们）。
- **离线可写**：文件先落本地（`round_folder` 这条路上连网络代码都没有），云端传不上去由 `pending_since`
  兜底，下一轮自愈。离线时用户照常在 Obsidian 里记，没有任何功能被网络拖住。
- **手机端与桌面共用同一套编排**：`services::md_cloud::round` 是唯一入口，`app/md_sync_mobile.rs:147`
  调 `tick`，`app/tray_sync.rs:99` 与 `jobs/md_sync.rs:35` 也是。两端不存在「手机版行为略不同」的分叉。
- **备份闭环**：留底功能存在了四个月却只能写不能读，本轮补上读回与恢复。

代价：

- 两份落点各写一次备份，`KEEP = 30` 的回看窗口大约减半（从 30 份缩到「每个落点 15 份左右」）。
  本轮**不改**（任务书没要求，改它是未申报的行为变更），建议 v0.11.14 提到 60。
- 不做 PROPFIND 意味着「云端新增的文件」永远不可见（第 4 条）。这是刻意买的。
- `rustls-no-provider` 的 provider 安装是「删掉即崩」的隐式契约：`Cargo.toml` 的两段注释与
  `md_webdav.rs:181` 那一行必须一起活到换 provider 的那天。
- `md-sync:changed` 的语义被拓宽（第 8 条），前端不能假设「收到它就说明本地落点有变化」。
- `tick` 的广播判据多了「有 errors」一条 → 一整天连不上时会每 15 分钟发一条事件（设置页显示
  `lastError`）。比过去「完全无声」吵，但那是修「一整天 401 界面无感」的代价。

遗留：

- **Kotlin 侧未编译验证**：`gen/android/.../native/SecretStore.kt`（107 行）与 `TimingNativePlugin.kt` 的
  三条原生命令（`secretPut` / `secretGet` / `secretClear`）在 Windows 上编不到，只有 Android 构建才会暴露。
  ADR-055（`invoke.getArgs()` 取参）与 ADR-056（返回值只许 `JSObject`）是照着写的，但没有编译器背书。
- **`TimingNativePlugin.kt` 已 349 行**（改前 301）。注意 `scripts/check-size.mjs` 的 `EXT` 只有
  `.ts / .tsx / .css / .rs`，**门禁扫不到 `.kt`**——这条只能靠人守。拆分留 v0.11.14。
- **契约面未落地**：74 命令 / 17 错误码 / 五处对齐属 T04，`check-contract` 当前仍输出 71 / 16 / 11。
  `docs/phase2/IPC-CONTRACT-v2.md`、`types/domain/{ipc,models}.ts`、`services/ipc.ts`、两份 mock 与两份
  命令实现要一起改，否则本 ADR 第 8 节描述的是「已冻结的口径」而不是「现状」。
- 手机端备份恢复仍不做：手机落点是 `content://` 树，恢复要写回 SAF，属独立一轮（任务书 §4.4-5）。
