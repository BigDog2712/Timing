# ADR-062：WebDAV 目录补建内建于 infra、数据根改为可配指针

## Status

Accepted（v0.11.15 落地）

落地范围：`infra/md_webdav/`（拆 `mod.rs` + `dir.rs`，新增 MKCOL 整套）、`services/md_cloud/`
（`fail_text` 带路径、`probe::test_webdav` 两关）、`infra/root_pointer.rs`、`infra/disk_space.rs`、
`app/data_root_boot.rs`、`services/data_root/`（预检 / `VACUUM INTO` / 五表核对）、4 条新命令、
前端五块重组。

验收口径：`cargo test --lib` 465 → **492 passed**；前端 **50 files / 385 tests**；`check:size` 546 文件
零豁免；`check:contract` **78 / 17 / 11**（命令 +4，错误码与事件零变更）；`cargo clippy -D warnings`
0 warning；`cargo check --target aarch64-linux-android` 0 error。

## Background

主人报的两件事（原话见 `07-PRD-v0.11.15`）里，第一件是「WebDAV 服务返回 409，稍后自动重试，
webdav 未成功连接」。核实后病根不在凭据：

| 事实 | 后果 |
|---|---|
| `put()` 直接 PUT 完整 URL，**全仓无任何 MKCOL** | 远端目录不存在时服务端按 RFC 4918 回 409 |
| 远端相对路径恒为扁平的 `{date}.md`（三处） | 缺的不是子目录，而是配置的 `basePath` 本身 |
| `fail_on_status` 把 409 归到 `Server(409)` | 文案只有「稍后自动重试」，每轮重复、永不自愈 |
| `probe` 把 **404 判成 Reachable** | 「测试连接」绿字，保存后必 409 |

第二件事是设置页「逻辑有问题」：一个页签堆六段，且「改名格式」与「放哪个目录」混在同一张卡里。
要放第七段（SQLite 落点）已经没有位置。

## Decision

### 1. 目录补建内建于 `infra::md_webdav::put`，不散落在编排层

`send_put` 收 409 → `dir::ensure_base_dir` 逐级 MKCOL → **重试一次**。三条理由：

1. RFC 4918 里 `PUT → 409` 只有**一个**成因（父集合不存在），补建后重试一次是 HTTP 语义的一部分，
   不是业务策略；
2. 调用点有**三处**（`round_push::push_today`、`push_history`、`round_conflict` 的 412 重试），
   放编排层要写三遍，漏一处就是「补传成功、今天失败」这种极难复现的错；
3. 第一级建出来后，同轮后续 PUT 不会再 409，天然只有一次级联，不需要穿参数、不需要每轮状态机。

### 2. MKCOL 用独立 Client，**禁止跟随重定向**

reqwest 对 301/302/303 会把请求方法**改成 GET**（它按浏览器语义处理）。不禁跟随，一次「要求补尾
斜杠」的 MKCOL 就变成 `GET <dir>`，返回 200/404 之后我们既不知道到底建没建，日志也全是假的。
所以 MKCOL 走 `redirect(none)` 的 Client，**3xx 一律当「已存在」**——这是唯一说得清的判据。
GET / PUT 的 Client 保持默认（`probe` 依赖它把 3xx 走完）。

### 3. 逐级建、最多 8 级、幂等、失败不回滚

- 浅 → 深，顺序不可换（每级父级必须先存在）；`201/200/204` 算建成，`405`/`3xx` 视为已存在。
- `MAX_LEVELS = 8`，超过**一个请求都不发**（`EnsureOutcome::TooDeep`），由调用方决定怎么说：
  `put` 里降级成 `Server(409)`（PUT 确实是 409，不改写本义），「测试连接」里说人话。
- **失败不回滚、不删远端任何东西**。远端 `DELETE` 不可撤销，为了「干净」去删用户网盘里的目录，
  风险远大于留下一个空目录——而且那个空目录正是下一轮成功所需。这条写进模块头注释。

### 4. `WebdavError` 不加变体，四类失败只改文案

MKCOL 的四类失败（405/3xx、403、400、兜底）在**致命性与退避判据上与既有变体完全一致**，差的只有
文案。加变体等于让 `fatal()` 多一条永远走不到的分支。

`fail_text(err, remote_dir)` 加路径参数（8 个调用点同步）：三类可诊断失败各给一句能照做的话并**带出
用户填的路径**；其余 4xx/5xx 走兜底句且**不带状态码**（状态码对用户零信息量，只进日志）。
用例用 `\b\d{3}\b` 断言四类文案零命中。

代价记账：`Server(5xx)` 那句「稍后自动重试」被替换掉了。退避行为不变，只是不再向用户承诺时间。

### 5. 「测试连接」= 地址凭据 + 目录就绪，两关都过才绿字

旧版只做 `probe`，于是「绿字、保存后必 409」——绿字必须等于**真的能写**。现在 `probe` 之后调
`ensure_base_dir`，绿字里写明「已就绪」或「已补建 n 级」。`probe` 自己的三档语义（200/404 通、
405/3xx 通但读不了目录、其余错）**保持 V0.11.14 修 O8 时的样子不动**。

### 6. 数据根用「指针文件」，位置必须在数据根被决定之前可读

`%APPDATA%\<identifier>\data-root.json`，与 `portable-optout.json` 同目录。放数据根里等于
「要先知道答案才能读到答案」。启动优先级：

```
① 指针（可读 + 目录可写）> ② portable-optout.json > ③ 探测 <exe>\data
```

- 指针生效时**不搬数据、不弹迁移框**：数据是用户在界面里自己选、自己确认复制过去的，启动期再搬
  一次就成了「悄悄搬第二遍」。
- 坏 JSON / 读不出 → **当不存在**（一个被编辑器改坏的文件不能永久卡住启动）。
- 指针目录不可写 → 阻塞对话框三选一；选「这次按默认流程」时**指针保留**（下次启动仍先试它）。
- 指针生效时顺手调一次 `move_plugins`：正常顺序下早搬完了，但若那次失败，跳过整个 ③ 分支会让
  用户「插件全都不见了」而没有任何日志。

### 7. 库复制只走 `VACUUM INTO`，核对五张表行数之后才切指针

直接拷 `timing.db` + `-wal` + `-shm` 是**两个时刻的快照拼在一起**：主文件与 wal 可能撕裂，只拷主
文件又会丢掉 wal 里未 checkpoint 的数据。`VACUUM INTO` 由 SQLite 在一个读事务里生成一致副本、产物
单文件无 WAL。

核对清单是**用户数据的五张表**（`items` / `time_records` / `notes` / `todos` / `settings`）；
`md_cloud_pending` 不在其中——它是同步簿记，丢了下一轮会自己重建，但它**会被 `VACUUM INTO` 一起
带过去**，所以这份清单只用于「核对搬运结果」，不是「复制清单」。

核对不过 → 不写指针、返回 Err、在目标目录写 `MIGRATION-INCOMPLETE.txt`。

### 8. 页签 `id` 不改，手机端本轮只改 label

`id: 'sync'` 保留：它是 `aria-controls` / 条件渲染 / `TabId` 联合类型的内部标识，改名对用户零收益
却牵动模板串与断言。手机端本轮**只改`TABS` 的 label 一行**，`SyncPane` 结构与字段可编辑性一字不动
——缩减手机端既有编辑能力属于擅自减功能，留待单独一轮评审。

## Consequences

- 「绿字 = 真的能写」成为可断言的契约：以后任何让 `probe` 重新变「宽松」的改动都会被
  `md_webdav_dir` 的用例拦下。
- 远端会留下「建了一半」的目录（最多 8 级、只增不删）。这是刻意的：宁可留空目录，不删用户网盘。
- 数据根切换是**唯一会写两处配置**的动作（数据根指针 + 页面里的落点 refs）。旧目录不删、可撤销、
  重启才生效，三件事一起构成回滚路径。
- 新增 4 条命令后，`check:contract` 的四处（`generate_handler!` / `IpcApi` / `call<T>` / mock）
  必须同步；这是契约面扩张的固定成本，本轮逐条记账为 74 → 78。
- 「恢复云端备份后自动排补传」那条链路**仍然无自动化测试**：走它必须把 `%APP_DIR%` 指到临时目录，
  而那个路径被定成「永不读环境变量」。加可注入点等于为一条测试改生产路径语义，本轮判断不划算，
  留 v0.11.16。
