# ADR-047：Markdown 同步从插件内核化（`mdSync` 在 apiVersion 3 下架，契约数字不变）

## Status

Accepted（2026-11-06，V0.11.5；用户口径「删掉 `plugins/md-sync` 目录，同步只归内核」）

## Background

Markdown 双向同步从 V0.4.0 起是「插件声明 + 宿主执行」的形态（ADR-033）：
落点默认值放在仓库内 `plugins/md-sync/plugin.json` 的 `contributes.mdSync.bindings`，
`services/md_sync/config.rs::load()` 扫插件目录、找 `id == "md-sync"` 且启用且声明了
`mdSync` 的那一条，把它的 `bindings` 当作默认值。

**但真正的逻辑一直不在插件里。** 导出、导入、冲突判定、轮询、文件区块读写全部在
`services/md_sync/` 与 `infra/md_file.rs`；插件提供的那几行 JSON 里**只有数据**
（kind / enabled / root / file / heading），没有一行代码。声明式边界（ADR-015/ADR-033）
本来就是这么设计的，现在这条设计反噬出三个代价：

1. **插件目录没了 = 同步整体失效。** `load()` 找不到那个插件就回 `enabled: false`，
   轮询任务空转，用户辛苦配好的 `settings` 保存值一条也用不上。
2. **设置页必须解释一个不该存在的状态。** `MdSyncView` 带 `installed` / `pluginId` /
   `pluginName` / `pluginVersion` 四个字段，设置页据此显示「插件：Markdown 同步 v1.0.0」，
   并在找不到插件时打出「未检测到声明 mdSync 的插件」的告警——而这是一个**内核功能**，
   「插件没装」不该是它失效的理由。
3. **默认值是可被用户删掉的文件。** 用户清理 `%APPDATA%\com.timing.app\plugins` 时
   不会想到自己顺手关掉了一个同步功能；这条依赖不体现在任何界面上。

换句话说：这段插件只是把一份常量表从 Rust 搬到了 JSON 里，代价是多了一条
「文件存在性」的启动依赖和一个假的「未安装」状态。V0.11.5 把它收回内核。

## Decision

### 1. 默认落点写进内核

`src-tauri/src/models/md_sync_config.rs` 新增：

```rust
pub const MD_SYNC_DEFAULT_ROOT: &str = r"%USERPROFILE%\Documents\Timing";
pub const MD_SYNC_DEFAULT_FILE: &str = "{date}.md";

/// 出厂三档落点。唯一默认值来源——「按 kind 补齐」也用它。
pub fn default_bindings() -> Vec<MdSyncBinding>
```

三档固定：`timers` / `notes` / `todos`，`enabled` 均为 `true`，
`heading = format!("#### {}", kind.label())`（即 `#### 事项计时` / `#### 便利贴` /
`#### 待办事项`）。**标题走 `kind.label()`，不手抄字符串**——手抄的话，将来改一个
显示名就会让设置页卡片与文件里的标题分叉。

放 `md_sync_config.rs` 而不是 `md_sync.rs` 的三条理由：

| 理由 | 依据 |
|---|---|
| 语义归属 | 默认落点就是 `MdSyncConfig` 的出厂值，`impl Default` 就在这个文件；放这里才能让 `bindings: default_bindings()` 成为**唯一**默认口径 |
| 300 行门禁 | `md_sync.rs` 已 256 行，再塞 3×5 行常量表 + 注释逼近上限，而 `scripts/size-allowlist.json` 当前**为空**（零豁免额度，不许开） |
| 分层不重叠 | `md_sync.rs` 只放「数据形状 + 静态校验」，配置 / 出厂值 / 合并归 `md_sync_config.rs` |

### 2. 删除插件、下架贡献点

- 删除 `plugins/md-sync/`（`plugin.json` + `README.md`）。删完 `plugins/` 成为空目录，
  git 不留空目录 → `infra/plugin_fs.rs` 的 dev 扫描根不存在；`scan()` 里
  `let Ok(entries) = read_dir(&root) else { continue }` 已经吃掉这种情况，**不改代码**。
- `PLUGIN_API_VERSION` 2 → **3**；`PluginContributes.md_sync` 的类型从
  `Option<MdSyncContribution>` 改为 `Option<serde_json::Value>`（字段名保留，`rename_all`
  仍渲染成 `mdSync`），删除 `MdSyncContribution` 结构体。
  选 `serde_json::Value` 是刻意的：宿主**要能看见它存在**（据此给警告），
  但**不解析它的内容**——解析就等于还在支持。
- `infra/plugin_fs.rs` 删除 `validate()` 里整个 mdSync 校验分支，新增独立函数
  `pub fn warnings(manifest: &PluginManifest) -> Vec<String>`，`read_manifest` 返回
  `Result<(PluginManifest, Vec<String>), String>`。
  **`validate()` 的签名不动**（仍是 `Result<(), String>`）：`plugin_fs_test.rs` 有十几个
  `validate(&manifest)` 断言，把警告混进校验返回值会连带重写一堆无关测试。

### 3. `MdSyncView` 收敛为三个字段

删掉 `installed` / `pluginId` / `pluginName` / `pluginVersion`，只留
`today` / `config` / `status`。

**不加「配置来源」标识**：内核化以后来源恒等于「内核」，一个只有唯一值的字段是死重量。
`services::md_sync::config::Loaded` 结构体随之删除，`load()` 直接返回 `MdSyncConfig`，
`config::load` / `poll_secs` / `get_view` / `run` / `tick` / `open` / `sync_all` 全部
去掉不再需要的 `app_data_dir` 参数——`services/md_sync` 从此**不碰插件目录**。

### 4. 配置键 `plugin.md-sync.config` 不改名

带 `plugin` 前缀是 V0.4.0 的历史原因，但**不改**：改名要做「读新键 → 无则读旧键 →
写新键 → 删旧键」，而 `settings` 是 KV，没有迁移框架，双读逻辑会长期留在 `load()` 里；
漏掉任何一步，用户配好的 OneDrive 路径就会被内置默认值整体覆盖。收益是「名字好看」，
而这个键用户根本看不到。**用真实数据丢失风险换零收益，不做。**

### 5. 保留「按 kind 补齐」的合并语义

合并规则**一个字不改**，只把 `defaults` 的来源从插件换成 `default_bindings()`：

- 保存值存在 → 总开关与 `poll_secs` 用保存值；`bindings = merge_bindings(saved, default_bindings())`，
  saved 的顺序与内容不动，**saved 里完全没有的 kind 追加在后面**；
- 保存值不存在或解析失败 → `MdSyncConfig::default()`。

**为什么还要补**：设置页只渲染 `config.bindings`，没有「添加落点」入口。不补的话，
保存值只有 `timers + notes` 的老用户永远拿不到 `todos`，功能只对新装用户开放
（这个坑 ADR-033 之后已经踩过一次，`tests/md_sync_upgrade.rs` 就是它的守门人，
本轮必须改成断言「内核默认值补齐」，不能删）。

**防复活的判据**：合并**只按 `kind` 匹配、不看 `enabled`**。用户主动禁用一个落点只写
`enabled: false`、不删条目，所以该 kind 仍在保存值里，默认值补不回来。
这条由 `a_disabled_binding_is_not_resurrected` 单测咬死，本轮保留。

### 6. `enabled` 出厂默认改为 **false**

`impl Default for MdSyncConfig` 的 `enabled` 由 `true` 改 `false`，
`#[serde(default = "default_true")]` 同步改为 `#[serde(default)]`（两处一起改，
否则「JSON 缺 `enabled`」与 `Default::default()` 的口径会分叉）。

三条判据：

1. **首次运行零文件 IO**：`sync_all` 的第一道闸就是 `enabled`，关着就不会建目录、
   不会往 `文档\Timing` 写第一个 `.md`；
2. **默认开在插件时代是合理的，内核化后不是**：「装了插件」本身是一次明确动作，
   而内核功能对所有用户默认存在——默认开等于替所有用户决定往文档目录里写文件；
3. **只影响从没有保存值的人**：老用户保存值里 `enabled: true` 原样保留，升级不改变行为。

### 7. 契约数字一条不变

命令 **67** / 事件 **11** / 错误码 **16** 全部不变：4 条 `md_sync_*` 命令一条不减
（变的只是返回值里少了四个字段），不新增事件，不新增错误码。
`scripts/check-contract.mjs` 只做**交叉一致性**（handler ↔ `IpcApi` ↔ `ipc.ts` ↔ `browserMock`、
错误码两侧、错误码 ↔ `errorText()` case、事件三方、禁字面量 emit），
**不校验字段形状、不解析 Markdown、不比对固定数字** —— 所以字段增删不会让它变红。
本轮会红的是 `typecheck`（`MdSyncView` 少四个字段后 mock 与 fixture 对不上），这是预期的中间态。

## Alternatives

| 方案 | 否决原因 |
|---|---|
| 保留 `plugins/md-sync` 当「官方插件」 | 「内置功能靠用户目录里的一个文件活着」这个形态本身就是错的：用户清理插件目录会静默关掉同步，而界面上看不出因果 |
| 把 `mdSync` 保留为 apiVersion 3 的贡献点，内核默认值与插件值并存 | 两套默认值必然打架（谁赢？按 kind 合并顺序？），而插件这条路带来的唯一能力是「第三方预设一套落点」——设置页已经能改，收益为零 |
| 配置键改名 `md-sync.config` | 见 Decision 4：双读迁移的每一步都是数据丢失风险，收益仅是键名好看 |
| 不补 kind（保存值整体优先） | 老用户永远拿不到 `todos`，且设置页没有「添加落点」入口，等于新功能只对新装用户开放 |
| `enabled` 保持默认开 | 新装用户首次启动就在 `文档\Timing` 里创建目录与日记，且没有任何界面提示；未经同意的磁盘副作用 |
| 顺手把 `plugin_fs::validate` 改成 `Result<Vec<String>, String>` | 校验与警告混在一个返回值里，`plugin_fs_test.rs` 十几个无关断言要重写；警告走独立函数更稳 |
| 删掉 `tests/plugin_dev.rs` 之外，再补一个「内核默认值」专项测试文件 | `tests/md_sync_upgrade.rs` 已经完整覆盖补齐 / 不复活两条语义，再加文件只是重复 |

## Consequences

- **v2 插件里写 `contributes.mdSync` → 忽略并警告，不拒载。** 设置 → 插件 该行显示黄字：
  「声明了已下架的贡献点 mdSync（apiVersion 3 起改由内核实现）。插件仍正常生效；
  Markdown 同步请在 设置 → 同步 里配置。」插件仍标为生效（`warnings` 不参与启停，
  `PluginInfo::active_quick_timers()` 只看 `error`）。
  选忽略而非拒载的理由：同步逻辑本来就在宿主，插件里只是数据；为一个作废的贡献点让
  **整个插件**失效，惩罚大于过错。而 `entry` / `apiVersion` 这类「宿主必须解释其语义才能运行」
  的字段仍然拒载——「宁缺毋滥」只约束后者。
- **`PluginInfo` 新增 `warnings: Vec<String>`**：`error` = 红字 + 不生效，
  `warnings` = 黄字 + 仍生效，两个视觉层级不合并。
- **老用户保存值完全不受影响**：`enabled` / `poll_secs` / 落点内容按保存值走，
  只把缺的 kind 补齐。配置键不变，所以不需要任何迁移。
- **`tests/plugin_dev.rs` 删除**（含 `tests/mod.rs` 的 `mod plugin_dev;`）：
  它唯一的用途就是断言仓库内 `plugins/md-sync` 被 dev 扫描根读到并声明了 `mdSync`，
  被测对象已不存在。`tests/appdata_migrate.rs` **不用改**——它只拿
  `plugins/md-sync/plugin.json` 当一个「随便什么文件」验证数据目录搬迁。
- **`tests/md_sync_upgrade.rs` 的行为不变但措辞要改**：`..._from_the_plugin` →
  `..._from_the_kernel`，这是本轮最重要的回归——它是「只对新装用户可用」那个坑的守门人。
- **`services/md_sync` 不再依赖插件域**：`infra/plugin_fs.rs` 也不再 `use crate::models::md_sync`
  （此前它为了校验 mdSync 配置反向依赖了同步域模型），插件域与同步域从此无耦合。
- **v3 起 `mdSync` 只是历史**：`docs/plugin-spec.md` §5 标注「v2 起 · v3 下架」，
  内容作为 v2 历史规格保留；v3 的权威口径在 §10。

> 正文以本文为准；插件侧契约见 `docs/plugin-spec.md` §5 与 §10。
