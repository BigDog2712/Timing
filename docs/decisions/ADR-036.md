# ADR-036：品牌回归 Timing（`TickBar` 是重写期的工程代号）

## Status

Accepted（2026-11-04，V0.5.0）

## Background

本仓库的产品显示名、包名、identifier、crate 名在 0.2.0 起一直写作 `TickBar`。
但 `TickBar` 从来不是产品的目标名字，而是**重写期的工程代号**：

1. **上游对等物叫 Timing。** 本工程存在的理由是「把 macOS/Windows 上的 Timing v1.7.3
   做到 Windows 上一模一样地好用」。功能边界由 `docs/timing-1.7.3-parity.md` 的验收矩阵
   钉死；视觉与几何常量由 `docs/design/TIMING-DELTA-AUDIT.md` 逐项对齐（该审计的权威源是
   `Timing_v1.7.0/src/ElioTimer.Ui/`，C#/GDI 自绘，常量即规格）。**两份文档通篇都在说
   「Timing 权威值 vs 本项目现值」**——名字和它对不上，等于每读一次都要在脑子里换一次名。
2. **仓库本来就叫 Timing。** GitHub 仓库是 `BigDog2712/Timing_Rust`，工作目录是
   `261102-Timing`。「产品叫 TickBar、仓库叫 Timing」这个错位从第一天就存在。
3. **0.2.0 的交付概览自己写着这是临时名。** `docs/overview-V0.2.0.md` 与
   `docs/archive/v1/phase1/ARCHITECTURE-v1.md` 里都留有「（暂定名）」「工作名 TickBar」
   的字样——当时没人认为它是最终名。

0.4.x 之前不改名的唯一理由是**代价**：改 identifier 会让老用户的数据目录「消失」
（新目录里没有库，应用以空库启动），而 0.5.0 之前没有迁移能力。现在迁移已经上线并验证
（ADR-037 / `docs/rename-v0.5.0/PRD.md` §4），代价被消掉了。

## Decision

**用户可见身份统一改为 `Timing`**，一次性切完，不留半改名状态：

| 面 | 旧值 | 新值 |
|---|---|---|
| 显示名 / 安装产物 / 窗口标题 / 托盘 | `TickBar` | `Timing` |
| npm 包 | `tickbar` | `timing` |
| identifier | `com.tickbar.app` | `com.timing.app` |
| Rust crate / lib | `tickbar` / `tickbar_lib` | `timing` / `timing_lib` |
| DB 文件名 | `tickbar.db` | `timing.db`（迁移时映射，含 `-wal` / `-shm`） |
| 安卓包名（Tauri mobile） | `com.tickbar.app` | `com.timing.app` |
| 日志文件名 / 级别变量 | `tickbar-*.log` / `TICKBAR_LOG` | `timing-*.log` / `TIMING_LOG`（旧名回落一个版本 + WARN） |
| 编译期平台常量 | `__TICKBAR_MOBILE__` | `__TIMING_MOBILE__` |

### 1. 老数据怎么处理

**只复制、不移动**：迁移把 `%APPDATA%\com.tickbar.app` 整棵树复制到 `com.timing.app`，
老目录一字节不动并**永久保留**。回滚到 0.4.x 仍能读到全部老数据（M-12 已验证）。
这条是品牌改名能被接受的前提：任何「搬家即删源」的实现都会让改名的风险高于收益。

### 2. 既有 35 篇 ADR 的正文一个字都不改

ADR-001..035 是**当时的决策记录**。把正文里的 `TickBar` 批量替换成 `Timing`，会让历史
决策读起来像「当时就叫 Timing」，等于伪造决策语境（同 `docs/reviews/**` 与
`docs/archive/**` 的处理）。改名这件事本身由本篇（ADR-036）承载；本篇之前的 ADR 一律
按原样读，其中的 `TickBar` 请理解为本项目的旧名。

### 3. 不新增错误码、不改 schema

品牌层是「名字」的变更：命令 **65 → 67**（新增的 2 条是迁移可见性，见 ADR-037，与品牌
无关）、错误码 **16 不变**、事件 **11 不变**、DB schema **v4 不变**。把改名做成「顺手
改契约」是这类变更最常见的失控方式。

## Consequences

- **正面**：名字与上游对等物、仓库名、两份关键文档的语境终于一致；`check:brand` 把
  「品牌残留」变成机械门禁（含大小写不敏感 + 归档目录显式报数），下一轮不会再靠人眼。
- **代价**：identifier 变了 → **安卓包被视为新应用，必须卸载重装**（不能覆盖安装）；
  Windows 侧老用户首次启动多一次整树复制（一次性；正常路径只复制，不产生备份目录，
  只有「覆盖式迁移」才会留下 `<target>.premigrate-<ts>` 备份）。
- **不可逆点**：一旦 0.5.0 被安装并跑过迁移，用户的**新**数据只写进 `com.timing.app`。
  回滚到 0.4.x 能读到老数据，但读不到 0.5.0 之后新增的记录。这是单向门，发版说明必须
  写清楚。
- **一个版本的技术债**：`TICKBAR_LOG` 旧环境变量与 5 个 `tickbar.*` localStorage 键
  只读回落保留**一个版本**，0.6.0 删除（`scripts/brand-allowlist.txt` 里已登记，删的时候
  白名单条目要一起清）。
