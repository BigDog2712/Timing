# ADR-044：待办绑定事项（schema v5）

## Status

Accepted（2026-11-05，V0.11.3）

## Background

V0.3.12 起，待办开始计时靠**标题匹配**：`items.name = todos.title`，找不到就新建一个事项
（`services/todo_start.rs`）。当时的理由很直接——不新增列，同名事项不会重复出现。

问题不在创建，而在**之后**：

1. 用户建待办「写周报」，开始计时 → 自动创建事项「写周报」，计了三小时；
2. 下午把待办标题改成「写周报（二稿）」（这只是一次 `.update`，不影响已完成的记录）；
3. 再开始计时 → 匹配不到「写周报（二稿）」，**新建一个事项**；
4. 统计里同一件事变成两条，用户无法合并。

「同名两个事项」的隐患被避免了，换来的是「改名就裂开」。

## Decision

`todos` 增加 `item_id`（可空，schema v5），归属规则改为**绑定优先、标题兜底并回填**：

- 有绑定且事项仍存在 → 用它；
- 绑定的事项被删了 → 回落到标题匹配（不让「开始」直接失败）；
- 没有绑定 → 按标题匹配/新建，然后**把结果写回 `todos.item_id`**。

配套：

- 新建待办时若标题正好等于已有事项名，直接绑上（`services::todo::create`）；
- 老数据**不做一次性回填**：那等于批量跑一遍标题匹配，同名的几条待办会被绑到同一条，
  未必是用户想要的。第一次开始计时时自然绑上，成本为零。
- `TodoPatch` 增加同样的三态 `itemId`（省略 = 不动 / null = 解绑 / 值 = 改绑），
  改绑时校验事项存在，否则 `ITEM_NOT_FOUND`。

## Consequences

- 改标题不再影响归属，这是这条决策唯一的、也是最重要的收益。
- 待办与事项的关系变得**可见**（`Todo.itemId`），后续做「某事项还有哪些待办」
  「按事项归组待办」都有了落脚点，不必再靠字符串相等。
- 老待办在第一次开始计时前 `item_id` 为空——这是预期的过渡态，不是数据缺失。
- 移动端与桌面端共用同一条命令（`todo_start`），行为自动一致，无需分别实现。
