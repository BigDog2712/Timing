# ADR-007: 结束计时采用「一键结束并保存 + 撤销条」

## Status

Accepted (2026-10-16)

## Background

原设计（PRD v1 / ARCHITECTURE-v1 §7.2 / Spec 初稿）的结束流程为：右键触发 `stop_timer` 将会话置为 `draft`（待确认收尾态，`ended_at` 已填），弹出收尾浮层，用户点「保存」调 `confirm_stop`、点「取消」调 `cancel_stop` 回到 `active`。

该方案存在两个问题：
1. **操作摩擦高**：结束一次计时至少需要「右键 + 浮层点击」≥2 次交互，与核心指标「操作摩擦 = 1 次点击」冲突；而"忘记停止计时"正是现有计时工具的第一失败原因，任何额外摩擦都会放大该失败。
2. **数据模型复杂**：`draft` 引入了「既非进行中、亦非已结束」的第三态，使状态机、崩溃恢复（需处理 `status IN ('active','draft')`）、部分唯一索引、DTO 与前端状态分支全部多出一维。

用户于 2026-10-16 确认三文档时裁决：结束计时改为「右键单击 → 立即保存 + 撤销条」。本 ADR 记录该决策及其对数据模型与 IPC 契约的全部影响。

## Decision

**采用「右键单击 = `stop_timer` 立即置 `saved` + 3 秒 `undo_stop` 撤销窗口」；彻底移除 `draft` 态。**

具体锁定项：

1. **命令变更**：
   - `stop_timer` 语义由「置 `draft` + 弹收尾浮层」改为「立即置 `saved`（`ended_at=now`、冻结 `accumulated_sec`）」，返回记录并开启 3s 撤销窗口。
   - **删除** `confirm_stop` / `cancel_stop`。
   - **新增** `undo_stop({ recordId })`：将 `saved` 记录回滚为 `active`（`ended_at=null`、`running_since=now`、状态回 running），累计时长接续。
2. **数据模型**：`time_records.status` 由 `'active' | 'draft' | 'saved'` 收敛为 **`'active' | 'saved'`**；部分唯一索引由 `UNIQUE(status) WHERE status IN ('active','draft')` 改为 **`UNIQUE(status) WHERE status='active'`**（DB CHECK 同步收敛）。
3. **前端状态**：`TimerState.status` 由 `'idle' | 'running' | 'paused' | 'draft'` 收敛为 **`'idle' | 'running' | 'paused'`**。
4. **错误码**：`TIMER_NO_DRAFT` 删除，新增 **`TIMER_NO_UNDO`**（撤销窗口过期 / 记录非 saved / 记录已删除）。
5. **交互分工**：右键**单击** = 结束并保存；右键**长按 ≥500ms** = 打开上下文菜单（区分误触）。撤销窗口长度 `UNDO_WINDOW_MS = 3000`，前端与 Rust 侧常量须一致。
6. **撤销窗口以服务端为准**：`undo_stop` 以记录 `ended_at` 与服务器时间校验窗口（+200ms 容差）；前端计时仅用于 UI。

## Consequences

正面：
- 操作摩擦降至最低（1 次点击结束），直接对齐产品核心指标与"忘记停止"这一首要失败场景。
- 数据模型与状态机简化为一维；崩溃恢复只需处理单一 `active` 态；`ITEMS_SYSTEM` / 索引 / DTO / 前端分支同步收敛，减少沉默逻辑错误面。
- 撤销条提供等价的"确认/回退"能力，体验上接近弹窗确认却无阻塞成本。

负面 / 需处理：
- **竞态**：3s 窗口内用户若已开始新会话，`undo_stop` 必须返回 `TIMER_ALREADY_RUNNING` 并提示，绝不能出现两条 `active`（否则触发 `uq_records_open` 写失败）。
- **窗口依赖前端计时 + 服务端校验**：两者窗口不一致会产生边界争议，故以服务端 `ended_at` 为准。
- **撤销条资源管理**：撤销条定时器必须在组件卸载时清理，避免监听/定时器泄漏（K-8）。
- **误触风险**：右键单击即结束，若有误触则需在 3s 内撤销；用长按阈值区分菜单以降低误触概率。
