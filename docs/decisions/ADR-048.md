# ADR-048：插件 API v3 — 接口先定、运行时后置（`permissions` 是声明性，API 是既有命令的白名单投影）

## Status

Accepted（2026-11-06，V0.11.5；用户口径「插件应赋予插件本身最高权限，软件负责识别插件、
检测插件是否可行等，具体可参考 Obsidian 的插件功能。最后应可以实现通过插件开发 api 调用、
连接桌宠等功能。（但目前不考虑开发，现在要把接口写好）」）

## Background

插件系统到 v2 为止只有两个贡献点：`quickTimers`（v1，且 V0.3.9 起不驱动菜单）和
`mdSync`（v2，V0.11.5 已下架，见 ADR-047）。两者都是**声明式**的：宿主读 `plugin.json`，
不执行任何插件代码，能力边界靠"贡献点 schema"而不是"权限"。

用户要的是另一件事：插件本身拿到最高权限，像 Obsidian 那样能调宿主能力、能挂 UI、
最终能连桌宠。这带来一个无法回避的顺序问题——**接口和运行时必须分两次落地**：

- 运行时（Worker 隔离、API 注入、崩溃回收、钩子超时）是一次独立迭代，硬塞进 V0.11.5
  会和 ADR-047 的同步内核化抢同一批文件，两边都做不干净；
- 但接口不定，运行时就没法写：`Api` 对象的形状决定了插件怎么写、宿主怎么校验，
  改一次签名等于把所有已写插件推倒重来。

所以 V0.11.5 只做前一半：**把 v3 的字段、权限模型、API 面、生命周期、兼容策略定成契约，
写进 `docs/plugin-spec.md` §10，代码只认 `apiVersion: 3` 这个数字，不加载任何脚本。**
这一轮的价值不在"能跑"，而在"以后不用改签名"。

## Decision

### 1. `apiVersion` 升到 3，新增五个字段

`PLUGIN_API_VERSION` 2 → 3。新增（全部可选，缺省即"没声明"）：`permissions`、`engines`、
`author`、`homepage`、`dependencies`。完整字段全表（类型 / 必需性 / 默认值 / 约束 /
校验失败文案 / 本机实现状态）在 `docs/plugin-spec.md` §10.2，本文不重复。

两条判据值得单列：

- **`engines` / `dependencies` 不满足 → 拒载。** 这两个字段是作者在说「我需要 X 才能正确
  工作」。宿主拿低版本去解释它的清单，就是在**猜语义**——而"不认识就拒载、不猜"是插件
  系统从 v1 起就定下的口径（`entry` / `apiVersion` 同款处理）。
- **`permissions` / `author` / `homepage` 写错 → 警告，不拒载。** 它们是展示性字段，
  写错顶多显示不准，不构成"宿主无法正确解释清单"。

### 2. `permissions` 是**纯声明性**，不是约束性

这是本 ADR 最需要写清的一条：**宿主不据此拒绝任何调用。**

理由只有一条，但它是硬的：**约束性权限要求宿主在调用点上逐条拦截。** 而"插件即全权限、
不做沙箱、不逐条授权"意味着根本没有拦截点。这时候把 `permissions` 写成约束性，产出的
不是安全，而是**假的安全感**——设置页写着「此插件只能读取待办」，实际它什么都能干
（读写数据库、改设置、开窗口）。**比不写更坏。**

声明性仍然有价值：它唯一的产出是**可见性**。设置 → 插件 把 `permissions` 翻译成人话，
用户装之前能看到"它打算干什么"。这是 Obsidian 那套里「看得见」的部分，我们照搬；
「拦得住」那部分我们不做，也不假装做。因此**设置页展示 `permissions` 时必须固定带一行灰字
「声明，不是限制：插件与 Timing 同权限」**，否则用户会把声明当沙箱。

未知能力名 → 警告不拒载（声明性字段写错不该让插件失效）。
「声明与实际调用是否相符」的检测（调用点记账 → `onDisable`/`onUnload` 时与 `permissions`
求差集 → 多用了的记警告）**本轮不做**，口径写进 spec §10.3 供运行时落地时实现。

### 3. `api.commands` 是既有 67 条命令的**白名单投影**，不是新通道

调用路径仍是 `插件 → api → commands → services → repositories`（ADR-015 不破）。
插件不直连数据库、不直连 `repositories`、不碰 Tauri 的 `invoke`。
因此 v3 **不新增命令、不新增事件、不新增错误码**——插件拿到的错误就是现有那 16 个码，
`check:contract` 的四处/三方一致性完全不受影响。

开放 11 个域（timer / item / todo / note / record / settings / mdSync / window / theme /
reminder / dailyStatus）；未列出的命令**一律不开放**。四类明确不给，理由统一：

| 不开放 | 理由 |
|---|---|
| 插件自指（`plugin_*`） | 插件能列 / 能处置自己，故障表现是「插件把自己弄没了」，无法归因 |
| 一次性数据迁移（`get_migration_info` / `open_legacy_dir`） | 动的是用户数据目录，误调一次就可能搬走或暴露整个库 |
| 宿主生命周期与主条可见性（`quit_app` / `set_autostart` / `show_window` / `hide_window` / `toggle_window` / …） | 主条是宿主唯一的常驻界面，被藏起来后用户只能杀进程；应用自退 / 开机项被改，用户看到的是「Timing 自己出问题」 |
| 不可逆删除与历史改写（`delete_item` / `delete_record` / `update_record` / `note_delete`） | 都没有撤销入口——这是**数据不可逆**问题，不是权限问题。需要时按名字单独评审开放 |

`api.commands.settings.update` 是**全量写设置**，明确开放：与"全权限"一致，
且改成按键写的窄接口要新增命令 = 破契约。风险（插件一次写坏四色 / 摸鱼预设 / 同步落点）
由"装插件=信任它"这条前提承担。

### 4. `api.events` — 11 个宿主事件全可订阅，**不允许插件自定义全局事件**

订阅是只读的，`emit` 侧仍在宿主，所以 11 个全开放。

不允许自定义的判据是可核的：事件名是**全局广播**名字空间，而 `scripts/check-contract.mjs`
要求「`app/events.rs` 常量 ↔ 前端 `IPC_EVENTS` ↔ 真实 `emit` 点」三方一致，
且**每个前端声明都必须有 emit 来源**（死常量直接红）。插件自定义的事件名永远没有 emit 点
——要么让门禁变红，要么被迫往 `EVENT_ALLOWLIST` 加白名单，而白名单一旦出现（ADR-022 之后
已清空为 `new Map([])`），这条保护就等于失效。
插件需要的"回调"走 `api.ui` 的 `onUiEvent` 与 Promise 返回值。

### 5. `api.ui` — 只收**声明式节点树**，不收 HTML / CSS

四个挂载点：设置页卡片（`ui.settingsCard`）、独立面板（`ui.panel`）、主条菜单项（`ui.menu`）、
托盘子菜单（`ui.tray`，最多 5 项）。插件给的是 `UiNode` 数组，宿主逐个 `type`
映射到 `src/components/ui/*` 的既有组件。

三条硬理由，缺一不可：

1. **令牌规则会被击穿且门禁拦不住。** 主仓是手写 CSS + `var(--*)` 设计令牌、禁裸 hex / rgb，
   而 `check:size` / `check:layers` / `check:brand` **只扫 `src/`**——插件 CSS 不在扫描面内，
   等于开了一个永久豁免口子。
2. **XSS**：WebView 里插件 HTML 与宿主同源，`innerHTML` 一次就等于交出整个前端。
3. **深浅主题立刻失效**：字面量色值不跟 `data-theme` 走，插件在浅色主题下会变成一块黑。

因此插件能定制的只有 `tone`（`default` / `muted` / `warn`）与 `variant`（`primary` / `ghost`）
两个**语义枚举**：没有颜色、没有像素、没有类名。宿主**不保存**任何插件 UI 状态。

### 6. `api.desktopPet` — 只定义形状，标注未实现

`create` / `move` / `say` / `setState` / `remove` 五个方法，参数、返回、约束（`size` 32~256 DIP、
`text` ≤120 字符、同时最多 3 只、窗口透明置顶不可聚焦）全部写进 spec §10.4.4。

**未实现期间不新增错误码**：没有运行时，这些调用不可能发生；运行时落地后若确需新码，
走契约评审（union / `errorText()` / 契约文档 §2 三处同步）。

### 7. 生命周期四钩子：串行、超时 5s、失败不阻断启动

`onLoad` / `onEnable` / `onDisable` / `onUnload`，时机与顺序：

- 加载全局**串行**（共用同一个 WebView 与同一个 DB 连接池，并发加载只会让"卡住时是谁卡的"
  无法归因），顺序按来源优先级 `dev → exe → user` + id 字典序；
- `onUnload` **逆序**，且只要 `onLoad` 成功过就调，不论当前是否 `enabled`；
- 每个钩子超时 **5 000 ms**，超时 = 记日志 + 继续下一个，**不阻断启动**；
- `onLoad` / `onEnable` 失败 → 插件标 `failed`，`api.*` 全部 reject，但**清单仍列在设置页**
  （不静默消失）；`onDisable` / `onUnload` 失败只记日志（退出路径不能因为插件卡住用户）；
- 钩子执行期间拒绝同一插件的 `api.*` 调用，防 `onLoad` 自我递归。

### 8. `entry: "script"` 语义预留，但**仍拒载**

目录约定 `<插件目录>/main.js`（固定名）；运行时形态是 WebView 内的**独立 `Web Worker`**，
不共享 `window` / `document`，只经 `api` 对象通信。

选 Worker 而不是同页脚本的理由：插件死循环不能锁死主条。同页脚本一旦 `while (true)`，
整个界面就冻住，用户只能杀进程。

「反正没实现，随便写」是错的：目录约定与运行时形态决定了 API 的**同步 / 异步底色**
（Worker 里只能异步）。现在定错，将来所有插件的 `api.*` 签名都要改一遍。
因此本机仍按 v2 口径**拒载**：`entry=script 尚未实现运行时，当前宿主只执行 manifest`。

### 9. 兼容矩阵

| 插件 `apiVersion` | v3 宿主行为 |
|---|---|
| `1` | ✅ 载入，`quickTimers` 解析并展示（仍不注入摸鱼菜单，ADR-026） |
| `2` | ✅ 载入，`contributes.mdSync` **忽略 + 警告**（ADR-047），其余按 v2 语义 |
| `3` | 载入；v3 新字段本轮不解析；`entry: script` 仍拒载 |
| `4` 及以上 | ❌ 拒载：`apiVersion 必须为 1..=3（本机宿主版本更低）` |

未知字段一律忽略，不报错——向前兼容靠这条，不靠白名单。

## Alternatives

| 方案 | 否决原因 |
|---|---|
| 做沙箱 / 逐条授权 | 用户明确拍板"插件即全权限，装了就是自己人"。做半套沙箱只会让用户以为有隔离，而实际没有拦截点 |
| `permissions` 做成约束性（宿主不授权的调用直接 reject） | 见 Decision 2：没有拦截点的约束性权限 = 假安全感，比不写更坏；而真做拦截点就是沙箱，与上一条冲突 |
| 干脆不做 `permissions` 字段 | 失去唯一的价值——可见性。用户装之前完全不知道插件想干什么 |
| `api.commands` 另开一套插件专用命令 | 复制一份能力 = 两份校验、两份错误码、双倍契约面；而"白名单投影"零成本地复用既有 16 码与四层依赖 |
| 允许插件给 HTML / CSS（或 iframe 隔离） | 见 Decision 5 三条理由；iframe 能与宿主同源或需要额外 origin 策略，复杂度超过本轮收益 |
| 允许插件自定义全局事件 | 见 Decision 4：三方一致是机械门禁，白名单化等于关掉保护 |
| 本轮就把运行时一起做了 | Worker 隔离 / API 注入 / 崩溃回收 / 钩子超时是独立迭代，且与 ADR-047 抢同一批文件；两件事混做，两边都做不干净 |
| 把 `entry: script` 假装支持（加载成功但不执行） | 用户会对一个"什么都没发生"的插件排查半天。拒载至少明确告诉你"这条路还没通" |

## Consequences

- **v3 新字段本轮不解析**（用户已拍定，排 V0.11.6）：宿主接受 `apiVersion: 3` 的清单，
  但 `permissions` / `engines` / `author` / `homepage` / `dependencies` 写了既不校验也不展示。
  V0.11.6 的落地口径是**只解析到「能看见」**——解析 + 设置页展示，仍**不做**
  `engines` / `dependencies` 的硬校验（硬校验要等运行时，因为那时"能力不足"才真的有后果）。
  spec §10 每一项都标了 ✅ / ⬜ 状态列，"写了不报错也不生效"这件事对作者是可见的。
- **现在写 v3 插件得到的是「清单被识别」，不是「代码被跑起来」。** 这句话写进了
  spec §10.0 的表格里，是本节最需要被读到的一句。
- **契约数字不变**：v3 不新增命令 / 事件 / 错误码。`check:contract` 的四条命令比对、
  错误码两侧、事件三方一致性全部照旧咬死。
- **插件域与同步域解耦**：v3 的 `api.commands.mdSync` 只是把 4 条既有命令再暴露一次，
  `mdSync` 贡献点本身已随 ADR-047 下架。
- **文档成为唯一契约**：`docs/plugin-spec.md` §10 约 290 行，含字段全表、权限模型、
  API 面、生命周期、兼容策略、不做清单。代码与本文件冲突时以 spec 为准（spec 与本文
  冲突时以本文为准）。
- **V0.11.6 的入口已经备好**：运行时落地时不需要改字段名、不需要改 API 签名、
  不需要动现有插件——只需把 spec 里的 ⬜ 逐项翻成 ✅，并按需要走一次契约评审。

> 正文以本文为准；v3 接口契约见 `docs/plugin-spec.md` §10。
