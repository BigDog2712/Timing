## 1. 产品目标

### 1.1 电梯稿

> 让药丸和分析窗变成同一款应用的两扇门：**在药丸上能看见今天发生了什么，在分析窗里能对刚刚发生的事直接动手**，而颜色、日期、数字全应用只有一套。

### 1.2 「融合得更紧密」的可判定定义

四条，每条都能被验收（做不到即视为未融合）：

**D1 · 看到以前看不到的东西（同轴可见）**
在分析窗「历史」页任选一天，时间线上同时存在两条泳道：「电脑活动」（Patina 自动片段）与「Timing 计时」（手动计时记录）。两泳道共用同一 0–24h 轴、同一日期口径；同一分钟的区间在视觉上首尾对齐（偏差 ≤ 1 分钟）。进行中的记录显示到「现在」并标注「进行中」。
*判据：当天无记录时该泳道整条不渲染（沿用既有「不留空壳」口径），不允许出现空泳道。*

**D2 · 能做到以前做不到的事（双向可动手）**
① 从药丸一步到达「分析窗的今天」；② 从分析窗的某段活动一步开始在 Timing 里计这件事，且药丸在 2 秒内反映为计时中。
*判据：两条路径都 ≤ 1 次点击，不需要进设置页。*

**D3 · 少做的多余动作（入口与配置收敛）**
- 到「分析窗的今天」：现在是 ≥ 4 步（药丸无入口 → 托盘「时间统计…」或 设置→通用→时间统计「打开」→ 侧栏「历史」→ 选日期），收敛为 1 步。
- 改主色/语义色：现在分析窗一套预设 + 宿主一套四色共 2 处，收敛为 1 处。
- 同名参数（最短会话时长、时间线合并间隔、刷新间隔）：现在两窗各有一套编辑处，收敛为 1 处编辑 + 另一侧只读同值。

**D4 · 只有一套真相（无第二口径）**
- 同一天的总时长，两窗数字必须相等（同一 SQL、同一区间、同一「今天」定义）。
- 主色改一次，两窗同步（≤ 2 秒，切窗即可见）。
- 深/浅已单源，本轮不得回退成两套。

### 1.3 用户故事

1. **工作时用悬浮条**：作为长时间在电脑前工作的人，我想在药丸上一眼看到「今天已经计了多久、刚才在用什么软件、有没有一件事还没停」，这样我不用打开任何窗口就能确认今天没跑偏。
2. **工作时被问「这半天干了啥」**：作为被临时打断的人，我想从药丸直接跳到「今天的时间线」，在那里看到自动记录的应用片段和我自己计的事并排摆在同一条时间轴上，这样我能在 10 秒内回答，而不是翻两个应用。
3. **复盘时看分析**：作为每周复盘的人，我想在分析窗看到某段活动后直接说「这件事我要计时/我要记下来」，这样我不用切回药丸重新建事项、重新开始。
4. **配色只调一次**：作为在意观感的人，我想在一个地方把主色定下来，两个窗口同时变，这样我不会在两个设置页里看到同一个 App 有两套配色。
5. **不被两套说法搞混**：作为新用户，我想知道「番茄钟」和「倒计时」到底哪个会计入我的时间账，这样我不会因为选错工具而丢掉统计。

## 3. 关键交互设计

### 3.1 路径① 从药丸看今天 → 跳到分析窗当日（D2-① / D3）

```
[药丸 384×360 idle]
   │ 点击条上新增的 16px「今天」图标（便利贴手柄左侧；宽度由 auto-fit 吸收）
   ▼
[记录面板]  ← 当前不可达，P0-03 补入口
 ┌──────────────────────────────────────────────┐
 │ 今天  2h40m            [ 在分析窗看这一天 ↗ ] │
 │ ── 同时在用 ─────────────────────────────── │
 │  VSCode 1h10 · Chrome 40m · WeChat 12m   →   │  ← 点任一 chip 也跳
 │ ── 记录 ─────────────────────────────────── │
 │  10:00  写方案      25m                      │
 │  13:35  周会        45m                      │
 └──────────────────────────────────────────────┘
   │ ↑ 两种跳法都落到同一个「待消费目标」
   ▼
[分析窗] 标题栏右侧 [● 计时中 写方案 12:31]   ← P0-04 常驻胶囊
         侧栏自动高亮「历史」，日期 = 今天，
         滚动到当天最近活动处；点 chip 跳的带应用高亮
```

规则：
- 目标 = `{ view: 'history', dateKey, focusApp?: string }`，**一次性消费**（取走即清空，冷启动也能拿到）。
- 「今天」按宿主本地日定义，与分析窗同一个日期口径，不允许两窗各自算。
- 药丸既有 7 个点击区（圆环 1 / 时间数字左右 2 / 事项名左右 2 / 便利贴手柄左右 2）语义全部已被占用且是 Timing v1.7.3 对齐行为，**不得挪用**；新入口只能新增一个图标位，且图标必须带可读 `aria-label`。
- 第二处入口（提高可发现性）：事项窗口顶部同一行「今天 2h40m →」，与药丸图标落到同一目标。


### 3.2 路径② 在分析窗对某段活动「开始计时」（D2-② / D1）

```
[分析窗 · 历史 · 时间线]
  电脑活动 ▏▏▏ VS Code 14:00–14:30 ▏▏▏▏▏ Chrome ▏▏▏
  Timing   ▏▏ 写方案 13:35–14:20 ▏▏            ← P0-02 新增泳道
                    ▲ 点活动段（或计时段）
        ┌───────────────────────────────────┐
        │ VS Code · 14:00–14:30 · 30 分钟    │
        │ [ 在 Timing 计这件事 ▸ ]   [ 关闭 ] │
        └───────────────────────────────────┘
                    │ 点「计这件事」
                    ▼
        同名事项「VS Code」存在？ ── 是 → 直接用
                    └────────── 否 → 用应用名新建事项
                    ▼
  宿主是否已在计时？ ── 是 → ┌──────────────────────┐
                    │ 正在计「写方案」12:31  │
                    │ [ 切换并开始 ] [ 取消 ] │
                    └──────────────────────┘
                    │ 否 / 切换
                    ▼
[药丸] ≤2s 进入 running，事项名 = VS Code（用户可在药丸上改名）
[分析窗] 该段/新泳道段出现「计时中」角标，胶囊同步更新
```

关键取舍（产品口径，不要放宽）：
- **计时从「现在」开始，不回填历史区间。** 回填 = 修改历史账，属 P1-01，且需要宿主的写命令。
- 取消冲突提示必须**完全无副作用**：不切换、不结束原计时。
- 这一段数据由**宿主执行并落库**，分析窗只表达意图（见 §5，保住只读桥边界）。
- 弹卡里不出现「分类/标签」等分析窗概念，避免把两套模型混在一起。

### 3.3 路径③ 两个窗口的入口位置（不能只有设置页一个按钮）

```
┌─ 药丸（主窗 384×360）────────────────────────┐   ┌─ 分析窗 ────────────────────────────┐
│  ○ 写方案   12:31  [▤今天]  [便利贴]         │   │ [Timing ● 计时中 写方案 12:31  ▸]  │ ← P0-04
│  ↑圆环      ↑事项   ↑P0-03   ↑已有            │   │  ↑ 标题栏右侧常驻；▸ = 回药丸       │
│                                              │   ├─────────────────────────────────────┤
│  ┌ 记录面板（点「今天」）──────────────┐      │   │ 侧栏 │ 总览｜历史｜数据｜映射｜工具… │
│  │ 今天 2h40m      [在分析窗看这一天 ↗] │      │   │      │  历史页：P0-02 双泳道        │
│  │ 同时在用 chip →                    │      │   │      │  工具页：P0-07 状态行         │
│  └──────────────────────────────────┘      │   │      │  设置页：P0-06 已下线外观     │
└──────────────────────────────────────────────┘   └─────────────────────────────────────┘
    药丸 → 分析窗：今天图标 → 面板头按钮 / 同时在用 chip（2 条路径，同一目标）
    分析窗 → 药丸：标题栏胶囊（1 处，常驻可见）
    入口不放在设置页；设置页现有「时间统计 · 打开」保留但降级为备用路径
```

规则：
- 药丸侧入口必须**常驻可见**（一个带标签的图标位），不依赖托盘菜单（托盘的「时间统计…」保留，但不是唯一路径）。
- 分析窗侧入口必须**常驻在标题栏**，随任意视图可见（参考现有标题栏已挂 `ToolsStatusEntry` 的做法）。
- 两侧入口都要有可读文案或 `aria-label`，不允许只有一个无标签图标。

## 4. 不做的事（Out of scope，本轮明确不碰）

1. **单窗合一 / 药丸内嵌分析视图**：双窗形态是既定形态，不做面板化重排。
2. **移动端分析功能**：Android 仍是单窗容器，不引入 Patina 引擎，不加分析 Tab。
3. **重写 vendored 引擎**：Patina 的数据模型、采集器、统计口径、分类算法一律不动；只做宿主侧融合层与已登记的漂移。
4. **新统计指标 / 改现有口径**：P0 不允许「顺便」调整时长算法、会话切分、去重阈值。
5. **补记与修改历史账**（回填记录、批量改归属）：P1-01 之后再谈。
6. **配色预设全量迁移到宿主四色**：只收敛「主色 + 语义色」，中性底色仍由预设决定（否则等于重画 28 套主题）。
7. **插件系统与 md_sync 行为变更**：只动文案与入口，不动同步/备份逻辑。
8. **快捷键体系重构**：仅 P1-05 加一条新快捷键，不改既有键位。
9. **分析窗直接写宿主数据的任何能力**（含直接开始/结束计时、改记录、改事项）：一律走**事件 handoff**、由宿主侧执行并落库，不给分析窗写命令。这是本项目既定边界（`src-tauri/permissions/patina-host-bridge.toml` 明文「只读、不给任何写命令」），不是本轮可选项——后续任何需求若要求分析窗写入，都必须先改这条边界并升版本，不能在实现里就地开口子。

1. **「数据融合」缺的不是数据源，是字段与呈现。** 分析窗历史页已有一块「同期计时」（`HistoryTimingOverlap`），但它只取 `itemId` + `accumulatedSec` 并在历史页按**日聚合**成一行；而宿主 `list_records` 实际返回完整 `TimeRecord`（含 `started_at` / `ended_at` / `mode` / `target_sec`）。**P0-02 只需扩展 `platform/runtime/timingOverlapGateway.ts` 的字段映射 + 新增泳道**，无需新命令、无 IPC 契约变更。
2. **桥的边界是「只读」，写死了的。** `src-tauri/permissions/patina-host-bridge.toml` 只放行 `list_records` / `list_items`，并在注释里写明「不给任何写命令」。所以 P0-05 走「宿主执行」：分析窗表达意图 → 宿主侧落 pending 目标 → 药丸消费并执行。反方向（分析窗 → 药丸）目前不存在，需要新开一条；已有 `MAIN_TOOLS_TARGET_CHANGED` + `cmd_take_main_tools_target` 的 pending-target 模式可镜像（注意窗口 label 语义是反的：`main` = 药丸，`patina` = 分析窗）。
3. **配色只差一步。** 深/浅已单源（`useHostThemeMode` + `theme_get`/`theme_set`/`theme-changed`，权限在 `patina-host-theme.toml`）。P0-01 只需在同族权限里加一条**只读** `accent_get`（宿主 `src/lib/theme.ts` / `themeStore` 已有该数据），并把四色映射进 `deriveTheme` 的令牌生成；`--qp-*` 的中性底色保持不动。`deriveTheme` / `themePresets` 位于 `src/shared/theme/`（vendored），改动必须登记漂移。
4. **记录面板与今日摘要当前不可达。** 全仓 `openPanel('records')` / `openPanel('digest')` **0 处调用**（只有 `'create'` 与 `'settings'`），意味着「同时在用」这条唯一的既有融合可见物在 UI 上没有入口。P0-03 是「补入口」而非「改布局」，成本低、体感提升大。两点连带约束：① `ActivityStrip` 组件注释里明确写了「不可点击（只是旁证）」，P0-03 要把它改成可点，注释与 `aria` 需同步更新；② 药丸当前 4 个组件（Ring / TimerDisplay / ItemName / NoteHandle）的左右键 **7 个点击区全部被占用**，且都是 v1.7.3 对齐行为，新入口只能新增图标位，不能复用既有手势。
5. **落地位置受 L9 约束。** 主窗层（`components/hooks/lib/mocks/services/stores/styles/types`）与分析窗层（`app/features/platform/shared`）互相禁止 import。两窗都要用的东西，要么落在两侧都合法的位置（需架构师定，可能要新增共享根并同步改门禁），要么走 IPC。请优先选择**不改门禁**的方案。
6. **成本提醒**：`ipc.ts` 已卡在 300 行棘轮上；每新增一条宿主命令要同步四处代码 + 四处文档。P0 全部 7 项目标是 **+0 命令 / +0 错误码**（事件最多 +1，用于分析窗 → 药丸的 pending 目标）；若架构方案做不到，请在方案里点名是哪一项、代价多少。

## 7. 已知技术债（本轮不修）

以下缺陷由 QA 在 B1 验证阶段定位，**与本轮改动无交集**（`git diff` 与 `src-tauri/src/infra/insight/**`、`engine|data|repositories|icon` 目录交集为空），故不在本轮修，单开一批处理。

### TD-01 · 图标负缓存并行测试偶发失败

- **现象**：`cargo test --lib` **并行**跑时，`failed_refresh_retains_old_icon_and_backs_off_even_for_packaged_apps` 偶发失败；串行跑、单跑均通过。属于**测试隔离**问题，不是产品行为缺陷。
- **根因**：`src-tauri/src/.../metadata.rs` 的 `icon_negative_cache()` 是**进程级全局** `Mutex<HashMap>`，多个测试共享同一份缓存；而 `cleanup_icon_negative_cache(cache, now_ms)` 用**各测试自己的假时钟**做 `retain`。同模块并行测试里 `now = 100 / 101` 的用例执行清理时，会把另一用例刚写入的 `last_failed_at_ms = 10_000` 条目当作「时钟回滚的陈旧条目」删掉 → 该用例的退避（backoff）失效 → 断言失败。
- **判据**：`--test-threads=1` 时必过；并行时失败点随调度变化，且日志里能看到条目在无 `ensure` 调用的情况下消失。
- **候选修法**（QA 给出，按优先级）：
  1. **把 cache 改成可注入**：`ensure_icon_cache_with` 已经注入了 clock / semaphore，再加一个 cache 参数即可就地单测、并行互不干扰（首选，改动面最小、语义最干净）。
  2. **统一假时钟量级 + 单调清理**：模块内所有用例的假时钟统一到一个量级，且 `cleanup` 取「单调递增 now 的 max」再做 `retain`（次选，仍是共享状态，靠约定维持）。
  3. 全局 `--test-threads=1`：**不采纳**，`cargo test --lib` 会从数十秒涨到 102s，CI 不可接受。
- **本轮处置**：不修、不改测试、不加 `#[ignore]`（掩盖比失败更糟）。修复需单开一批，且必须在 `--test-threads` 默认并行下稳定通过才算完成。
- **对验收的影响**：B1/B2 的验收结论中，该条以「已知技术债，非本轮引入」记录，不计入回归失败；但**若后续改动触碰了 `metadata.rs` 或该测试**，此债立刻升级为必修项。
