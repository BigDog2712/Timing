## 3. 分项评估

### 3.1 架构与分层 —— 优

后端六层加前端三层，依赖方向由 `scripts/check-layers.mjs` 的 6 条 grep 规则机械执行（components 不 `invoke`、stores 不碰 `ipc.`、只有 `lib/window.ts` 引 `@tauri-apps/api/window`、`infra` 不引 `services`、`commands` 不引 `repositories`、无 `eprintln!`）。**这几条真的能挡住人**——本次我加前端组件时，第一反应是「要不要直接调 ipc」，规则的存在让这个念头在写之前就断了。

2026-10-18 那份架构评估里点出的 `infra ↔ services` 双向环、前端 actions 层非强制、`domain.ts` 552 行单点，现在都已经解掉了（`jobs/`、`platform/`、`app/` 三层拆出来，`services/api.ts` 做领域门面，`types/domain/*` 按域拆开）。**上一轮的技术债是真的还了，不是记成「已排期」。**

一处仍在的小口径分裂：时间公式在前端有一份复刻（`src/hooks/useTimerTick.ts` 的 `computeLiveSec`）。这是有意的（避免状态同步瞬间数字跳变），而且用 `tests/fixtures/timer-formula.json` 双端共用锁住了。**可以接受，不必强拆**。

### 3.2 契约纪律 —— 优（本项目的护城河）

`scripts/check-contract.mjs` 干的事比大多数团队 CI 都硬：

- 命令名在 `generate_handler!` / `IpcApi` / `ipc.ts` / `browserMock` 四处集合必须相等；
- 错误码在 Rust `as_str` 与前端 union 逐字一致；
- 事件在后端常量 / `IPC_EVENTS` / emit 点三方一致，且**禁止事件名字面量**；
- 每个错误码必须在 `errorText()` 里有 `case`——这条能抓出「静默落到通用兜底」的体验 bug。

这套东西的价值不在「好看」，在于**改契约时改动点可枚举**。本次加日志时我特意没有新增命令（会牵动 4 处 + 文档 + 契约评审），就是因为这套机制把「顺手加一条命令」的成本抬到了正确的水平。

### 3.3 数据与并发正确性 —— 优

三个设计值得单独记住：

1. **并发正确性下沉到 DB**：`uq_records_open` 唯一索引保证「最多一条 active」，唯一冲突翻译成 `TIMER_ALREADY_RUNNING`；`finalize` / `end_and_start` 用 `rows_affected() != 1` 判并发。双击结束、并发 stop、崩溃残留天然正确，不靠内存锁。
2. **零内存业务状态**：`AppState` 只持 `SqlitePool`。消灭「内存与库不一致」整类 bug，代价是读放大（单用户本机可忽略）。
3. **迁移幂等**：SQLite 没有 `ADD COLUMN IF NOT EXISTS`，用 `PRAGMA table_info` 守卫 + `ensure_column`，先补列再建索引，4 个迁移都可重入。

### 3.4 测试 —— 良

- 后端 338 条，覆盖计时状态机、切换、阈值、崩溃恢复、迁移、md-sync 往返、托盘、窗口几何；
- 前端 245 条，重点在纯函数（`autoFit` 21 条、`useTimerTick` 13 条）与关键组件（`TodosPanel` / `ReminderPopover` / `MdSyncTab` 等）；
- **双端黄金用例**：`tests/fixtures/timer-formula.json` 一份数据喂两边，这是「公式复刻」唯一可靠的防漂移手段。

缺口：**没有 E2E**。这是 2026-10-18 那份评估里明确「有意不做」的一项（`tauri-driver` + WebDriver 在单人项目里维护成本高于收益），我认同这个判断——但要接受「窗口建窗时序、跨 DPI 回填、拖拽」这些只能人肉回归。

### 3.5 可观测性 —— 中偏弱（本次补强）

有通道，没内容。

真机证据：`timing-2026-10-23.log` 整个文件 845 字节，一次运行只有两行——

```
INFO [log] ---- Timing v0.4.0 start ----
INFO [app::bootstrap] startup complete
INFO [platform::boot_timing] boot[setup] setup=480ms ...
INFO [platform::boot_timing] boot[first_frame] setup=480ms first_frame=4605ms ...
```

代码里 `log_info!` 只有 **3 处**、`log_warn!` 33 处、`log_error!` **0 处**。也就是说：

- 用户说「我计了 20 分钟，记录里没有」——日志里查不到任何一次 start / stop；
- 用户说「它不见了」——如果原因是前端渲染抛错，Rust 侧**一个字都不会有**（错误在 WebView 里，从不经过 IPC）；
- 真正的故障（写库失败、IO 失败）和一句无害的告警（同步跳过）在日志里同级，全是 `WARN`。

本次补的三处见 §5。**未补但建议补**：前端错误落盘需要一条 IPC 命令（改契约），见 §6 A 档。

### 3.6 启动与运行性能 —— 中

真机 90 次采样（`boot-timing.tsv`）：

| 指标 | p50 | p95 | 最大 | > 1s 次数 |
|---|---|---|---|---|
| `setup`（进程入口 → Rust 装配完成） | 320ms | 480ms | 5068ms | — |
| `first_frame`（进程入口 → 前端首次 `show_window`） | 531ms | 1656ms | 7108ms | **11 / 87** |

拆开看最近一次启动的 trail：

```
log_ready=449  db_ready=470  defaults_ready=471  tray_ready=478
reclamped=479  diagnostics_done=479  jobs_spawned=480  setup_done=480
first_frame=4605
```

两个结论：

1. **Rust 侧不是瓶颈**。日志初始化之前的 449ms 主要是 Tauri 运行时 + 窗口创建（`boot_timing::start()` 在 `Builder` 之前）；之后从建库到装完 5 个调度器只用了 **31ms**。PDF 里常说的「启动串行 block_on」在这个数据下**不值得动**——评估纪律是对的（先埋点再优化）。
2. **长尾在前端**。`setup_done` 到 `first_frame` 之间空了 4.1 秒，这段是 WebView2 起进程 + 加载 425 kB 单 chunk JS + React 首帧。中位数 531ms 说明常态没问题，**长尾意味着有 12.6% 的启动体验很差**。

推断（未验证）长尾的成因，按可能性排序：

- 单 chunk 425 kB 无分包，冷启动要下载/解析全部代码才能首帧；
- `additionalBrowserArgs` 里带了 `--disable-gpu`（为透明窗稳定），软件渲染下首帧更慢；
- 采样集中在开发机满载时段（10-19 晚 17:23~23:23 那批 1.4–7.1s 明显是边编译边启动）。

**运行期成本**：5 个常驻任务里，`countdown` 从 1s/次降到 15 tick 节流（有 `active_hint()` 提前返回），`md_sync` 每 2s 做一轮「读配置（含插件目录扫描）+ 3 个落点各读一次整文件 + 若干 SQL」。**这条我起初以为很贵，算完不值得改**：单轮是毫秒级，落在页缓存里不产生真实 IO；真正贵的是「内容变化时重写整篇日记」，而它已经用「实时段对齐到整分钟」把写盘频率压到了每分钟一次（`export::live_interval` 的注释把取舍写清楚了）。**不动是对的。**

### 3.7 数据安全：Markdown 双向同步 —— 良（本次补强）

这是 v0.4.0 的核心新功能，也是全项目风险最高的地方：**它在写用户的私人日记**。

做得好的部分：

- **三方合并基线**：内存里存「上次写出的区块」，用「文件变没变 / SQL 变没变」二分判定，只有两边都变才比 mtime 与 `updated_at`。比单纯的 mtime 轮询安全得多；
- **标题缺失不导入**：只补写、不把「空」当删除，用户改标题不会误删数据；
- **待办区块一行不删**（它是过滤视图，「文件里没有」证明不了用户想删）；
- **只改目标标题那一段**，其余字节原样保留；CRLF/LF 归一后再换回；
- **原子写**：同目录临时文件 + rename，写一半崩溃不会留半个区块。

弱点（本次已补一半）：

- **覆写前没有副本**。原子写只保证「不留半个区块」，保证不了「写进去的内容是对的」。区块边界判错（用户手写了 `#` 开头但不打算当标题的行、粘贴了别人的片段）就是覆写手写内容，只能靠 OneDrive/坚果云的历史版本兜底。
- **跨设备的最后写入者胜**（ADR-033 已记录为已知取舍）。两台机器同时开 Timing 同步同一份 OneDrive 日记，落后一方会覆盖回去。这不是 bug，是设计取舍，但**用户不一定知道**——建议在设置页「同步」页签加一句人话说明，见 §6 B 档。

### 3.8 发布工程 —— 弱

- `tauri.conf.json` 无 `plugins.updater`、无 `createUpdaterArtifacts`、无签名配置 → **用户装了 0.4.0 就永远停在 0.4.0**，每次升级要手动下载重装；
- `webviewInstallMode: embedBootstrapper` → 首次安装要联网拉 WebView2；
- 未签名 → SmartScreen 拦截。

这三条都不是代码问题，是证书（要买）与托管（要域名/对象存储）的问题。上一轮评估把它们归到「有意未做」，我同意——但**它的用户成本是真实的**：每发一版，愿意手动重装的老用户就少一批。

### 3.9 工程治理 —— 弱（最该立刻处理的一条）

```
git log --oneline -5
ec02bf8 feat: align timer bar with Timing reference      ← 最后一次提交
...
git status --short | wc -l
162 修改 · 189 未跟踪 · 22 删除 · 184 files changed, 9093 insertions(+), 5494 deletions(-)
```

也就是说：**从 0.2.1 之后，0.3.0 / 0.3.x / 0.4.0 的全部成果都只有工作区一份，没有进版本库。** 6 类门禁把代码质量守得很好，但没有任何机制防止「一次误操作丢掉三个月的工作」。这是我在这次评估里唯一认为是 P0 的问题——比任何代码问题都危险。

（`docs/` 里 20 多个 ADR、IPC 契约、设计规格也是同一状态。）

## 5. 本次已落地的优化

四条都改在「出事了能不能查」和「数据能不能救回来」上，不碰业务逻辑、不碰 IPC 契约（命令仍是 65、事件 11、错误码 16）。

### O1 前端运行时兜底

- **问题**：主窗是 384×360 的全透明窗口，药丸是它唯一的可见内容。React 渲染期抛错会卸载整棵树 → 用户看到「药丸凭空消失」，而错误在 WebView 里，Rust 侧完全无痕。
- **改法**：
  - 新增 `src/components/ui/AppErrorBoundary.tsx`：`getDerivedStateFromError` + `componentDidCatch`，兜底界面是**能点的**（一条含原因与「重新加载」按钮的卡片，走设计令牌，不自造颜色）；
  - 同文件导出 `installGlobalErrorHooks()`：挂 `error` 与 `unhandledrejection`，走既有 `NoticeBar` 提示（事件回调里的异步抛错不再静默）；
  - `src/main.tsx` 在外层包住 `<App />`，并 import 新的 `src/styles/error-boundary.css`。
- **为什么不用「上报后端」**：前端落盘需要新增一条 IPC 命令 → 牵动契约 4 处 + 文档 + 契约评审。这一版先做「别静默消失」，落盘作为 §6 A 档的下一步。
- **验证**：`npm run check` 全绿（typecheck / lint / 行数 / 分层）；`npm test` 245 通过；`npm run build` 通过。

### O2 错误统一收口 + 日志分级

- **问题**：65 条命令的失败路径没有统一埋点；全项目 `log_error!` 使用次数为 0，真故障和良性告警同级。
- **改法**：在 `impl Serialize for AppError`（`src-tauri/src/error.rs`）里埋点——**这是命令错误回到前端的唯一收口**，一处覆盖 65 条命令，不用在 65 个 command 里各写一遍（写了也一定会漏）。分级：
  - `DB_ERROR` / `IO_ERROR` → `ERROR`（用户看不出原因、必须留痕）；
  - 业务校验类（找不到 / 名字为空 / 时长非法…）→ `DEBUG`（界面已给明确提示，`TIMING_LOG=debug` 才可见，避免把正常操作刷成告警）。
- **顺带修文档漂移**：`ErrorCode` 文档头写「共 15」，实际枚举 16 个（V0.4.0 新增 `MD_SYNC_CONFIG_INVALID` 后没同步）。已改为「共 16」并补上 V0.4.0 那笔。
- **验证**：`cargo test` 338 通过；`cargo clippy -- -D warnings` 0 error；`cargo fmt --check` 通过。

### O3 关键业务事件埋点

只加 INFO，不加噪声：

| 位置 | 记什么 | 为什么 |
|---|---|---|
| `services/timer.rs::start` | `timer start: item=<id> at=<ms>` | 「计时怎么少了」的第一现场 |
| `services/timer.rs::switch` | `timer switch: item=<id> mode=<..> at=<ms>` | 分段与仅改归属是两套语义，事后要能分清 |
| `services/timer_stop.rs::stop` | `timer stop: saved id=<id> item=<id> accumulated=<s>s` | 结束时的真实累计秒，可对账 |
| 同上（阈值分支） | `timer stop: discarded id=<id> accumulated=<s>s` | 「我明明计了却没记上」→ 一看就知道是低于最短记录时长被忽略 |
| `services/md_sync/import.rs::by_kind` | `md import <kind>: created=/updated=/deleted=` | **导入是唯一会按用户手改删数据的路径**（默认软删），必须可回溯 |
| `infra/md_file.rs::write_section` | `md write: <path> (<bytes> bytes, backup=<bool>)` | 写用户文件这个动作本身要留痕，含是否留底 |

量级：一次用户动作一行，一天最多几百行，远小于 7 天滚动清理的承受能力。

### O4 Markdown 写前留底

- **问题**：原子写不防「写错」。区块边界判错就是把用户手写内容写没了。
- **改法**：新增 `src-tauri/src/infra/md_backup.rs`：
  - 只在「文件已存在**且内容确实要变**」时留底（新建文件没有旧内容可丢，空内容不写）；
  - 落点 `<app_data_dir>/backups/md/`，**不写进用户 vault**——不在 Obsidian 库里堆 `.bak`；
  - 文件名 `<原文件名>-<yyyyMMdd-HHmmss>.md`，中文保留（能一眼看出是哪篇日记），路径分隔符与 `..` 一律替换成 `_`；
  - 保留最近 30 份，按修改时间淘汰（与 `platform::log` 同口径）；
  - **任何失败都静默**：留底是附加保险，不能因为它写不出来挡住同步本身。
- **接入**：`infra/md_file.rs::write_section` 在 `write_atomic` 之前调用；`app/bootstrap.rs` 在日志初始化后注入落点目录（放在 `app_data` 而非 vault，是这条设计的重点）。
- **验证**：新增 4 条单测（原样保存 / 空内容不备份 / 超量淘汰 / 文件名净化），`cargo test` 338 全绿。

## 6. 建议但本次未做

### A 档：低成本高收益，建议下个版本就做

1. **提交这一版**（P0，见 G1）。建议按版本拆 commit，别做成一个 9000 行的巨型提交——将来 `git bisect` 会感谢你。
2. **删 `core:event:allow-emit`**（1 行）：前端只 `listen` 从不 `emit`，这条权限让 WebView 里的任意脚本能伪造 `timer:state-changed` 这类后端事件，与 ADR-015「最小权限」的方向相反。改完跑一次 `npm run tauri dev` 冒烟（托盘 / 设置 / 便利贴各点一遍）即可。
3. **Vite 分包**：`build.rollupOptions.output.manualChunks` 把 `react`/`react-dom`/`lucide-react` 拆出去。目的是让首帧只等首屏代码，先把 G5 的长尾压下去一半，再谈 WebView 参数。
4. **前端错误落盘**：新增一条 `log_frontend { level, message }` 命令（要走一次契约评审：4 处 + 文档 + `errorText` 不涉及）。做完之后「药丸消失」类反馈才有据可查。

### B 档：需要外部条件或专项测量

5. **自动更新 + 签名**（G6）：证书（约千元/年）+ 一处能放 `latest.json` 的 HTTPS。代码侧只差 `tauri.conf.json` 的 `plugins.updater` 与 release workflow。**没有证书之前，不建议先接线**——半成品更新器比没有更糟。
6. **首帧长尾专项**（G5）：先量后改。顺序建议：分包 → 复测 → 若仍 >1s 再试去掉 `--disable-gpu`（牺牲一点透明稳定性换首帧），最后才考虑 Rust 侧（数据显示那里只有 31ms，先别碰）。
7. **`opt-level` 复测**（G10）：`"s"` → `"3"` 打一次包，对比 exe 体积与 `boot-timing` 的 `setup`。有数据再定，别凭直觉。
8. **同步页签补一句人话**（G12）：「两台电脑同时改同一篇日记时，后保存的那台会覆盖另一台」。

### C 档：明确不建议

- **E2E（`tauri-driver`）**：单人项目维护成本高于收益，5 条手测清单够用（把清单贴进 PR 模板即可）。
- **引入 UI 框架（MUI/AntD）**：与「极轻悬浮条 + 手写令牌 + 零字面量色值」直接冲突，体积翻十倍。
- **前端自建缓存层**：零内存业务状态是 A2 级优点，读放大在本机单用户场景可忽略，别为假想性能问题引入真一致性问题。
- **重写 `useWindowAutoFit`**：它是平台缺陷驱动的补偿层（ADR-014），已被抽成纯函数 + 21 条用例。看不懂可以，动它不行。
